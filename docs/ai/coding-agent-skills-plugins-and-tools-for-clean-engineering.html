Overview

Use this note as a practical menu for configuring coding agents to produce cleaner code across TypeScript/Next.js, Python, Go, Rust, Java/Spring, and polyglot repos.
The setup should not rely on one big “clean code” prompt.
Use different layers:
  • AGENTS.md for permanent repo rules
  • skills for task-specific workflows
  • MCP/tools for code intelligence and deterministic checks
  • hooks/CI for enforcement
Use these resources when the goal is:
  • clean architecture
  • folder structure
  • separation of concerns
  • linting
  • type checking
  • API structure
  • test placement
  • dedicated test folders
  • avoiding unnecessary try/catch
  • framework-specific best practices
  • agent-review workflows

Selection filter

Include:
  • official or vendor-backed
  • maintained by a known expert or organization
  • specific to a coding-agent skill, plugin, MCP tool, or repo workflow
  • useful for linting, typing, tests, architecture, or framework conventions
  • trusted by the community or clearly tied to a mature ecosystem
Exclude:
  • generic “clean code” prompts
  • random low-signal skills
  • broad marketplaces without a specific useful item
  • skills that only repeat SOLID principles without a workflow or enforcement path

TypeScript, React, and Next.js

vercel-labs/next-skills

Next.js-specific agent skills.
Use when the agent is editing:
  • App Router code
  • Server Components
  • Server Actions
  • caching behavior
  • layouts
  • route handlers
  • Next.js file conventions

Practical use

Add this to the coding-agent prompt when the task touches Next.js behavior:
Use the Next.js skills from vercel-labs/next-skills for App Router, Server Components, Server Actions, caching, routing, and file conventions. Keep route handlers thin. Separate validation, business logic, and data access.
Good AGENTS.md rule:
For Next.js code, follow App Router conventions. Route handlers should delegate to validation, service, and data-access layers. Do not put business logic directly inside route handlers.

vercel-labs/react-best-practices

React/Next.js best-practices skill.
Use when the agent is editing:
  • React components
  • client/server boundaries
  • data fetching
  • render behavior
  • component structure
  • frontend performance
  • bundle-sensitive code

Practical use

Ask the agent to run this as a review pass after implementing UI changes:
Review the React/Next.js changes using react-best-practices. Check for unnecessary client components, avoidable re-renders, data-fetching mistakes, bundle bloat, and weak component boundaries.
Good AGENTS.md rule:
Do not mark components as client components unless browser APIs, state, effects, or event handlers require it. Keep server-renderable code on the server.

addyosmani/code-review-and-quality

Code quality review skill.
Use when the agent has finished a non-trivial change.

Practical use

Run as the final review pass:
Before finalizing, use code-review-and-quality to review correctness, readability, architecture, maintainability, security, and performance. Fix issues found by the review before reporting completion.
Good AGENTS.md rule:
Before completion, review the diff for avoidable complexity, weak abstractions, duplicated logic, misplaced responsibilities, and missing validation.

addyosmani/spec-driven-development

Spec-first workflow skill.
Use before implementation when the task includes:
  • new modules
  • larger refactors
  • new APIs
  • behavior changes
  • unclear boundaries
  • multi-file changes

Practical use

Start the task with:
Use spec-driven-development first. Define the behavior, module boundaries, affected files, test plan, and non-goals before editing code.
Good AGENTS.md rule:
For larger changes, first identify the smallest coherent implementation slice, then define expected behavior and validation commands before editing.

addyosmani/doubt-driven-development

Adversarial review skill.
Use when the agent is making assumptions about:
  • architecture
  • migration strategy
  • security
  • performance
  • framework behavior
  • unfamiliar code paths

Practical use

Add before finalizing risky changes:
Use doubt-driven-development to challenge the implementation. Look for wrong assumptions, fragile design, missing edge cases, and hidden coupling. Apply fixes before completion.
Good AGENTS.md rule:
When touching unfamiliar or high-risk code, explicitly check assumptions against existing tests, nearby code, and framework conventions.

addyosmani/browser-testing-with-devtools

Browser validation skill using Chrome DevTools MCP.
Use when the task affects:
  • UI behavior
  • forms
  • client-side state
  • network calls
  • browser console errors
  • visual output
  • performance

Practical use

After frontend implementation:
Use browser-testing-with-devtools to inspect the page, console, network requests, DOM state, and user-visible behavior. Do not rely only on unit tests for UI changes.
Good AGENTS.md rule:
For UI changes, validate browser behavior when possible. Check console errors, failed requests, and visible state transitions.

addyosmani/web-quality-skills

Web quality skill pack.
Use when the task affects:
  • accessibility
  • Core Web Vitals
  • Lighthouse score
  • frontend performance
  • perceived speed
  • UX quality

Practical use

Use this after UI changes or performance-sensitive work:
Run a web-quality review. Check accessibility, layout stability, loading behavior, performance regressions, and obvious UX issues.
Good AGENTS.md rule:
UI changes must not introduce obvious accessibility regressions. Prefer semantic HTML, keyboard-accessible controls, and stable layouts.

mattpocock/skills

TypeScript/TDD skill collection.
Use when the task is TypeScript-heavy or test-sensitive.

Practical use

Use for TypeScript behavior changes:
Use the TypeScript/TDD workflow from mattpocock/skills. Add or update tests before changing behavior. Prefer strong types over loose any or type assertions.
Good AGENTS.md rule:
Avoid any unless there is a clear boundary reason. Prefer explicit types, inferred local types, discriminated unions, and narrow interfaces.

ESLint MCP Server

Official ESLint MCP tool.
Use when the agent can access MCP tools and the project uses ESLint.

Practical use

Connect ESLint MCP so the agent can get lint diagnostics directly.
Good AGENTS.md rule:
Run the project lint command before completion. Fix lint errors instead of suppressing them unless the suppression is local, justified, and minimal.

Example validation commands

pnpm lint
npm run lint
yarn lint

Model Context Protocol TypeScript SDK

SDK for building custom MCP tools.
Use when normal linters do not cover repo-specific rules.

Practical use

Build custom MCP tools for checks like:
  • route handlers contain too much business logic
  • tests are outside approved folders
  • broad catch blocks swallow errors
  • files violate folder conventions
  • API modules bypass the service layer
  • generated files were edited manually
Good AGENTS.md rule:
Use project validators when available. Do not bypass repo-specific architecture checks.

Python

GitHub Awesome Copilot pytest-coverage skill

Python test coverage skill.
Use when the task changes Python behavior.

Practical use

After implementation:
Run the pytest coverage workflow. Identify uncovered changed lines and add focused tests for meaningful behavior gaps.
Good AGENTS.md rule:
Python behavior changes require tests. Prefer focused tests for behavior and edge cases over snapshot-style coverage padding.

Example validation commands

pytest
pytest --cov

GitHub Copilot CLI pytest-gen skill

Pytest generation skill.
Use when adding tests for existing Python code.

Practical use

Tell the agent:
Generate pytest tests that follow the existing test folder structure and naming conventions. Do not place tests next to source files unless the repo already uses that convention.
Good AGENTS.md rule:
Tests belong under the repo’s dedicated test directory unless an existing package-level convention says otherwise.

GitHub Awesome Copilot python-pypi-package-builder skill

Python packaging and quality workflow skill.
Use for Python libraries, packages, and reusable modules.

Practical use

Use when the task touches packaging or public APIs:
Apply the Python package workflow. Validate tests, linting, typing, packaging metadata, versioning, and build output before completion.
Good AGENTS.md rule:
Public package changes must preserve backward compatibility unless the task explicitly allows breaking changes.

Ruff

Python linting and formatting tool.
Use for every Python repo where possible.

Practical use

Put Ruff commands in AGENTS.md, hooks, or CI.
Good AGENTS.md rule:
Run Ruff before completion. Fix warnings rather than adding broad ignores.

Example validation commands

ruff format --check .
ruff check .

Pyright

Python type checker.
Use when the repo uses typed Python or should move toward typed Python.

Practical use

Run after behavior changes:
pyright
Good AGENTS.md rule:
Prefer typed function boundaries for services, API handlers, and data-access modules. Do not weaken types to silence errors.

mcp-server-analyzer

Python code-analysis MCP server.
Use when you want MCP-based Python diagnostics.

Practical use

Use as an MCP analysis layer for Ruff-style checks, type-related checks, dead-code detection, and Python project inspection.
Good AGENTS.md rule:
When MCP analysis tools are available, use them before manual refactoring.

ruff-mcp-server

Ruff MCP server.
Use when the agent should access Ruff through MCP instead of shell commands.

Practical use

Connect it when the coding environment supports MCP and you want lint feedback exposed directly to the agent.
Good AGENTS.md rule:
Use Ruff diagnostics as source of truth for Python linting and formatting issues.

mcp-language-server

Cross-language language-server MCP tool.
Use for Python with:
  • Pyright
  • pylsp
  • other Python language servers

Practical use

Use for safer refactors:
Before renaming or moving Python symbols, use LSP references and diagnostics.
Good AGENTS.md rule:
Do not perform broad Python renames by text search only. Use language-server references where available.

  • REST tests
  • Spring Security tests
  • WebFlux tests
  • WebSocket tests
  • integration tests
Good AGENTS.md rule:
Keep controller, service, repository, and integration tests in their proper locations. Do not replace integration tests with shallow unit tests when framework behavior matters.

Good AGENTS.md rule:
Keep controllers thin. Put business logic in services or use-case classes. Keep persistence concerns out of domain logic unless the repo convention explicitly differs.

AGENTS.md official format

Agent instruction format.
Use for permanent repo instructions.

Practical use

Put stable rules here:
  • project structure
  • architecture boundaries
  • test placement
  • lint commands
  • typecheck commands
  • build commands
  • forbidden shortcuts
  • error-handling expectations
Good AGENTS.md rule:
If instructions conflict with the repo’s existing conventions, stop and ask or follow the more local repo-specific instruction.

Practical setup by stack

TypeScript / Next.js

Use:
  • vercel-labs/next-skills
  • vercel-labs/react-best-practices
  • ESLint MCP Server
  • mcp-language-server
  • addyosmani/code-review-and-quality

Enforce

pnpm lint
pnpm typecheck
pnpm test
pnpm build

Permanent repo rules

  • route handlers stay thin
  • validation is separate from business logic
  • data access is separate from request handling
  • avoid unnecessary client components
  • avoid broad try/catch unless it adds recovery, translation, cleanup, or contextual logging

Python

Use:
  • GitHub pytest-coverage skill
  • GitHub pytest-gen skill
  • Ruff
  • Pyright
  • mcp-language-server

Enforce

ruff format --check .
ruff check .
pyright
pytest

Permanent repo rules

  • tests live under the dedicated test folder unless the repo convention differs
  • no broad exception swallowing
  • typed service/API boundaries
  • business logic stays outside API route handlers
  • data access stays behind clear repository/client modules

Go

Use:
  • samber/cc-skills-golang
  • cxuu/golang-skills
  • golangci-lint
  • mcp-gopls
  • mcp-language-server

Enforce

gofmt -w .
go test ./...
golangci-lint run

Permanent repo rules

  • idiomatic error handling
  • package boundaries stay clear
  • avoid premature abstraction
  • prefer small interfaces
  • use table-driven tests where useful
  • benchmarks for critical paths

Rust

Use:
  • leonardomso/rust-skills
  • apollographql/skills
  • mcp-language-server
  • agent-lsp

Enforce

cargo fmt --check
cargo clippy
cargo test

Permanent repo rules

  • no unnecessary unwrap
  • explicit error handling
  • clear module boundaries
  • tests follow repo convention
  • use Result and domain errors intentionally

Java / Spring

Use:
  • spring-ai-community/spring-testing-skills
  • java-architect skill
  • polyglot-test-agent
  • mcp-language-server

Enforce

mvn test
mvn verify
or:
./gradlew test
./gradlew check

Permanent repo rules

  • controllers stay thin
  • services own business logic
  • repositories own persistence
  • DTO/domain separation where relevant
  • unit, integration, and API tests stay in proper locations
  • migration changes must be explicit and tested
