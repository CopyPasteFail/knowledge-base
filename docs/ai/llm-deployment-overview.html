LLM Deployment Overview

Overview

Deploying Large Language Models (LLMs) for real-time inference in production requires a careful selection of technologies and architectural patterns. This guide explains how various components connect and offers comparisons to help making informed decisions.

Key Terms

Before diving into the architecture, let's define some fundamental terms used throughout this guide:
  • API (Application Programming Interface): A set of rules and protocols for building and interacting with software applications.
  • API Gateway: A management tool that sits in front of backend services (like your LLM inference endpoints) to handle requests, routing, security, and other cross-cutting concerns.
  • ASGI (Asynchronous Server Gateway Interface): A specification for Python web servers and applications to communicate asynchronously.
  • BentoML: A framework for packaging and serving AI/ML models as production APIs and deployable services. It is useful when you want a practical serving layer around models from different frameworks.
  • Autoregressive generation: The process by which LLMs generate text token by token, using previously generated tokens as context for the next one.
  • Canary Deployments: A deployment strategy where a new version of an application is rolled out to a small subset of users or traffic first, before a full rollout.
  • Cluster Autoscaler: A Kubernetes component that automatically adjusts the number of Nodes in your cluster based on the resource requirements of your pending Pods and the utilization of existing Nodes.
  • Cold Start: The delay experienced when a new instance of an application (e.g., an LLM serving container) needs to start up and load its resources (like model weights) into memory.
  • Container: A lightweight, standalone, executable package of software that includes everything needed to run an application: code, runtime, system tools, libraries, and settings.
  • Continuous Batching: An optimization technique used by LLM serving engines (like vLLM and TGI) that processes multiple incoming requests concurrently, constantly feeding new tokens to the GPU as resources become available from other ongoing requests, maximizing throughput.
  • Declarative Configuration: A paradigm where you define the desired state of your system (e.g., in YAML files), and the system (like Kubernetes) works to achieve and maintain that state.
  • DevOps Practices: A set of software development practices that combine software development (Dev) and information technology operations (Ops) to shorten the systems development life cycle and provide continuous delivery with high software quality.
  • Docker: A platform that enables developers to package applications and their dependencies into standardized units called containers.
  • Docker Image: A read-only template with instructions for creating a Docker container.
  • Dynamic Batching: A general term for batching requests on the fly, often used interchangeably with "continuous batching" in the context of LLMs, where batches are not fixed in size and new requests can join an ongoing batch.
  • FastAPI: A modern, fast (high-performance) Python web framework for building APIs.
  • Fine-tuning: The process of taking a pre-trained LLM and further training it on a smaller, specific dataset to adapt it to a particular task or domain.
  • FlashAttention: An optimized attention algorithm that speeds up Transformer computation and reduces memory usage for long sequences.
  • Gateway API: A set of Kubernetes APIs that provide advanced traffic routing and load balancing capabilities, particularly useful for modern microservices and AI workloads.
  • GKE (Google Kubernetes Engine): Google Cloud's managed Kubernetes service.
  • GKE Inference Gateway: An extension to the Kubernetes Gateway API specifically designed by Google to optimize routing and load balancing for generative AI workloads (like LLMs) on GKE.
  • GPU (Graphics Processing Unit): A specialized electronic circuit designed to rapidly manipulate and alter memory to accelerate the creation of images, but also highly effective for parallel computations required by deep learning models.
  • Hugging Face: A company and platform that fosters an open-source community around machine learning, providing tools, models, datasets, and a central hub for AI development.
  • Hugging Face Hub: A platform where users can share and discover machine learning models, datasets, and demos.
  • Hugging Face transformers: A library that provides pre-trained models, tokenizers, and configuration for a vast array of Transformer-based models, including LLMs.
  • Hugging Face transformers format: A standardized way of saving and loading LLM models, tokenizers, and configurations, widely supported across the ML ecosystem.
  • HPA (Horizontal Pod Autoscaler): A Kubernetes feature that automatically scales the number of Pod replicas in a Deployment or ReplicaSet based on observed metrics (e.g., CPU utilization, custom metrics).
  • Inference: The process of using a trained machine learning model to make predictions or generate outputs based on new input data. For LLMs, this means generating text from a given prompt.
  • Kubernetes: An open-source container orchestration platform that automates the deployment, scaling, and management of containerized applications.
  • KV Cache (Key-Value Cache): A memory optimization technique used in Transformer models during inference to store previously computed "Key" and "Value" vectors, avoiding redundant computations.
  • Latency: The time delay between a request being sent and a response being received. For LLMs, this includes Time-to-First-Token (TTFT) and Time-to-Last-Token (TTLT).
  • LiteRT: Google's renamed on-device AI runtime (successor to TensorFlow Lite), designed for running ML models, including LLMs, directly on devices like phones and web browsers.
  • LLM (Large Language Model): A type of artificial intelligence model capable of understanding and generating human-like text.
  • Load Balancer: A networking device or software that distributes incoming network traffic across a group of backend servers or services to ensure high availability and reliability.
  • LoRA (Low-Rank Adaptation): A parameter-efficient fine-tuning (PEFT) technique that allows adapting large pre-trained models to new tasks with minimal computational cost by training only a small number of new parameters.
  • MediaPipe: An open-source framework by Google for building multimodal (e.g., video, audio, text) machine learning pipelines, often used for on-device ML.
  • Microservices: An architectural style that structures an application as a collection of loosely coupled, independently deployable services.
  • MLOps: A set of practices that combine Machine Learning, DevOps, and Data Engineering to streamline the entire machine learning lifecycle, from experimentation to production deployment and monitoring.
  • NVIDIA MIG (Multi-Instance GPU): A feature on certain NVIDIA GPUs that allows a single GPU to be partitioned into multiple, isolated GPU instances, enabling more efficient sharing of GPU resources.
  • Node: A worker machine in a Kubernetes cluster, which can be a VM or a physical server, where Pods are launched.
  • Node Pool: A group of Nodes within a Kubernetes cluster that have the same configuration.
  • ONNX Runtime: A high-performance inference engine for ONNX (Open Neural Network Exchange) models, supporting various hardware and frameworks.
  • Parameters: The internal variables or "weights" of a machine learning model that are learned during the training process and define its behavior. The number of parameters often indicates a model's size and complexity.
  • Persistent Storage: Data storage that outlives the Pods or containers that created it, ensuring data is not lost when Pods are restarted or deleted. In Kubernetes, this is often provided by Persistent Volumes.
  • Pod: The smallest deployable unit in Kubernetes. A Pod represents a single instance of a running process in a cluster, often containing one or more containers.
  • Prometheus / Grafana / Cloud Logging: Common tools used for monitoring (Prometheus for metrics collection, Grafana for visualization) and centralized logging (Cloud Logging for log aggregation and analysis) in cloud environments.
  • Quantization: A technique to reduce the precision of model weights (e.g., from 32-bit to 8-bit or 4-bit) to decrease model size and memory footprint, leading to faster inference with minimal accuracy loss.
  • Resource Packing/Bin Packing: The strategy of efficiently placing multiple smaller workloads (e.g., LLM inference Pods) onto larger compute resources (e.g., GPU Nodes) to maximize utilization and reduce costs.
  • Rolling Updates: A Kubernetes deployment strategy that gradually replaces old versions of Pods with new ones, ensuring zero downtime during application updates.
  • Service Discovery: The process by which services or applications in a distributed system find and communicate with each other.
  • Spot VMs: Virtual machine instances on cloud providers that offer significant discounts in exchange for being interruptible (can be preempted by the cloud provider if resources are needed elsewhere).
  • .task file format: A specific model format used by Google's MediaPipe LLM Inference API for on-device LLMs, bundling the model with tokenizer parameters.
  • TensorFlow: An open-source machine learning framework developed by Google, widely used for building and deploying deep learning models.
  • TensorFlow Serving: A production-serving system for machine learning models, especially common in TensorFlow/TFX environments and SavedModel-based deployments.
  • TensorRT-LLM: An NVIDIA library and toolkit specifically designed to optimize and accelerate LLM inference performance on NVIDIA GPUs.
  • TGI (Text Generation Inference): Another highly optimized open-source toolkit for deploying and serving LLMs, developed by Hugging Face.
  • Throughput: The rate at which a system can process requests or generate outputs (e.g., tokens per second, requests per second).
  • Tokenization: The process of breaking down raw text into smaller units called "tokens" that a language model can understand and process.
  • torch (PyTorch): An open-source machine learning framework that provides the core components for building and running deep neural networks, especially on GPUs.
  • TorchServe: A PyTorch model-serving framework. It is mostly relevant for existing TorchServe deployments rather than new projects because the project is now in limited maintenance.
  • TPU (Tensor Processing Unit): A type of specialized hardware accelerator developed by Google, optimized for machine learning workloads, particularly neural networks.
  • Uvicorn: A lightning-fast ASGI server, commonly used to run FastAPI applications.
  • vLLM: A high-throughput and memory-efficient open-source serving engine specifically designed for LLM inference.
  • VM (Virtual Machine): A virtualized computer system that runs on a physical server, acting like a separate physical machine with its own operating system and resources.
  • Vertex AI Endpoints: A fully managed service on Google Cloud for deploying and serving machine learning models, abstracting away much of the underlying infrastructure.

Connecting the Dots: An Ecosystem Overview

At its core, LLM inference involves taking a trained LLM and making it available to receive prompts and generate responses efficiently. This journey involves several layers of technology:
  • The LLM Itself: This is your trained or fine-tuned model, typically saved in a standard format (like Hugging Face transformers format).
  • Underlying Deep Learning Framework (torch / TensorFlow): This is the computational engine that performs the actual mathematical operations of the LLM on hardware (like GPUs or TPUs).
  • LLM Inference Serving Engines (vLLM, TGI, TensorRT-LLM, ONNX Runtime): These are specialized software layers built on top of the deep learning framework. They are designed to optimize the performance of LLM inference specifically, handling complex tasks like continuous batching and KV Cache management to maximize throughput and minimize latency.
  • API Layer (Custom FastAPI Application): While vLLM/TGI provide an API, you might wrap them in a custom FastAPI application to add custom business logic, authentication, or integrate with other microservices.
  • Containerization (Docker): The LLM, serving engine, and any custom code are packaged into a self-contained Docker image using Docker.
  • Deployment Platform (VMs, GKE, Vertex AI Endpoints): This is the infrastructure where your Docker containers run as Pods, providing compute resources, scalability, and reliability. This can be a raw VM, a managed Kubernetes service like GKE, or a fully managed ML endpoint like Vertex AI Endpoints.
In essence, you package your LLM and an optimized serving engine (like vLLM or TGI) into a Docker container. This container then runs as a Pod on a chosen cloud platform (VM, GKE, or Vertex AI Endpoints), which handles the underlying hardware and scaling. Your applications then interact with this deployed service via an API Gateway or Load Balancer.

Core LLM Inference Optimization Concepts

KV Cache (Key-Value Cache)

The KV Cache is a critical optimization for Transformer-based LLMs during text generation (inference).
  • What it is: In Transformer models, each token's "attention" calculation involves generating "Key" and "Value" vectors. During autoregressive generation (token by token), the model needs to attend to all previously generated tokens (and the initial prompt). The KV Cache stores these computed Key and Value vectors in GPU memory.
  • Why it's needed: Without the KV Cache, the model would have to recompute the Key and Value vectors for all preceding tokens at every step of generation. This leads to a quadratic increase in computation and memory usage with sequence length, making long generations extremely slow.
  • How it optimizes: By storing the KV pairs, the model only needs to compute them for the new token being generated, significantly reducing redundant computation and speeding up subsequent token generation.
  • Impact: While it dramatically speeds up computation, the KV Cache itself consumes a significant amount of GPU memory, which grows linearly with the sequence length and the number of concurrent requests. Efficiently managing this memory is paramount for high throughput.

Tokenization

Tokenization is the fundamental first step in processing text for LLMs.
  • What it is: The process of breaking down raw text (like a user's prompt or a generated response) into smaller units called "tokens." These tokens can be words, subwords, or even individual characters, depending on the tokenizer used.
  • Why it's needed: LLMs don't understand raw text directly; they operate on numerical representations. Tokenization converts human-readable text into a sequence of numerical IDs that the model can process. Conversely, it converts the model's output IDs back into human-readable text.
  • Impact: The choice of tokenizer affects the model's vocabulary size, the length of sequences, and ultimately, the model's performance and efficiency. Efficient tokenization is crucial for minimizing the number of tokens processed, which directly impacts cost and latency.

Tokenization Methods

Different algorithms are used to perform tokenization, each with its own characteristics:
  • Word-based Tokenization:
    What it is: Splits text into words using spaces or punctuation as delimiters.
    • Pros: Simple, human-readable tokens.
    • Cons: Very large vocabulary for many languages; struggles with out-of-vocabulary (OOV) words (words not seen during training).
    • Use Cases: Basic NLP tasks, older models.
  • Character-based Tokenization:
    What it is: Splits text into individual characters.
    • Pros: Smallest vocabulary size; can handle any word (no OOV issues).
    • Cons: Very long sequences of tokens, which increases computational cost; less semantic meaning per token.
    • Use Cases: Specific tasks where character-level detail is crucial, or for very small models.
  • Subword Tokenization (BPE, WordPiece, SentencePiece): The most common approach for modern LLMs, balancing vocabulary size and sequence length.
    What it is: Breaks words into smaller, frequently occurring subword units. This allows the tokenizer to handle rare or unseen words by composing them from known subwords.
    • Common Methods:
      • BPE (Byte Pair Encoding): Iteratively merges the most frequent pairs of characters or character sequences in the training data until a desired vocabulary size is reached.
      • WordPiece: Used by models like BERT and DistilBERT. Similar to BPE but merges based on likelihood of forming a new word in the training data.
      • SentencePiece: A language-independent subword tokenizer that can handle raw text directly, including whitespace. It's often used by models like Llama and Gemma.
    • Pros: Balances vocabulary size and sequence length; handles out-of-vocabulary words (by breaking them into known subwords); efficient for many languages; reduces the overall number of tokens for complex words compared to character-based.
    • Cons: Less intuitive for humans to read tokens; can be complex to implement from scratch.
    • Use Cases: All modern LLMs (e.g., GPT, Llama, Mistral, Gemma) rely on subword tokenization for efficient and effective language processing.

LLM Inference Serving Engines

These are specialized software solutions designed to run LLMs efficiently in production. They are built on top of deep learning frameworks like PyTorch (torch) and TensorFlow and leverage models from libraries like Hugging Face transformers.

vLLM

  • What it is: An open-source, high-throughput, and memory-efficient serving engine for LLM inference, developed at UC Berkeley.
  • Key Innovation: PagedAttention: Inspired by operating system virtual memory, PagedAttention manages the KV Cache by breaking it into non-contiguous "blocks." This drastically reduces memory waste (internal and external fragmentation) and allows for more concurrent requests on a single GPU.
  • Continuous Batching: vLLM dynamically batches incoming requests and processes them token-by-token. As soon as a token is generated for one request, its GPU resources are immediately freed and can be used by another request in the batch, maximizing GPU utilization.

Text Generation Inference (TGI)

  • What it is: Another highly optimized open-source toolkit for deploying and serving LLMs, developed by Hugging Face.
  • Key Features: Also employs dynamic batching (continuous batching), supports various quantization methods, tensor parallelism (sharding models across multiple GPUs), and integrates with FlashAttention (an optimized attention mechanism). It often provides an OpenAI-compatible API.

TensorRT-LLM

  • What it is: An NVIDIA library and toolkit specifically designed to optimize and accelerate LLM inference performance on NVIDIA GPUs. It generates highly optimized kernels for specific LLM architectures and hardware.
  • Pros:
    Maximum Performance on NVIDIA GPUs: Often achieves the highest throughput and lowest latency on NVIDIA hardware due to highly specialized kernels.
  • Deep Optimization: Leverages NVIDIA's deep expertise in GPU optimization.
  • Supports Advanced Features: Includes features like quantization, tensor parallelism, and efficient KV Cache management.
    Cons:
    NVIDIA-Specific: Limited to NVIDIA GPUs, not portable to other hardware (AMD, Intel, TPUs).
  • Compilation Step: Requires a compilation step to convert models into TensorRT engines, which can add complexity to the MLOps pipeline.
  • Less Flexible for Custom Architectures: May require more effort to support highly custom or experimental LLM architectures compared to more general frameworks.
    Use Cases:
  • High-performance, production-grade LLM inference on NVIDIA GPU infrastructure.
  • Scenarios where every millisecond of latency or every token per second of throughput matters.

ONNX **Runtime

  • What it is: A high-performance inference engine for ONNX (Open Neural Network Exchange) models. ONNX is an open format designed to represent machine learning models, allowing models to be trained in one framework (PyTorch, TensorFlow) and then run in another.
  • Pros:
    • Cross-Platform Compatibility: Runs on a wide variety of hardware (CPUs, GPUs from different vendors, edge devices) and operating systems.
    • Framework Agnostic: Can run models trained in PyTorch or TensorFlow after conversion to ONNX format.
    • Optimizations: Provides its own set of optimizations like graph fusions and kernel improvements.
      \
  • Cons:
    • Conversion Step: Requires converting your LLM to the ONNX format, which can sometimes be complex or lose certain optimizations.
    • Potentially Lower Peak Performance: While highly performant, it might not always match the absolute peak throughput of hardware-specific engines like TensorRT-LLM for certain LLM architectures on NVIDIA GPUs.
  • Use Cases:
    • Deploying LLMs across diverse hardware environments (e.g., cloud, edge, mobile).
    • Ensuring model portability between different training and inference environments.
    • Scenarios where flexibility in deployment targets is a high priority.

Custom FastAPI Application

  • What it is: A modern, high-performance Python web framework for building APIs, leveraging standard Python type hints and asynchronous programming (ASGI). It typically runs with an ASGI server like Uvicorn.
  • Role in LLM Inference: Can be used as a thin API wrapper around highly optimized LLM serving engines (like vLLM/TGI) to add custom logic, authentication, or integrate with other services. Less commonly, it can directly load and serve LLMs, but this is less performant for concurrent requests without significant manual optimization.
  • Pros: High flexibility, good for custom logic, familiar for Python developers.
  • Cons: Direct LLM inference is less performant than specialized engines; adds a small overhead as a wrapper.
  • Use Cases: Building custom LLM applications with specific business rules, acting as a frontend for vLLM/TGI endpoints.

General Model Serving Frameworks

The tools below are broader model-serving frameworks rather than LLM-specific inference engines. They are useful when you need to package models, expose APIs, manage versions, or serve traditional ML/deep learning models alongside LLMs. For pure high-throughput LLM serving, engines like vLLM, TGI, and TensorRT-LLM are usually more directly relevant.
  • BentoML: The most practical choice for a modern, flexible serving layer. It is framework-agnostic (PyTorch, TensorFlow, sklearn, and custom Python) and simplifies turning inference scripts into production-ready REST APIs and Dockerized deployments.
  • TensorFlow Serving: A mature, high-performance system specialized for the TensorFlow/TFX ecosystem. While it operates at a lower level than BentoML, it remains a standard option for high-throughput production serving of SavedModel formats.
  • TorchServe: High-risk for new projects. Official project materials now mark it as Limited Maintenance, with no planned updates, bug fixes, new features, or security patches. It should only be used when legacy compatibility with an existing TorchServe setup is strictly required.

Deployment Platforms for LLM Inference

Bare Metal / Raw Virtual Machine (VM)

  • What it is: Directly provisioning a physical server (bare metal) or a virtualized instance (VM) with an operating system and necessary drivers. You manage everything from the OS up.
  • Pros:
    • Full Control: Complete control over hardware, software stack, and optimizations.
    • Maximum Raw Performance: No virtualization overhead (for bare metal), minimal overhead for VMs.
  • Cons:
    • High Operational Overhead: You are responsible for OS patching, security, networking, Load Balancing, and manual scaling.
    • Poor Scalability: Manual scaling is slow and inefficient for fluctuating LLM traffic.
    • Cost Inefficiency: Paying for idle resources during low traffic, difficult to optimize resource packing.
    • No Built-in High Availability: Requires significant manual effort to set up redundancy.
  • Common Use Cases:
    • Very specific, niche performance requirements where every ounce of raw power matters.
    • Highly controlled on-premises environments.
    • Research and development where deep system-level access is needed.

Managed Kubernetes (e.g., Google Kubernetes Engine - GKE)

  • What it is: A managed Kubernetes service (like GKE) that handles the Kubernetes control plane, while you manage your worker Nodes and deployments. It orchestrates Docker containers.
  • Pros:
    • Automated Scaling: Horizontal Pod Autoscaler (HPA) scales Pods, Cluster Autoscaler scales Nodes (including GPU Nodes) based on demand and custom metrics (e.g., LLM queue size).
    • High Availability & Resilience: Kubernetes self-heals, reschedules failed Pods, and supports multi-zone deployments.
    • Resource Efficiency: Efficiently packs multiple LLM Pods onto GPU Nodes, maximizing utilization. Supports Spot VMs for cost savings.
    • Declarative Configuration: Infrastructure and application state defined in YAML, enabling GitOps and reproducibility.
    • Flexibility: Provides significant control over networking, Persistent Storage, and custom configurations, leveraging concepts like Service Discovery and Gateway API.
    • Advanced Deployment Strategies: Easy blue/green and canary deployments for model updates.
  • Cons:
    • Higher Operational Complexity than Managed Endpoints: Still requires Kubernetes expertise to configure, monitor (Prometheus/Grafana), and troubleshoot (Cloud Logging).
    • Cold Start Management: While autoscaling helps, LLM cold starts (model loading) still need careful management (e.g., minReplicas > 0, persistent caching via Persistent Volume).
  • Cost: Incurs costs for Nodes (VMs + GPUs), control plane, and other Kubernetes resources.
  • Common Use Cases:
    • Organizations with existing Kubernetes expertise.
    • Complex ML platforms requiring integration with other microservices.
    • Need for fine-grained control and customization over the serving stack.
    • High-volume, variable LLM inference workloads where cost optimization through Spot VMs and efficient resource packing is critical.

Fully Managed ML Endpoints (e.g., Vertex AI Endpoints)

  • What it is: A high-level, fully managed service that abstracts away almost all infrastructure management. You simply upload your model, and the platform handles deployment, scaling, and monitoring.
  • Pros:
    \
  • Lowest Operational Overhead: Google manages everything (Kubernetes, VMs, scaling logic, drivers, Load Balancing).
  • Fastest Time-to-Deployment: Simplest way to get an LLM endpoint running.
  • Built-in MLOps Integration: Seamlessly integrates with model registries, monitoring, and data drift detection.
  • Simplified Cost Management: Often a simpler pricing model, though potentially less granular control.
  • High Availability & Reliability: Built-in redundancy and Google's operational expertise.
    \
  • Cons:
    Less Control & Customization: Limited ability to fine-tune underlying infrastructure or serving logic.
  • Potential Vendor Lock-in: Tightly integrated with the cloud provider's ecosystem.
  • Cost (sometimes): While simpler, for very high-volume or specific optimized workloads, a highly tuned GKE setup could be more cost-efficient, but this requires significant expertise.
    \
  • Common Use Cases:
  • Teams prioritizing speed of deployment and minimal operational burden.
  • Rapid prototyping and experimentation.
  • Organizations without deep Kubernetes or MLOps expertise.
  • Standard LLM inference needs.

Handling Custom and Fine-Tuned Models (LoRA)

When you fine-tune an LLM, the resulting model (or adapter) is typically saved in the Hugging Face transformers format. This format includes the model's configuration, tokenizer files, and the actual weights (.safetensors or .bin files).
  • Saving Your Model: After fine-tuning (e.g., using peft with transformers), you'll use model.save_pretrained() and tokenizer.save_pretrained() to store your model files in a directory.
  • Supplying to vLLM / TGI:
    Hugging Face Hub (Recommended): The most common approach is to push your fine-tuned model (including LoRA adapters) to the Hugging Face Hub (public or private). You then configure vLLM/TGI to load the model by its Hugging Face ID. This keeps your Docker image small and leverages Hugging Face's infrastructure for model distribution. The model is downloaded at container startup.
  • Local in Docker Image: For smaller models or specific needs, you can copy the model files directly into your Docker image. This results in larger images but eliminates runtime downloads.
    LoRA Specifics:
  • Modern versions of vLLM and TGI offer direct LoRA adapter support. This means you don't necessarily need to "merge" the LoRA weights into the base model beforehand.
  • You can load a single base model and then dynamically load multiple LoRA adapters on top of it at runtime. This is highly memory efficient for serving many fine-tuned versions of the same base model.
Recommendation: For fine-tuned models, especially with LoRA, it's generally best to dynamically pull both the base model and the LoRA adapters from the Hugging Face Hub (or a similar model repository) at container startup. This keeps your Docker images lean and flexible, and allows you to leverage advanced features like multi-LoRA serving. You can use Persistent Volumes in Kubernetes to cache these downloads, mitigating cold start impacts.

Why Use Open-Source Base Models?

It is common to use an open-source base model for several compelling reasons:
  • Cost-Effectiveness: Training an LLM from scratch is astronomically expensive, requiring vast amounts of data, compute resources (GPUs/TPUs), and time. Using a pre-trained open-source model eliminates this prohibitive cost.
  • Accessibility: Open-source models (often available on the Hugging Face Hub) democratize access to powerful LLM capabilities, allowing individuals and smaller organizations to build AI applications without massive budgets.
  • Community Support & Ecosystem: Open-source models benefit from large communities of developers, researchers, and users. This leads to:
    Extensive documentation and tutorials.
  • Robust tools and libraries (like Hugging Face transformers, peft, vLLM, TGI) built around them.
  • Faster bug fixes and continuous improvements.
  • Availability of fine-tuned versions and LoRA adapters.
  • Transparency & Controllability: With open-source models, you can inspect the model's architecture, understand its training data (to some extent), and have more control over its behavior. This is crucial for addressing biases, ensuring safety, and meeting regulatory requirements.
  • Flexibility for Fine-tuning: Open-source models are designed to be easily fine-tuned on custom datasets using techniques like LoRA, allowing you to adapt them to your specific domain or task without retraining the entire model.
  • Reduced Vendor Lock-in: Relying on open-source models reduces dependency on a single commercial API provider, offering more flexibility in deployment and future model choices.

Widespread Open-Source Base Model Families

Several key players offer widely adopted open-source LLM families, each with different sizes and characteristics, but often sharing a common tokenizer across the family.
  • Meta's Llama Family:
    • Overview: A highly popular family of LLMs known for strong performance and a permissive license for commercial use.
    • Tokenizer: Uses a SentencePiece tokenizer (often with a vocabulary size of 128K for Llama 3).
    • Common Models & Parameters:
      Llama 2: 7B, 13B, 70B parameters.
    • Llama 3: 8B, 70B parameters (with larger versions planned). Llama 3 models also feature Grouped-Query Attention (GQA) for improved inference scalability.
    • Code Llama: Specialized versions for code generation (e.g., 7B, 13B, 34B parameters).
  • Google's Gemma Family:
    • Overview: A family of lightweight, open models built from the same research and technology used to create the Gemini models, designed for responsible AI development.
    • Tokenizer: Uses a SentencePiece tokenizer (often with a vocabulary size of around 256K for Gemma 2 and 262K for Gemma 3).
    • Common Models & Parameters:
      Gemma 2: 2B, 9B, 27B parameters.
    • Gemma 3: 1B (text-only), 4B, 12B, 27B parameters (with 4B, 12B, 27B supporting multimodality).
    • CodeGemma: Code-specific variants (e.g., 2B, 7B parameters).
    • PaliGemma: Multimodal models (text and image) (e.g., 3B, 10B, 28B parameters).
  • Mistral AI's Models:
    • Overview: Known for creating powerful yet efficient LLMs, often excelling in performance for their size.
    • Tokenizer: Typically uses a byte-fallback BPE tokenizer (e.g., with a vocabulary size of 32K or 128K).
    • Common Models & Parameters:
    • Mistral 7B: 7.3B parameters.
    • Mixtral 8x7B (MoE): 46.7B total parameters (with 12.9B active parameters), utilizing a Mixture-of-Experts architecture.
    • Codestral: Code-specific models (e.g., 22B parameters).

Train with One Framework, Infer with Another

This is a powerful concept in MLOps and is very common, especially for LLMs.
  • The Principle: You can train your LLM (or fine-tune it) using one deep learning framework (e.g., PyTorch or TensorFlow) and then deploy it for inference using a different, specialized inference engine or runtime (e.g., TensorRT-LLM, ONNX Runtime, or even vLLM/TGI).
  • Why it's Done:
    • Training vs. Inference Optimization: Training frameworks (like PyTorch and TensorFlow) are optimized for flexibility, ease of experimentation, and efficient gradient computation.
    • Inference engines, on the other hand, are optimized for speed, memory efficiency, and low latency on specific hardware during prediction.
  • Hardware Specialization: You might train on TPUs (with TensorFlow or PyTorch), but want to infer on NVIDIA GPUs (where TensorRT-LLM excels) or even CPUs/edge devices (ONNX Runtime, MediaPipe with LiteRT).
  • Portability: Converting a model to an intermediate format (like ONNX) allows it to run on various hardware and software stacks without being tied to the original training framework.
  • Cost Efficiency: Using a highly optimized inference engine can drastically reduce the cost per inference by maximizing hardware utilization.
  • How it Works (General Steps):
    1. Train/Fine-tune: Develop and train your LLM in your preferred framework (e.g., PyTorch with Hugging Face transformers).
    2. Save Model: Save the trained model weights and configuration in a standard format (e.g., Hugging Face transformers format, PyTorch .pth checkpoint, TensorFlow SavedModel).
    3. Conversion/Optimization (Optional but Recommended):
    • For TensorRT-LLM: You would typically convert the Hugging Face transformers model into a TensorRT engine using the TensorRT-LLM build tools.
    • For ONNX Runtime: You would export the model from PyTorch or TensorFlow to the ONNX format, then potentially optimize the ONNX graph.
    • For vLLM/TGI: These engines often directly consume the Hugging Face transformers format, but they perform their own internal optimizations (like PagedAttention, FlashAttention) that are equivalent to this "conversion" step for inference.
    • For MediaPipe/LiteRT: Models are converted to a .task file format, often based on TensorFlow Lite.
    • Deploy: Deploy the optimized model using the chosen inference engine on your target hardware.
This separation allows developers to leverage the strengths of different tools at each stage of the MLOps lifecycle, leading to more efficient and flexible LLM deployments.

Conclusion

The choice of architecture for LLM inference deployment boils down to a trade-off between control and flexibility versus operational simplicity and speed of deployment.
  • For maximum performance, cost optimization, and deep customization, Managed Kubernetes (GKE) with specialized serving engines like vLLM or TGI offers a powerful solution, provided you have the necessary Kubernetes expertise.
  • For rapid deployment, minimal operational overhead, and integrated MLOps features, Fully Managed ML Endpoints (Vertex AI Endpoints) are an excellent choice.
Regardless of your platform, leveraging KV Cache and continuous batching (provided by vLLM/TGI/TensorRT-LLM), along with techniques like quantization, is crucial for efficient LLM inference at scale, ensuring your expensive GPU resources are utilized to their fullest potential.
