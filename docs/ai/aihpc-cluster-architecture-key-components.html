AI/HPC Cluster Architecture & Key Components

Source: AIHPC Cluster Architecture & Key Components.html

Links

  • https://chatgpt.com/c/69f9b2a2-6ea8-8391-ac46-06c81b30012b

Glossary

AI Training: The process of creating or improving a model by updating its weights using data.
Inference: Using a trained model to produce predictions, completions, classifications, embeddings, or other outputs.
Cold Start: The delay that happens when a model service needs to initialize before it can respond quickly. It can happen because the model weights need to be loaded into GPU memory, the container or VM is starting, caches are empty, dependencies are warming up, or autoscaling just created a new worker. Cold starts are common in inference systems when traffic is bursty or replicas scale down when idle.
Time to First Token, TTFT: The time between a user request arriving and the model producing the first output token. TTFT matters for chat and streaming inference because users feel it as initial responsiveness. High TTFT can come from queueing, routing, cold starts, long prompts, model prefill work, GPU memory pressure, overloaded workers, or network latency.
GPU: Graphics Processing Unit. A processor optimized for parallel computation, heavily used in AI.
VRAM: Video RAM, meaning memory attached to a GPU. In AI workloads, GPU memory stores model weights, activations, batch data, temporary tensors, and KV cache. Running out of VRAM often causes CUDA out-of-memory errors.
HBM: High Bandwidth Memory. A very fast memory technology used in data-center GPUs. HBM matters because AI workloads need huge memory bandwidth to feed the GPU efficiently.
KV Cache: Key-value cache used during transformer inference. It stores attention state from previous tokens so the model does not recompute everything from scratch for every new token. It speeds up generation but consumes GPU memory, especially with long context windows or high concurrency.
LoRA: Low-Rank Adaptation. A parameter-efficient fine-tuning method that trains small adapter weights instead of updating the full model. It reduces compute and memory requirements compared with full fine-tuning.
QLoRA: Quantized LoRA. A memory-efficient fine-tuning method that combines LoRA with quantization, often allowing large models to be fine-tuned on much smaller GPU memory budgets.
CUDA: NVIDIA’s GPU programming and runtime platform.
NCCL (nickel): NVIDIA Collective Communications Library. Used for efficient multi-GPU and multi-node communication.
RDMA: Remote Direct Memory Access. Allows one machine to access memory on another machine with low CPU overhead.
GPUDirect RDMA: NVIDIA technology that allows network or storage devices to exchange data more directly with GPU memory.
InfiniBand: High-performance network fabric common in HPC and AI clusters.
RoCE (ROH-see): RDMA over Converged Ethernet. Enables RDMA-style communication over Ethernet.
NVLink: NVIDIA high-speed GPU-to-GPU interconnect.
NVSwitch: NVIDIA switching fabric for connecting many GPUs with high bandwidth.
MIG (mig, like “fig”): Multi-Instance GPU. NVIDIA technology for partitioning supported GPUs into isolated GPU instances.
vGPU: Virtual GPU. NVIDIA software stack for exposing GPU capabilities to virtual machines.
GPU Passthrough: Assigning a whole physical GPU directly to a VM.
Hypervisor: The virtualization layer that runs virtual machines on a physical server.
IOMMU: Input-Output Memory Management Unit. A hardware feature that helps isolate and map device memory access. In this doc, it matters mainly for GPU passthrough, because assigning a physical GPU directly to a VM usually depends on IOMMU support.
SR-IOV (S-R-I-O-V): Single Root I/O Virtualization. A hardware virtualization mechanism for exposing multiple virtual functions from one PCIe device.
Slurm (slurm, rhymes with “worm”): A workload manager and scheduler used in HPC and AI training clusters.
Kubernetes: A container orchestration system used to run and manage workloads across clusters.
Object Storage: Bucket-based storage for objects, commonly used for datasets, checkpoints, logs, and artifacts.
Block Storage: Disk-like storage attached to a machine or VM.
File Storage: Shared filesystem storage accessible through paths such as /mnt/shared.
Lustre (LUS-ter): A high-performance parallel file system used in HPC. In this doc, Lustre is relevant as a shared storage option for large datasets, checkpoints, and multi-node workloads that need high throughput.
BeeGFS (bee-G-F-S): A parallel file system used in HPC and AI environments. In this doc, BeeGFS is relevant as another shared high-performance filesystem option for datasets, checkpoints, and multi-node jobs.
NVMe: High-speed SSD storage protocol.
NVMe-oF (N-V-M-E over fabrics): NVMe over Fabrics. NVMe-style storage accessed over a network fabric.
Checkpoint: Saved training state that allows a job to resume after failure.
ECC Errors: Error Correcting Code memory errors. ECC errors can indicate GPU memory or system memory reliability problems. Repeated ECC errors can point to failing hardware and may justify draining or replacing a node.
XID Errors: NVIDIA driver-reported GPU error codes. XID errors can indicate GPU driver, hardware, PCIe, memory, or workload-triggered GPU faults. Repeated XID errors on the same node are a strong signal for node-level investigation.
Noisy Neighbor: A workload that negatively affects another workload by consuming shared resources.
Blast Radius: The scope of impact from a failure: one job, one node, one rack, one cluster, one region, or all users.
RCA: Root Cause Analysis. A post-incident explanation of what happened, impact, timeline, root cause, resolution, and prevention.

Overview: What an HPC / AI Cluster Is

High-performance computing, or HPC, is infrastructure designed to run computationally intensive workloads across many machines as one coordinated system.
Modern AI infrastructure is a specialized form of HPC. Instead of only running scientific simulations or numerical workloads, it runs large-scale model training, fine-tuning, inference, data processing, and research workloads.
The important mental model:
An AI/HPC cluster behaves like one large machine.
Performance depends on how well compute, GPUs, networking, storage, scheduling, and operations work together.
A simplified stack:
Users / ML teams / researchers
↓
Access layer: SSH, APIs, notebooks, portals, CLI
↓
Schedulers and orchestrators: Slurm, Kubernetes, Ray, workflow systems
↓
Compute layer: CPU nodes, GPU nodes, NVIDIA accelerators
↓
GPU software layer: drivers, CUDA, NCCL, containers, ML frameworks
↓
GPU sharing layer: passthrough, vGPU, MIG, time-slicing
↓
Networking: NVLink, NVSwitch, InfiniBand, RoCE, Ethernet, DPUs
↓
Storage: object, block, file, NVMe, distributed storage
↓
Operations: metrics, logs, alerts, health checks, burn-in, RCA
↓
Data center layer: power, cooling, racks, cabling, maintenance
The expensive component is usually the GPU, but GPU performance depends on everything around it. A powerful GPU is wasted if it waits on slow storage, congested networking, bad placement, insufficient CPU preprocessing, or broken scheduling.

Why AI Clusters Are Different From Normal Cloud Clusters

Traditional cloud applications are usually built around web services, databases, queues, and APIs. AI/HPC workloads are different.
They often need:
  • Many GPUs allocated at once.
  • Very fast GPU-to-GPU communication.
  • High-throughput storage for datasets and checkpoints.
  • Long-running jobs that may run for hours, days, or weeks.
  • Strong observability because failures are expensive.
  • Careful scheduling so workloads land on the right nodes.
  • Isolation between users or tenants.
  • Fast failure detection and node remediation.
The practical takeaway:
In AI infrastructure, compute, network, and storage are not separate topics. They are one performance system.

Workload Types

Before designing or troubleshooting an HPC/AI system, understand the workload. Different workloads stress different parts of the stack.

AI Training

Training creates or improves a model.
Examples:
  • Pretraining a large language model.
  • Fine-tuning an existing model on domain data.
  • Training a vision model.
  • Running reinforcement learning workloads.
Training usually needs:
  • Many GPUs.
  • Fast multi-node networking.
  • Large datasets.
  • Checkpointing.
  • Slurm or Kubernetes scheduling.
  • Long job runtimes.
  • Careful fault tolerance.
Common failure modes:
  • Job hangs during distributed communication.
  • One bad node slows the entire job.
  • Checkpoint writes are too slow.
  • GPU utilization is low because data loading is slow.
  • Job fails after hours due to node, network, or storage issues.

Fine-Tuning

Fine-tuning modifies an existing model for a narrower task or dataset.
It is usually smaller than full training but still sensitive to:
  • GPU memory.
  • Dataset loading.
  • Container dependencies.
  • Checkpointing.
  • Experiment reproducibility.
Typical use cases:
  • Adapting a general model to legal, medical, financial, or company-specific data.
  • Instruction tuning.
  • LoRA or QLoRA style parameter-efficient training.

Inference

Inference uses a trained model to serve predictions or responses.
Examples:
  • Chat completion API.
  • Embedding generation.
  • Image generation.
  • Classification endpoint.
  • Retrieval-augmented generation service.
Inference usually cares about:
  • Latency
  • Throughput
  • Time to first token.
  • Total generation time.
  • GPU memory pressure.
  • Request batching.
  • Autoscaling.
  • Routing to healthy workers.
  • Cost per token
  • Time to first token: especially important for chat-style streaming. It measures how long the user waits before the first visible output appears. A request can have a high time to first token because it is queued, routed to an overloaded worker, waiting for a cold model replica to start, processing a very long prompt, or doing a large prefill step before generation begins
  • Cold start: an inference startup delay. It usually happens when the system needs to start a container or VM, load model weights into GPU memory, initialize the model server, build empty caches, or create a new autoscaled worker. Cold starts are more likely when traffic is bursty, when replicas scale down when idle, or when the model is very large.
Common failure modes:
  • Latency spike
  • High time to first token
  • Cold start too slow
  • Model worker OOM
  • Bad batching behavior
  • One unhealthy worker still receiving traffic
  • Long prompts consuming too much KV cache

Scientific HPC / Simulation

Traditional HPC workloads include:
  • Weather simulation.
  • Molecular dynamics.
  • Computational fluid dynamics.
  • Physics simulation.
  • Genomics.
  • Financial risk simulation.
These often use:
  • MPI.
  • Slurm.
  • High-speed interconnect.
  • Shared filesystems.
  • Large CPU or GPU clusters.

Batch Processing

Batch workloads run large numbers of jobs or data-processing tasks.
Examples:
  • Dataset preprocessing.
  • Evaluation jobs.
  • Rendering jobs.
  • Offline model scoring.
  • ETL pipelines.
Key concerns:
  • Queueing.
  • Retry behavior.
  • Throughput.
  • Cost efficiency.
  • Storage access.

Interactive Research

Interactive environments include:
  • Jupyter notebooks
  • SSH sessions
  • Development containers
  • Small experiments
  • Debug runs
These often do not need full GPUs all the time, so they are good candidates for GPU sharing, MIG, or time-slicing, depending on isolation and performance needs.

Compute Layer: CPUs, GPUs, Nodes, and Racks

The compute layer is where work actually runs.

CPU Role

Even GPU-heavy workloads still need CPUs.
CPUs handle:
  • Operating system work.
  • Process scheduling.
  • Data loading
  • Tokenization
  • Compression and decompression.
  • Network stack work
  • Storage interaction
  • Control-plane agents.
  • Preprocessing.
A GPU job can be CPU-bound if the CPU cannot prepare data fast enough.
Example:
Dataset → CPU dataloader/tokenizer → GPU

If CPU preprocessing is slow, the GPU waits.

GPU Role

GPUs accelerate highly parallel math. AI models rely heavily on matrix operations, which GPUs handle efficiently.
GPUs are used for:
  • Model training.
  • Fine-tuning.
  • Inference.
  • Embeddings.
  • Scientific simulation.
  • Rendering.
  • Vectorized data processing.
Important GPU considerations:
  • Compute performance.
  • GPU memory capacity.
  • GPU memory bandwidth.
  • Interconnect bandwidth.
  • Power and cooling.
  • Driver and framework support.
  • Availability and cost.

GPU Memory

GPU memory, often called VRAM or HBM in data-center GPUs, stores:
  • Model weights.
  • Activations.
  • Optimizer state.
  • Batch data.
  • KV cache during inference.
  • Temporary tensors.
Common memory-related problems:
  • CUDA out-of-memory errors.
  • Model cannot load.
  • Long-context inference fails.
  • Batch size is too high
  • Inference concurrency is too high
  • Training optimizer state is too large

GPU Utilization

GPU utilization shows whether the GPU is actually doing work.
Low GPU utilization often means the GPU is waiting on something else:
  • Slow storage.
  • Slow dataloader.
  • CPU bottleneck.
  • Network synchronization.
  • Bad batching.
  • Small batch size.
  • One slow node.
  • Poor topology placement.
  • Application-level inefficiency.
Useful mental model:
Customer says: “The GPU is slow.”
Better question: “Is the GPU busy, or is it waiting?”

Node Design

A compute node usually includes:
  • CPUs.
  • GPUs.
  • RAM.
  • Local NVMe.
  • NICs.
  • Power and cooling components.
  • Baseboard management controller.
  • Host operating system.
  • Drivers and agents.
Design questions:
  • How many GPUs per node?
  • Which GPU type?
  • Enough CPU per GPU?
  • Enough RAM for preprocessing and data loading?
  • Enough local NVMe for scratch/cache?
  • Which network adapters?
  • Is the node optimized for training, inference, or mixed use?

NVIDIA DGX and HGX Systems

DGX and HGX are useful reference points for understanding NVIDIA-based AI infrastructure.
DGX is NVIDIA’s integrated AI system line. A DGX system is a complete NVIDIA-branded platform that combines NVIDIA GPUs, CPU/memory, NVLink/NVSwitch connectivity, networking, storage options, power/cooling design, and validated software assumptions.
HGX is NVIDIA’s GPU server platform or reference design used by OEMs, cloud providers, and system builders. HGX is not usually the customer-facing branded box in the same way DGX is. It is more like the GPU baseboard/platform design that other vendors build systems around.
The practical distinction:

Why they matter in this doc:
  • High-end AI servers are not just normal servers with GPUs added.
  • GPU placement, NVLink/NVSwitch layout, PCIe topology, NIC placement, power, cooling, and validated software all affect performance.
  • DGX/HGX-style systems explain why node design and rack design are part of AI performance engineering.

Rack and Data Center Design

At scale, racks and data centers become part of the system design.
Considerations:
  • Power density.
  • Cooling method.
  • Cabling complexity.
  • Network topology.
  • Failure domains.
  • Serviceability.
  • Spare capacity.
  • Maintenance procedures.
High-end NVIDIA-based systems such as DGX, HGX, and GB200-class platforms require careful power, cooling, cabling, and networking planning. The hardware is not just “a server with GPUs.” It is a dense, specialized AI compute unit.

NVIDIA Driver

The driver is the low-level software that lets the OS and applications use the GPU.
Common issues:
  • Driver not installed.
  • Driver version incompatible with CUDA or framework.
  • GPU not visible.
  • Driver crash.
  • NVIDIA XID errors.
  • Kernel module issue.
Useful checks:
nvidia-smi
journalctl -k
dmesg
lsmod
lspci

CUDA

CUDA is NVIDIA’s main GPU programming and runtime platform.
Most AI frameworks depend on CUDA for NVIDIA GPU acceleration.
Key point:
Driver, CUDA version, framework version, and container image must be compatible.
A common failure pattern:
Container uses CUDA version X
Host driver supports CUDA version Y
Framework expects CUDA version Z
↓
GPU workload fails or behaves unpredictably

NCCL

NCCL, usually pronounced “nickel,” is NVIDIA’s communication library for multi-GPU and multi-node workloads.
It is central to distributed training.
NCCL helps GPUs perform collective operations such as:
  • All-reduce.
  • Broadcast.
  • Reduce-scatter.
  • All-gather.
Common NCCL-related symptoms:
  • Distributed training hangs.
  • NCCL timeout.
  • Poor multi-node scaling.
  • Wrong network interface selected.
  • One node cannot communicate with others.
  • RDMA or InfiniBand issue.
Troubleshooting usually involves:
  • NCCL logs.
  • Network interface configuration.
  • RDMA/InfiniBand health.
  • Node placement.
  • GPU and driver health.
  • Firewall/routing issues.

NVIDIA Container Runtime

Containers do not automatically get GPU access.
The NVIDIA container stack bridges the host GPU into container namespaces.
Simplified flow:
Host sees GPU through NVIDIA driver
↓
NVIDIA container runtime exposes GPU devices and libraries
↓
Containerized workload sees GPU
↓
Framework uses CUDA inside container
Common issues:
  • Container does not request GPU.
  • Runtime not configured.
  • CUDA libraries missing in image.
  • Driver/runtime mismatch.
  • GPU devices not mounted into container.

NVIDIA GPU Operator

In Kubernetes environments, the GPU Operator helps manage the GPU software stack.
It can manage components such as:
  • Driver deployment.
  • Container runtime integration.
  • Device plugin.
  • Monitoring components.
  • MIG configuration support.
Useful idea:
Kubernetes does not magically understand GPUs. The NVIDIA stack exposes GPUs to Kubernetes in a schedulable way.

Triton Inference Server

NVIDIA Triton Inference Server is used to serve AI models in production.
It supports multiple frameworks and model formats and is commonly used for:
  • Model serving.
  • Dynamic batching.
  • GPU inference.
  • Multi-model serving.
  • Production inference APIs.
Not every inference stack uses Triton. Other common choices include vLLM, Hugging Face TGI, TensorRT-LLM, and custom model servers.

GPU Virtualization, Sharing, and Hypervisors

GPU virtualization and sharing are about exposing one physical GPU to one or more workloads.
The central trade-off:
Utilization and flexibility
vs.
Performance, isolation, and simplicity

Why GPU Virtualization Exists

GPUs are expensive. Many workloads do not need a full GPU all the time.
GPU sharing can help with:
  • Higher utilization.
  • Lower cost per workload.
  • Multi-tenant environments.
  • Interactive notebooks.
  • Development and testing.
  • Small inference workloads.
  • VDI and virtual workstations.
  • Better resource packing.
But it can introduce:
  • Performance overhead.
  • Licensing constraints.
  • Operational complexity.
  • Noisy-neighbor issues.
  • Harder debugging.
  • Weaker isolation, depending on method.
Practical rule:
Large distributed training usually prefers full GPUs or full nodes.
Inference, notebooks, dev/test, and VDI may benefit from GPU sharing.

Hypervisor

A hypervisor is the virtualization layer that runs virtual machines on a physical server.
Examples:
  • VMware ESXi.
  • KVM / QEMU.
  • Hyper-V.
  • Xen.
  • Proxmox, built on KVM.
In normal virtualization, the hypervisor virtualizes CPU, memory, disk, and networking.
With GPUs, the problem is harder because GPUs are high-performance PCIe devices that often need direct hardware access.
Key question:
Does the VM get the whole GPU, a virtual GPU, or no direct GPU access?

GPU Passthrough

GPU passthrough assigns an entire physical GPU to one VM.
Simplified path:
Physical server
↓
Hypervisor
↓
VM gets direct access to whole GPU
↓
Guest OS installs NVIDIA driver
↓
Workload uses GPU almost like bare metal

Pros:
  • Near bare-metal performance.
  • Simple performance model.
  • Strong VM-level ownership.
  • Good for production workloads needing full GPU.
Cons:
  • No sharing of that GPU.
  • Lower utilization if workload is small.
  • Requires platform/IOMMU support. IOMMU is important because it lets the hypervisor safely map and isolate direct device access when assigning a physical GPU to a VM.
  • Less flexible for multi-tenant packing.
Best fit:
  • Performance-sensitive VMs.
  • Dedicated customer environments.
  • Workloads that need predictable full-GPU performance.

NVIDIA vGPU

NVIDIA vGPU shares GPU access across VMs using NVIDIA’s vGPU software stack.
Simplified path:
Physical GPU
↓
NVIDIA vGPU manager on hypervisor
↓
Multiple VMs receive virtual GPU profiles
↓
Each VM installs guest vGPU driver

Use cases:
  • VDI.
  • Virtual workstations.
  • CAD/rendering.
  • Shared GPU VM environments.
  • Smaller AI development workloads.
Considerations:
  • Requires supported hardware.
  • Requires supported hypervisor.
  • Requires matching host and guest drivers.
  • Often involves NVIDIA licensing.
  • Adds operational complexity.
Good rule:
vGPU is useful when the platform is VM-based and needs GPU sharing, but it is not the simplest choice for raw training performance.

MIG

MIG means Multi-Instance GPU.
MIG partitions a supported NVIDIA GPU into multiple isolated GPU instances.
Simplified model:
One physical GPU
↓
Split into smaller hardware-backed GPU instances
↓
Each workload gets a slice of compute and memory
Best for:
  • Multi-tenant inference.
  • Notebooks.
  • Development environments.
  • Smaller workloads that need predictable isolation.
  • Cases where a full GPU would be wasteful.
Pros:
  • Hardware-backed partitioning.
  • Better isolation than time-slicing.
  • Predictable memory allocation.
  • Useful for GPU utilization.
Cons:
  • Only supported on certain NVIDIA GPUs.
  • Partition sizes are constrained.
  • Reconfiguring MIG can require operational coordination.
  • Not ideal for workloads needing full GPU resources.
Good rule:
MIG is the cleanest NVIDIA model for hardware-backed fractional GPU isolation.

Time-Slicing

Time-slicing means multiple workloads share one GPU by taking turns.
Difference from MIG:
MIG: GPU is partitioned into isolated hardware instances.
Time-slicing: workloads share the same GPU over time.
Best for:
  • Dev/test.
  • Low-duty-cycle notebooks.
  • Small experiments.
  • Internal platforms where utilization matters more than strict isolation.
Risks:
  • Weak performance isolation.
  • Noisy-neighbor behavior.
  • Unpredictable latency.
  • Not ideal for strict production inference.
  • Not ideal for large training jobs.
Good rule:
Time-slicing improves utilization but is the weakest isolation model.

SR-IOV

SR-IOV means Single Root I/O Virtualization.
A physical PCIe device exposes multiple lightweight virtual functions to VMs or workloads.
It is common in high-performance NIC virtualization.
For GPUs, be careful with wording. Support depends heavily on vendor, GPU generation, driver stack, and hypervisor support.
Useful framing:
SR-IOV is a hardware virtualization mechanism. In GPU discussions, it belongs to the broader topic of hardware-assisted device sharing, but exact behavior depends on the platform.

Kubernetes Fractional GPU Allocation

In Kubernetes, GPUs are usually exposed as resources such as:
nvidia.com/gpu: 1
With sharing or partitioning, platforms may expose:
  • Full GPUs.
  • MIG profiles.
  • Time-sliced GPU replicas.
  • Custom fractional GPU resources.
Important point:
Kubernetes does not split GPUs by itself. It depends on the NVIDIA device plugin, GPU Operator, MIG configuration, time-slicing configuration, and scheduler policy.
Design considerations:
  • Resource isolation.
  • Scheduling correctness.
  • Metrics per slice.
  • Tenant quotas.
  • Latency predictability.
  • Node labels.
  • MIG profile selection.
  • Operational visibility.

Discussion Prompts

Useful questions for technical conversations:
  1. When should we use passthrough, vGPU, MIG, or time-slicing?
  2. How do we balance utilization against isolation?
  3. What is the performance tax of virtualization for inference?

Networking and Interconnect Technologies

Networking is one of the most important parts of AI/HPC infrastructure.
For normal web systems, networking often means service reachability: can service A reach service B, is DNS working, is the firewall open, and is latency acceptable.
For AI/HPC, networking is more intense. Large training jobs may use hundreds or thousands of GPUs that need to exchange data constantly. If the network is slow, unstable, congested, or poorly placed, expensive GPUs sit idle.
Core idea:
In distributed AI training, the network is part of the computer.

Why Networking Matters in AI/HPC

Distributed training usually works like this:
Each GPU computes part of the work
↓
GPUs exchange gradients / activations / synchronization data
↓
All workers synchronize
↓
The next training step starts
If one node, NIC, link, or network path is slow, the whole job can slow down.
The customer-visible symptom may be:
“The GPUs are slow.”
But the real issue may be:

The GPUs are waiting on network communication.
Networking also matters for:
  • Storage access.
  • Checkpoint writes.
  • Model loading.
  • Multi-node inference.
  • Cluster management.
  • Tenant isolation.
  • API and control-plane reliability.

PCIe

PCIe, or Peripheral Component Interconnect Express, is the standard high-speed bus used inside servers.
It connects devices such as:
  • GPUs.
  • Network cards.
  • NVMe drives.
  • Other accelerators.
PCIe is the server’s internal device highway.
Use cases:
  • Connecting GPUs to CPUs.
  • Connecting NICs to the host.
  • Connecting local NVMe storage.
  • Enabling GPU passthrough to VMs.
Design considerations:
  • PCIe generation and lane count affect bandwidth.
  • Device placement matters.
  • Oversubscribed PCIe paths can bottleneck data movement.
  • GPUs, NICs, and NVMe devices all compete for server-level I/O paths.
Where it fits:
Inside one physical server.

NVLink

NVLink is NVIDIA’s high-speed GPU-to-GPU interconnect.
NVLink lets NVIDIA GPUs talk to each other faster than they could through normal PCIe paths.
Use cases:
  • Multi-GPU training inside one server.
  • Large models that need multiple GPUs.
  • Fast GPU-to-GPU tensor movement.
  • Reducing bottlenecks inside a node.
Why it matters:
If multiple GPUs inside one machine need to communicate heavily, PCIe alone may not be enough. NVLink provides a faster path between GPUs.
Common comparison:
PCIe
NVLink
General-purpose device bus
NVIDIA GPU-to-GPU interconnect
Connects many device types
Optimized for GPU communication
Standard server technology
NVIDIA-specific ecosystem
Where it fits:
Inside a server or tightly coupled NVIDIA GPU system.

NVSwitch

NVSwitch is a switch fabric for connecting many NVIDIA GPUs together.
NVSwitch lets many GPUs communicate with each other through a high-bandwidth switching fabric.
Use cases:
  • DGX/HGX-style systems.
  • Large multi-GPU servers.
  • Rack-scale GPU systems.
  • Workloads needing high GPU-to-GPU bandwidth.
Why it matters:
With only point-to-point links, connecting many GPUs efficiently gets complicated. NVSwitch helps create a high-bandwidth fabric between many GPUs.
Where it fits:
Inside high-end NVIDIA GPU systems, and in some rack-scale GPU architectures.

Ethernet

Ethernet is the standard networking technology used in most data centers.
Ethernet is the default network language of modern data centers.
Use cases:
  • General server networking.
  • Cloud VPC networking.
  • API traffic.
  • Storage traffic.
  • Management traffic.
  • Some AI/HPC fabrics when tuned for performance.
Pros:
  • Widely supported.
  • Familiar operational model.
  • Flexible ecosystem.
  • Works well for general cloud networking.
Cons for AI/HPC:
  • Traditional Ethernet was not designed specifically for tightly coupled HPC communication.
  • Packet loss, congestion, and latency can hurt distributed training.
  • RDMA over Ethernet requires careful design and tuning.
Where it fits:
Between servers, across data centers, and for general cloud networking.

InfiniBand

InfiniBand is a high-performance network fabric commonly used in HPC and AI clusters.
InfiniBand is a specialized low-latency, high-bandwidth network for tightly coupled compute clusters.
Use cases:
  • Large-scale AI training.
  • HPC simulation.
  • Multi-node GPU workloads.
  • Low-latency cluster communication.
  • RDMA-heavy workloads.
Why it matters:
Distributed training depends on frequent communication between nodes. InfiniBand is designed for this kind of low-latency, high-throughput traffic.
Pros:
  • Very low latency.
  • High bandwidth.
  • Strong HPC ecosystem.
  • Common in supercomputers and AI training clusters.
  • Well-suited for RDMA.
Cons:
  • Specialized operational knowledge.
  • Dedicated fabric design.
  • Cabling and topology complexity.
  • Less general-purpose than Ethernet.
Common symptoms when InfiniBand has problems:
  • NCCL timeout.
  • Multi-node training hangs.
  • Poor distributed scaling.
  • One node much slower than others.
  • High error counters.
  • Intermittent training failures.
Where it fits:
Between GPU servers in high-performance AI/HPC clusters.

RDMA

RDMA means Remote Direct Memory Access.
RDMA lets one machine access memory on another machine with very low CPU involvement.
Normal network path, simplified:
Application
↓
Operating system
↓
CPU copies data
↓
Network stack
↓
Remote operating system
↓
Remote application
RDMA-style path, simplified:
Memory on machine A
↓
Network adapter
↓
Memory on machine B
Use cases:
  • Distributed training.
  • HPC applications.
  • Low-latency storage.
  • High-throughput node-to-node communication.
  • Networked storage fabrics.
Why it matters:
RDMA reduces CPU overhead and latency. This helps keep GPUs fed and synchronized.
RDMA is not a physical cable or fabric by itself. It is a capability that can run over technologies such as InfiniBand or RoCE.
Where it fits:
A low-level communication capability used by high-performance networking and storage systems.

RoCE

RoCE means RDMA over Converged Ethernet.
RoCE brings RDMA-style communication to Ethernet networks.
Use cases:
  • AI clusters built on Ethernet.
  • High-performance storage over Ethernet.
  • Data centers that prefer Ethernet operations.
  • Environments that want RDMA without InfiniBand.
Why it matters:
RoCE tries to combine two ideas:
Ethernet ecosystem and flexibility
+
RDMA performance model
Pros:
  • Uses Ethernet-based infrastructure.
  • Supports RDMA-style low-latency communication.
  • Can fit cloud/data-center operational models better than InfiniBand.
Cons:
  • Requires careful congestion control.
  • Sensitive to packet loss.
  • Needs strong network tuning.
  • Misconfiguration can cause severe performance problems.

Spectrum-X

Spectrum-X is NVIDIA’s Ethernet networking platform for AI workloads.
Spectrum-X is NVIDIA’s attempt to make Ethernet perform better for AI-scale networking.
It combines NVIDIA Ethernet switches and network adapters designed for AI traffic patterns.
Use cases:
  • Ethernet-based AI clusters.
  • RoCE-based GPU communication.
  • Large-scale AI training over Ethernet.
  • Data centers standardizing on Ethernet instead of InfiniBand.
Why it matters:
AI training traffic is different from normal web traffic. Spectrum-X is positioned around making Ethernet more predictable and performant for AI workloads.
Where it fits:
Between nodes in NVIDIA Ethernet-based AI clusters.

BlueField DPU

A DPU, or Data Processing Unit, is a programmable infrastructure processor.
NVIDIA BlueField DPUs can offload and accelerate tasks such as:
  • Networking.
  • Storage.
  • Security.
  • Isolation.
  • Packet processing.
  • Infrastructure services.
A BlueField DPU takes infrastructure work away from the host CPU.
Use cases:
  • Network offload.
  • Storage offload.
  • Security isolation.
  • Multi-tenant cloud infrastructure.
  • Infrastructure services close to the server.
  • Reducing host CPU overhead.
Why it matters:
In AI/HPC systems, the CPU should not waste too much time on infrastructure overhead. DPUs can move some of that work to dedicated hardware.
Where it fits:
At the server edge, between the host and the network/storage infrastructure.

GPUDirect RDMA

GPUDirect RDMA allows network or storage devices to exchange data more directly with GPU memory.
GPUDirect RDMA helps data move between NIC/storage devices and GPU memory with less CPU copying.
Simplified path:
Network adapter or storage device
↔
GPU memory

Use cases:
  • Distributed training.
  • High-throughput GPU communication.
  • GPU-aware storage access.
  • Reducing CPU copy overhead.
  • Low-latency data movement into GPU memory.
Why it matters:
If data must constantly move through CPU memory before reaching the GPU, the CPU and memory subsystem can become a bottleneck. GPUDirect RDMA helps reduce this overhead.
Where it fits:
Between GPUs and high-performance network/storage devices.

NCCL and Network-Aware GPU Communication

NCCL is NVIDIA’s collective communication library for GPUs.
NCCL is the software layer that helps GPUs communicate efficiently during distributed training.
It uses the available hardware paths, such as:
  • NVLink.
  • NVSwitch.
  • PCIe.
  • InfiniBand.
  • RoCE.
  • Ethernet, depending on configuration and environment.
Common NCCL operations are communication patterns used by GPUs during distributed workloads. You do not need to implement them to understand the support impact: when NCCL communication fails or slows down, distributed training can hang, timeout, or scale badly.
Operation
What it does
Why it matters
All-reduce
Combines values from all GPUs and sends the combined result back to every GPU
Common in distributed training to synchronize gradients
All-gather
Collects data from all GPUs and gives every GPU the full combined result
Useful when each GPU has only part of the data
Reduce-scatter
Combines data across GPUs, then splits the result across them
Helps reduce communication and memory pressure in distributed training
Broadcast
Sends data from one GPU or process to all others
Useful for sharing model weights, config, or synchronization data
Why it matters:
If NCCL chooses the wrong interface, or if the fabric underneath is unhealthy, distributed training may hang or perform badly.
Common symptoms:
  • NCCL timeout.
  • Training hangs at startup.
  • Training hangs during synchronization.
  • Poor multi-node scaling.
  • One node causes repeated failures.
Useful investigation areas:
  • NCCL logs.
  • Selected network interface.
  • Node placement.
  • RDMA/InfiniBand health.
  • Firewall/routing.
  • GPU and driver health.

Topology-Aware Placement

Topology means the physical and logical layout of nodes, GPUs, racks, and network links.
Some GPUs and nodes are closer to each other than others.
Good placement:
A job needs 64 GPUs
↓
Scheduler places them on nearby nodes with strong network connectivity
↓
Lower communication overhead
↓
Better training performance
Bad placement:
A job needs 64 GPUs
↓
Scheduler spreads them across weaker or congested paths
↓
Higher latency / lower bandwidth
↓
Lower GPU utilization
Use cases:
  • Large training jobs.
  • Multi-node inference.
  • HPC simulations.
  • Jobs sensitive to communication latency.
Design considerations:
  • Rack locality.
  • Switch locality.
  • InfiniBand pod/group locality.
  • Oversubscription.
  • Failure domains.
  • Multi-tenant fairness.

Common Failure Modes

Multi-Node Training Is Slow

Possible causes:
  • Poor topology placement.
  • Congested fabric.
  • Bad NIC or link.
  • Wrong NCCL interface.
  • RDMA/InfiniBand errors.
  • One slow node.
  • Storage bottleneck mistaken for network bottleneck.
First checks:
  • GPU utilization.
  • NCCL logs.
  • Per-node performance.
  • Network error counters.
  • RDMA/IB metrics.
  • Storage throughput.
  • Job placement.

Training Hangs

Possible causes:
  • One worker crashed.
  • NCCL timeout.
  • RDMA path issue.
  • Firewall/routing issue.
  • Bad interface selection.
  • Node/NIC health issue.
  • Driver/runtime mismatch.
First checks:
  • Logs from all workers.
  • Which node failed first.
  • NCCL timeout messages.
  • Node health.
  • Network interface selection.
  • Whether issue follows node or workload.

Inference Latency Spikes

Possible causes:
  • Worker overload.
  • Routing issue.
  • Network path issue.
  • GPU memory pressure.
  • Bad batching.
  • Storage/model loading delay.
  • Load balancer issue.
First checks:
  • Time to first token vs full response time.
  • Request size.
  • GPU utilization and memory.
  • Worker health.
  • Routing/load balancer logs.
  • Network metrics.

Storage Access Is Slow

Possible causes:
  • Network congestion.
  • Remote storage path issue.
  • Bad NIC/link.
  • Storage backend bottleneck.
  • Too many small files.
  • Checkpoint write saturation.
First checks:
  • Storage throughput and latency.
  • Network metrics.
  • Local vs remote storage comparison.
  • File count/access pattern.
  • Checkpoint timing.

Summary

In AI/HPC, networking is not just connectivity. It determines whether many GPUs can work efficiently as one system. NVLink and NVSwitch handle fast GPU communication inside NVIDIA systems. InfiniBand and RoCE handle high-speed communication between nodes. RDMA reduces CPU overhead for memory-to-memory communication. GPUDirect RDMA helps move data directly between GPU memory and network or storage devices. NCCL is the software layer that uses these paths for distributed training. Topology-aware placement makes sure jobs land where the network can support them.

Storage and Data Layer

AI/HPC workloads need fast and reliable access to data.
The storage layer handles:
  • Datasets.
  • Model weights.
  • Checkpoints.
  • Logs.
  • Artifacts.
  • Shared home directories.
  • Temporary scratch data.
  • Model serving assets.

Object Storage

Object storage stores data as objects in buckets.
Think:
s3://bucket/dataset/file.parquet
s3://bucket/checkpoints/step-10000.pt
Good for:
  • Large datasets.
  • Checkpoints.
  • Artifacts.
  • Logs.
  • Backups.
  • Model files.
Less ideal for:
  • Low-latency random writes.
  • POSIX filesystem behavior.
  • Workloads with many tiny file operations.

Block Storage

Block storage behaves like a disk attached to a machine.
Good for:
  • VM disks.
  • Databases.
  • Application volumes.
  • High-performance attached volumes.
Less ideal for:
  • Many nodes writing to the same volume.
  • Shared filesystem use without an additional file layer.

File Storage

File storage provides a shared filesystem path.
Examples:
/mnt/shared/datasets
/mnt/shared/checkpoints
/home/users
Protocols and systems may include:
  • NFS.
  • SMB.
  • Lustre.
  • BeeGFS.
  • Other distributed filesystems.
Good for:
  • Shared datasets.
  • Shared home directories.
  • HPC workflows.
  • Multi-node jobs expecting normal file paths.
Risks:
  • Metadata bottlenecks.
  • Too many small files.
  • Mount failures.
  • Shared filesystem contention.
  • Slow checkpoint writes.

Local NVMe

NVMe is high-speed SSD storage.
Local NVMe is useful for:
  • Scratch space.
  • Dataset cache.
  • Temporary files.
  • Fast local reads/writes.
  • Checkpoint staging.
Trade-off:
Local NVMe is fast but usually not the durable source of truth.

NVMe-oF

NVMe-oF means NVMe over Fabrics.
NVMe-style storage accessed over a network fabric.
It can provide high-performance networked storage, but network health becomes part of storage performance.

Distributed Storage

Distributed storage spreads data across multiple machines.
Why use it:
  • Scale capacity.
  • Increase throughput.
  • Improve durability.
  • Avoid one storage node becoming the bottleneck.
Complexity:
  • Replication.
  • Consistency.
  • Metadata performance.
  • Network dependency.
  • Failure handling.
  • Hot files or hot partitions.

Dataset and Checkpoint Considerations

AI training commonly follows this pattern:
Read dataset
↓
Preprocess/tokenize
↓
Feed GPUs
↓
Periodically write checkpoints
Storage-related performance problems:
  • Dataset reads are too slow.
  • Too many small files.
  • Metadata server is overloaded.
  • Checkpoints are too large.
  • Checkpoints are too frequent.
  • All workers write at once.
  • Object storage path or permissions are wrong.
  • Mount works on some nodes but not others.
Good design principle:
Storage must be sized for throughput and access pattern, not only for capacity.

Scheduling and Orchestration

Schedulers decide when and where workloads run.

Slurm

Slurm is a job scheduler widely used in HPC and AI training.
It thinks in terms of:
  • Jobs.
  • Queues.
  • Partitions.
  • Nodes.
  • GPU allocations.
  • Accounts.
  • Fair-share.
  • Job states.
Useful commands:
squeue
sinfo
sbatch
srun
scancel
sacct
Best for:
  • Large training jobs.
  • HPC simulation.
  • Batch workloads.
  • Multi-user compute clusters.
Common issues:
  • Job stuck pending.
  • Wrong partition.
  • Not enough GPUs.
  • Node drained/down.
  • Job dependency blocking execution.
  • Fair-share or priority issue.
  • Job fails immediately due to environment/script.

Kubernetes

Kubernetes orchestrates containers across nodes.
It thinks in terms of:
  • Pods.
  • Nodes.
  • Deployments.
  • Jobs.
  • Services.
  • Namespaces.
  • Node pools.
  • Resource requests.

  • Containerized services.
  • Inference platforms.
  • Internal ML platforms.
  • Managed clusters.

Acceptance Testing and Burn-In

Before new nodes enter production, they should be validated.
Typical checks:
  • Node reachable.
  • Correct GPU count and type.
  • GPU visible through driver.
  • CUDA works.
  • Stress test passes.
  • NCCL tests pass.
  • Network bandwidth and latency acceptable.
  • RDMA/InfiniBand health verified.
  • Storage mounts work.
  • Storage throughput acceptable.
  • Kubernetes or Slurm sees the node correctly.
  • Thermal and power behavior stable.
  • No obvious hardware errors.
Important principle:
At cluster scale, hardware failures are expected. The goal is fast detection, isolation, remediation, and prevention.

RCA

RCA means root cause analysis.
A good RCA includes:
  • Summary.
  • Impact.
  • Timeline.
  • Root cause.
  • Detection.
  • Mitigation.
  • Resolution.
  • Prevention.
  • Follow-up actions.
Bad RCA:
A GPU node failed.
Better RCA:
Training jobs failed because node X had repeated GPU XID errors. The node was not drained quickly enough, so new jobs continued landing there. We drained the node, moved workloads away, and added a follow-up to improve alerting and automatic remediation.

Checkpointing

Checkpointing saves progress so long-running jobs can resume after failure.
Design questions:
  • How often to checkpoint?
  • Where to write checkpoints?
  • How large are checkpoints?
  • Does only rank zero write, or do all workers write?
  • Can the job resume cleanly?
  • Does checkpointing pause training too much?
Trade-off:
Frequent checkpoints reduce lost work but increase storage load.
Infrequent checkpoints reduce overhead but increase recovery cost.

Blast Radius

Blast radius means how wide the impact is.
Examples:
  • One request.
  • One job.
  • One node.
  • One customer.
  • One rack.
  • One cluster.
  • One region.
  • Whole platform.
Reliability work should reduce blast radius where possible.

Network isolation may involve:
  • VPCs.
  • Subnets.
  • Firewall rules.
  • Security groups.
  • Network policies.
  • Tenant-specific routing.

Data Isolation

Data isolation includes:
  • Bucket permissions.
  • Filesystem permissions.
  • Storage credentials.
  • Encryption.
  • Tenant-specific volumes.
  • Audit trails.

GPU sharing introduces security and performance concerns.

Noisy Neighbor Problems

A noisy neighbor is one workload that hurts another workload’s performance.
Examples:
  • One time-sliced GPU workload consumes too much memory or time.
  • One tenant saturates shared storage.
  • One job congests the network fabric.
  • One user writes too many small files to a shared filesystem.
Design goal:
Isolation is not only about security. It also protects performance predictability.

Performance engineering is the process of identifying what limits workload speed or efficiency.

Training Performance

Important factors:
  • GPU utilization.
  • Batch size.
  • Data loading speed.
  • CPU preprocessing.
  • Storage throughput.
  • Network bandwidth/latency.
  • NCCL behavior.
  • Topology placement.
  • Checkpoint strategy.
  • One slow worker.
Common tuning areas:
  • Increase dataloader workers.
  • Improve dataset format.
  • Cache data locally.
  • Tune batch size.
  • Use mixed precision.
  • Improve checkpoint strategy.
  • Use topology-aware scheduling.
  • Investigate NCCL/network settings.

Inference Performance

Important factors:
  • Time to first token.
  • Total generation time.
  • Tokens per second.
  • Batch size.
  • Request concurrency.
  • Context length.
  • KV cache memory.
  • Routing.
  • Model worker health.
  • Cold start/model loading.
Time to first token and total generation time are different.
Time to first token:
How long before the model starts responding.

Total generation time:
How long until the full response is done.
A high time to first token often points to queueing, routing, cold start, long prompt prefill, overloaded workers, or network/request-path latency.
A high total generation time with normal time to first token can point to slow decoding, long requested output, GPU saturation, poor batching, or memory pressure.
Cold start happens when serving capacity is not already warm. The system may need to start a container, attach resources, load model weights from storage, initialize CUDA/framework state, allocate GPU memory, build caches, or register the worker behind a load balancer.
Common tuning areas:
  • Keep warm replicas.
  • Reduce model load time.
  • Improve autoscaling policy.
  • Dynamic batching.
  • Autoscaling.
  • Model quantization.
  • Better routing.
  • GPU memory management.
  • KV cache management.
  • Full GPU vs MIG vs time-slicing decision.

Practical Debugging Question

For almost any performance issue, ask:
Is the workload compute-bound, memory-bound, network-bound, storage-bound, scheduler-bound, or application-bound?

That question prevents guessing.

Troubleshooting Playbooks

Playbook: GPU Not Visible

Symptom:
Workload starts, but framework says no GPU is available.
Likely layers:
  • Container/runtime.
  • Kubernetes resource request.
  • NVIDIA driver.
  • Device plugin.
  • Node health.
  • Hardware issue.
First checks:
  • Did the workload request GPU resources?
  • Did it land on a GPU node?
  • Does nvidia-smi work on the host?
  • Is the GPU visible inside the container?
  • Are driver/CUDA/framework versions compatible?
  • Are there driver or kernel errors?
Possible mitigation:
  • Reschedule to a healthy node.
  • Fix resource request.
  • Fix container/runtime configuration.
  • Drain bad node.

Playbook: Low GPU Utilization

Symptom:
GPU utilization is low even though workload is running.
Likely layers:
  • Storage.
  • CPU preprocessing.
  • Dataloader.
  • Network synchronization.
  • Batch size.
  • Application code.
  • One slow worker.
First checks:
  • GPU utilization over time.
  • CPU usage.
  • Storage read throughput.
  • Dataloader logs.
  • Network metrics.
  • Batch size.
  • Per-node performance.
Possible mitigation:
  • Cache data locally.
  • Increase dataloader workers.
  • Tune batch size.
  • Improve dataset format.
  • Move away from slow node.

Playbook: Multi-Node Training Hangs

Symptom:
Distributed job starts, then hangs.
Likely layers:
  • NCCL.
  • RDMA/InfiniBand/RoCE.
  • Node/NIC health.
  • Firewall/routing.
  • Driver/runtime mismatch.
  • One worker crashed.
  • Storage checkpoint hang.
First checks:
  • Job logs from all nodes.
  • NCCL logs.
  • Node health.
  • Network/IB counters.
  • GPU utilization before and after hang.
  • Whether one worker failed first.
  • Whether issue follows node or workload.
Possible mitigation:
  • Resubmit excluding suspicious node.
  • Drain unhealthy node.
  • Check network interface selection.
  • Escalate to networking/SRE with logs and affected nodes.

Playbook: Slurm Job Pending

Symptom:
Job stays pending and does not start.

Likely layers:
  • Resource availability.
  • Partition configuration.
  • Priority/fair-share.
  • Node state.
  • Job dependency.
  • Invalid resource request.
First checks:
  • Pending reason.
  • Requested GPUs/nodes.
  • Partition.
  • Node states.
  • Job dependencies.
  • Account/user permissions.
Possible mitigation:
  • Adjust resource request.
  • Use correct partition.
  • Wait for capacity.
  • Clear dependency if appropriate.
  • Escalate if nodes are unexpectedly drained/down.

Playbook: Kubernetes CrashLoopBackOff

Symptom:
Pod starts, crashes, restarts repeatedly.
Likely layers:
  • Application error.
  • Bad image.
  • Bad entrypoint.
  • Missing config.
  • Missing secret.
  • Permission issue.
  • Resource limit.
  • GPU/runtime issue.
First checks:
  • Pod logs.
  • kubectl describe pod.
  • Exit code.
  • Recent image/config changes.
  • Env vars.
  • Secrets/config maps.
  • Volume mounts.
  • Resource limits.
Possible mitigation:
  • Roll back image/config.
  • Fix env/secret.
  • Increase limits if justified.
  • Correct GPU request/runtime.

Playbook: Inference Latency Spike

Symptom:
Model endpoint becomes slow.
Likely layers:
  • Request size.
  • Queueing.
  • Time to first token.
  • Total generation time.
  • GPU memory pressure.
  • Model worker overload.
  • Bad batching.
  • Routing/load balancer.
  • Cold start.
  • Network path.
  • Storage/model loading.
First checks:
  • Time to first token vs total generation time.
  • Whether this is cold start or warm-path latency.
  • Request length/context length.
  • Concurrency.
  • Queue time.
  • GPU utilization and memory.
  • Worker restarts.
  • Routing errors.
  • Recent deployment.
  • Model loading events.
  • Autoscaling activity.
Possible mitigation:
  • Keep warm replicas.
  • Reduce concurrency.
  • Add replicas.
  • Route away from unhealthy worker.
  • Warm models.
  • Adjust batching.
  • Tune autoscaling policy.

Playbook: Storage Mount Failure

Symptom:
Workload fails because a mounted path is missing or inaccessible.
Likely layers:
  • Filesystem mount.
  • Node-specific issue.
  • Storage backend.
  • Network path.
  • Permissions.
  • DNS.
  • Kubernetes PVC.
First checks:
  • Does it fail on all nodes or one node?
  • Is the mount configured?
  • Are permissions correct?
  • Can node reach storage endpoint?
  • Kernel/mount logs.
  • PVC/binding state if Kubernetes.
Possible mitigation:
  • Remount.
  • Reschedule to healthy node.
  • Fix permissions.
  • Escalate storage backend issue.

Playbook: Slow Checkpointing

Symptom:
Training pauses too long during checkpoint writes.
Likely layers:
  • Storage throughput.
  • Checkpoint size.
  • Checkpoint frequency.
  • Network congestion.
  • Too many writers.
  • Shared filesystem bottleneck.
First checks:
  • Checkpoint size.
  • Write throughput.
  • Storage latency.
  • Network metrics.
  • Which process writes checkpoints.
  • Whether all nodes write at once.
Possible mitigation:
  • Reduce checkpoint frequency.
  • Write from rank zero only if appropriate.
  • Stage to local NVMe then upload.
  • Improve storage target.

Playbook: Node Repeatedly Fails Jobs

Symptom:
Different workloads fail on the same node.
Likely layers:
  • GPU hardware.
  • Driver/kernel.
  • NIC.
  • Storage.
  • Thermal/power.
  • Node image/config.
First checks:
  • Correlation with node.
  • GPU XID/ECC errors.
  • Kernel logs.
  • Reboots.
  • NIC/storage errors.
  • Node state in Slurm/Kubernetes.
  • Recent maintenance.
  • Repeated ECC errors, which can point to GPU or system memory reliability problems.
  • Repeated XID errors, which can point to GPU, driver, PCIe, memory, or hardware-path problems.
Possible mitigation:
  • Drain node.
  • Move workloads.
  • Escalate hardware/SRE.
  • Add health-check improvement if detection missed it.

Playbook: API or CLI Operation Stuck

Symptom:
CLI/API operation hangs, times out, or resource stays pending.
Likely layers:
  • Auth/permissions.
  • Quota/capacity.
  • API backend.
  • Async operation stuck.
  • Terraform state drift.
  • Region-specific issue.
First checks:
  • Exact command/request.
  • Timestamp.
  • Request ID.
  • HTTP status code.
  • Error body.
  • Resource ID.
  • Region/project/account.
  • Reproducibility.
  • Backend/platform health.
Possible mitigation:
  • Retry if safe.
  • Correct request/config.
  • Check quota/capacity.
  • Compare Terraform state with actual resource state.
  • Escalate with request ID and timeline.
