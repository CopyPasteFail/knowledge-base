RAG (Retrieval-Augmented Generation)

Glossary

  • Embedding(s):
    Turning text, and sometimes images/audio/video, into numbers that represent meaning.
    Example: "reset my password" and "I can't log in" should end up close together because they probably mean a similar support problem, even though the words are different.
  • KV Cache:
    A speed optimization used while an LLM is generating text.
    It does not store finished answers. It stores internal model calculations for tokens the model has already read, so the model does not need to redo the same work again.
    The model reads your prompt token by token. For every token, it calculates internal attention data called keys and values. The KV cache keeps those calculations around. When the model continues generating the next token, it can reuse the previous calculations instead of starting from scratch.
    Simple example:
    If many requests start with the same system prompt, the inference engine can reuse the cached calculations for that shared prefix. That saves time.
    KV cache is especially useful for:
    • Long prompts
    • Long conversations
    • Repeated system prompts
    • RAG prompts with repeated instructions
    • High-throughput serving with vLLM, TGI, TensorRT-LLM, SGLang, or similar engines
  • Response Cache / Semantic Cache:
    A separate cache that stores full answers or previous prompt/answer pairs.
    Example:
    This can live in Redis, Memcached, or another datastore.

RAG Architecture: Overview

RAG (Retrieval-Augmented Generation) combines two main AI capabilities:
  • Retrieval: Fetch relevant information from an external knowledge base, usually with semantic search in a vector database.
  • Generation: Use an LLM to generate a natural language answer using the user query and the retrieved information.

RAG Workflow: Step-by-Step

Simple

  1. User Query: User sends a question or prompt.
  2. Query Embedding: An embedding model converts the query into a vector.
  3. Vector Search: The vector DB compares the query vector to stored document vectors and retrieves the most semantically similar documents.
  4. Context Assembly: Retrieved documents are compiled into a prompt along with the original question.
  5. LLM Inference: The inference model (LLM) takes the prompt and generates a coherent, context-aware response.
  6. Return Response: The answer is returned to the user.

Optional

  • KV Caching / Prefix Caching: The LLM serving engine reuses internal calculations for repeated prompt prefixes, such as the same system prompt or conversation history. This improves speed and throughput.
  • Response/Semantic Caching: The app stores full answers or prompt/answer pairs for repeated or near-duplicate questions.
  • Agentic Workflow: If multi-step actions are needed, such as planning, API calls, or tool usage, an agentic layer may manage additional steps.

Agent/Orchestrator

Step-by-Step Flow
  1. User/API sends a query.
  2. The API Gateway / Ingress receives the query and routes it to the Agent/Orchestrator.
  3. The Agent/Orchestrator:
    • Embeds the query using an embedding model service or external API.
    • Searches the Vector DB with the query embedding to retrieve relevant documents.
    • Assembles the prompt by combining the user query, retrieved docs, and system/developer instructions.
    • Optionally checks a response cache for repeated or near-duplicate questions.
  4. The LLM Serving Engine receives the prompt and generates the answer.
  5. The serving engine may use KV cache / prefix cache internally to avoid recomputing repeated prompt prefixes.
  6. The response is returned to the user via the API gateway.
  7. If response caching is enabled, frequent or safe-to-cache answers may be stored by the app layer.

Where Each Technology Sits

  • Embedding Model: Pod/service or external API, such as OpenAI, Google, Cohere, Hugging Face, or a local model.
  • Vector DB: Pod/service or managed service, such as Weaviate, Qdrant, Milvus, Pinecone, or FAISS.
  • LLM Serving Engine: Pod/service such as vLLM, TGI, TensorRT-LLM, SGLang, llama.cpp, Ollama, or a managed cloud LLM endpoint.
  • KV Cache: Usually inside the LLM serving engine. Not normally a separate Redis service.
  • Response/Semantic Cache: App-level cache, often Redis, Memcached, Postgres, or another datastore.
  • Agent/Orchestrator: Your business logic, often a FastAPI service, LangGraph workflow, LangChain app, custom router, or similar.
  • API Gateway / Ingress: K8s ingress controller, NGINX, Istio, cloud load balancer, or API gateway.

They are separate models, but they work together. The embedding model finds relevant context. The LLM uses that context to generate the answer.

Common Use Cases That Connect All the Above

  • AI Chatbots with Company Knowledge: Users ask questions; RAG retrieves and summarizes internal docs, policies, and FAQs.
  • Semantic Search Applications: Employees or users search a knowledge base by meaning, not just exact keywords.
  • Document Q&A: RAG finds relevant sections from long legal, scientific, or technical documents and uses them to answer questions.
  • Code/Support Copilots: RAG retrieves support tickets, code snippets, logs, or docs, and the LLM explains or troubleshoots.
  • Agentic Workflow Example: “Book a meeting with Alice next week and summarize her last three emails.” An agent retrieves data, calls tools, generates summaries, and takes action step by step.
Caching helps in different ways:
  • KV cache speeds up LLM generation by reusing internal calculations.
  • Response cache can skip the LLM call entirely when the same safe answer can be reused.
  • Semantic cache can reuse an answer for questions that mean almost the same thing.

How This Is Served on Kubernetes (Managed or Self-Hosted)

Typical Architecture

  • Pods/Deployments:
    • Embedding Model Service: Converts text/media into vectors. Can be a REST API, open-source model, or cloud embedding endpoint.
    • Vector DB Service: Weaviate, Qdrant, Milvus, or an external managed service such as Pinecone.
    • LLM Inference Service: vLLM, TGI, TensorRT-LLM, SGLang, llama.cpp, Ollama, or a cloud LLM endpoint.
    • Agent/Orchestrator: Runs business logic, prompt assembly, retrieval, routing, and tool usage.
    • API Gateway/Ingress: Receives user queries and routes requests.
    • Response Cache: Optional Redis, Memcached, or database-backed cache.
  • Managed setup, such as GKE + Vertex AI:
    • Kubernetes handles app deployment, networking, scaling, and monitoring.
    • Managed AI services can host embeddings, LLM endpoints, and vector search.
    • Secrets, autoscaling, logging, and monitoring can be handled by the cloud provider.
  • Self-hosted setup:
    • Vector DB, embedding service, LLM server, orchestrator, and cache all run as containers/pods.
    • Kubernetes handles config, scaling, rolling updates, and networking.
  • KV caching:
    • Usually managed by the LLM serving engine itself.
    • Helps when prompts are long or share repeated prefixes.
    • Example: many users hit the same assistant with the same system prompt, so the serving engine can reuse part of the prompt computation.
