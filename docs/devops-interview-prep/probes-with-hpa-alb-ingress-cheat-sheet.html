Probes with HPA, ALB, Ingress - Cheat-sheet

TL;DR

Readiness runs continuously. If it fails, the pod stays Running but NotReady and is removed from Service endpoints so traffic stops. Liveness failure restarts the container but the pod usually stays Running. HPA does not read probes, but readiness failures shift load to fewer pods and can trigger scaling. Ingress and ALB route only to Ready endpoints, and draining needs readiness plus preStop plus grace period

The chain of control (who decides what)

  • Readiness decides whether a pod is in Service endpoints
  • Service endpoints decide where Ingress and ALB can route
  • HPA decides replica count based on metrics
  • Liveness restarts containers, does not directly decide traffic

HPA (Horizontal Pod Autoscaler)

  • Scales number of pods
  • Based on metrics:
    • CPU
    • memory
    • custom metrics (Prometheus, KEDA)
  • Bounded by:
    • minReplicas
    • maxReplicas
  • HPA decides within those limits
  • HPA does not read readiness or liveness directly

Probes and HPA interaction

How readiness affects HPA indirectly
  • Pod fails readiness → removed from endpoints
  • Traffic concentrates on fewer Ready pods
  • Metrics spike on remaining pods
  • HPA scales up
This can be good or can cause oscillations if readiness flaps.
Common failure pattern
  • Readiness is too strict or flaky
  • Pods flip NotReady often
  • Load concentrates, HPA chases spikes, cluster becomes unstable
Best practices
  • Keep readiness stable (avoid flapping)
  • Use startupProbe for slow boots
  • Prefer meaningful metrics (RPS, latency, queue depth) over CPU when possible

Probes and Ingress interaction

Traffic path: Client → Ingress → Service → Ready endpoints only
Readiness fails:
  • Endpoint removed
  • Ingress stops routing new traffic to that pod (via Service)
Ingress does not “check readiness” directly, it follows endpoints.

Probes and ALB interaction (AWS)

You often have two layers of health gating:
  1. Kubernetes readiness (endpoints)
  2. ALB target group health checks
Instance / NodePort mode
  • ALB sends to nodes
  • kube-proxy routes to Ready pods
  • Readiness still controls traffic
IP mode
  • ALB registers pod IPs directly
  • Readiness still removes endpoints, and targets often get deregistered
  • ALB health checks can add lag and complexity
Common mistake
  • Using a strict dependency-based /ready for ALB health checks
  • Causes slow deregistration and traffic glitches when dependencies blip
