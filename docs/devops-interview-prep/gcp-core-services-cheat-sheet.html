GCP Core Services – Cheat-sheet

Source: GCP Core Services – Cheat-sheet.html

How to use this note

This is a practical GCP services cheat-sheet. Each section follows the same pattern:
  • What the service is
  • When to use it
  • Key points worth remembering
  • Common gotchas
  • Self-managed or lower-level alternatives where useful
The goal is not to list every Google Cloud product. The goal is to cover the services that commonly matter in architecture, interviews, system design, production operations, and cloud migration work.

Resource Manager, organization policy, and landing zones

What it is
The resource hierarchy and governance layer for Google Cloud.
Core model
  • Organization
  • Folders
  • Projects
  • Resources
When to use
Always. Every serious GCP environment depends on project structure, IAM inheritance, billing boundaries, networking boundaries, and organization policies.
Use case
A company creates separate folders for prod, staging, and dev, then creates one project per app per environment. Production projects get stricter IAM, logging, and organization policies.
Key points
  • Projects are the main isolation and billing unit
  • Folders group projects by environment, team, product, or department
  • IAM inheritance flows downward from org to folders to projects to resources
  • Organization policies enforce constraints across the hierarchy
  • Shared VPC lets networking live in host projects while workloads run in service projects
  • Landing zones usually combine project factories, IAM baselines, logging, networking, org policies, and Terraform modules
Common gotchas
  • One giant project for everything
  • Too much IAM at the organization level
  • No folder or project naming convention
  • Shared VPC without clear network ownership
  • Adding org policies late after teams already built around bad defaults
Rule of thumb
Design project boundaries intentionally. In GCP, projects are closer to cloud accounts than many people expect.

Folders

What it is
A folder is an organizational container above projects. It groups projects and lets you apply shared IAM, organization policies, and governance rules.
Where it sits
Folders live under the organization or under other folders. Projects can live inside folders.
Organization
├── Folder: Production
│ ├── Project: payments-prod
│ └── Project: analytics-prod
│
└── Folder: Staging
├── Project: payments-staging
└── Project: analytics-staging

How folders and projects work together
Think of the folder as the shared rule layer, and the project as the place where the actual cloud resources live. For example, a Production folder can block public VM IPs, restrict who can change IAM, and require logs to be exported centrally. Under it, payments-prod runs the payment Cloud Run service and Cloud SQL database, while analytics-prod runs BigQuery datasets and pipelines. Both projects inherit the production guardrails, but each project still has its own resources, APIs, quotas, IAM bindings, logs, and billing attribution.
Key points
  • Folders are for grouping projects, not for running workloads directly
  • IAM and organization policies can be applied at the folder level
  • Projects under a folder inherit policies from that folder
  • Folders are often organized by environment, department, team, product, or business unit
Common gotchas
  • Creating too many folder levels before the company actually needs them
  • Applying broad IAM at a folder and forgetting every child project inherits it
  • Mixing unrelated environments under the same folder
  • Treating folders as billing accounts. They are not billing accounts
Rule of thumb
Folders are the grouping and policy layer. Projects are the workload and resource boundary.

Projects

What it is
A project is the main workspace and boundary where most Google Cloud resources live.
Where it sits
Projects live under an organization or folder, and resources live inside projects.
Organization
└── Folder
└── Project
└── Resources

Example
A payments-prod project contains the production payment service, its Cloud Run service, Cloud SQL database, logs, IAM bindings, enabled APIs, quotas, and billing attribution. If it sits under the Production folder, it also inherits the production-wide rules from that folder.
Key points
  • Most resources are created inside a project
  • Projects have their own IAM policies, APIs, quotas, billing links, and audit logs
  • Projects are commonly separated by app, team, environment, or compliance boundary
  • IAM and organization policies can be inherited from folders and the organization above the project
Common gotchas
  • Putting dev, staging, and production in one project
  • Treating a project as just a folder for resources
  • Enabling APIs and permissions manually with no repeatable project setup
  • Forgetting that inherited IAM can affect project access
Rule of thumb
Use projects as real isolation boundaries, not just naming containers.

IAM (“eye-am”)

What it is
The identity and authorization system for Google Cloud resources.
Core idea
An IAM allow policy binds a principal to a role on a resource.
Example
A Cloud Run service account gets Cloud SQL Client on one project and Secret Manager Secret Accessor only on the specific secrets it needs. Developers get Viewer access through a group, not direct personal grants.
Core components
  • Principal: user, group, service account, workload identity, workforce identity, or domain
  • Role: collection of permissions
  • Resource: organization, folder, project, or service resource
  • Allow policy: grants access
  • Deny policy: blocks access even when allow policies exist
  • Organization policy: constrains allowed configurations
Roles
  • Basic roles: Owner, Editor, Viewer. Avoid in production unless there is a narrow reason
  • Predefined roles: service-specific Google-managed roles
  • Custom roles: your own permission bundles
Service accounts
  • Service accounts are workload identities
  • Grant roles to service accounts
  • Let workloads impersonate service accounts when appropriate
  • Avoid long-lived service account keys
Best practices
  • Use groups for human access
  • Use service accounts for workloads
  • Prefer least privilege
  • Audit service account impersonation permissions
  • Avoid project-wide Editor
  • Use short-lived credentials and federation where possible
Common gotchas
  • Granting access too high in the hierarchy
  • Forgetting inherited permissions
  • Giving Service Account Token Creator too broadly
  • Treating custom roles as maintenance-free
  • Keeping JSON keys around after moving to better identity patterns

Workload Identity

What it is
A way for workloads to authenticate to Google APIs without storing long-lived service account keys.
When to use
Use it whenever a workload needs Google Cloud access from GKE, Compute Engine, Cloud Run, Cloud Functions, or external CI/CD systems.
Example
A GKE Pod reads from Pub/Sub using a Kubernetes ServiceAccount mapped to a Google service account. No JSON key is stored in the container image or Kubernetes Secret.
Core idea
A workload proves its runtime identity and receives short-lived credentials to act as a Google service account.
Where it appears
  • GKE: Kubernetes ServiceAccounts can map to Google service accounts
  • Cloud Run: each service runs as a service account
  • Cloud Functions: each function runs as a service account
  • Compute Engine: each VM has an attached service account
  • CI/CD: external identity federation avoids storing JSON keys
Key points
  • Service accounts are identities, not permission bags
  • IAM roles grant permissions to service accounts
  • Runtime identity should be separated by service or workload
  • Removing the IAM binding stops access
  • JSON service account keys are production debt unless there is a very specific reason
Common gotchas
  • Confusing Google service accounts with Kubernetes service accounts
  • Attaching broad roles like Editor to runtime service accounts
  • Leaving old JSON keys active
  • Forgetting that VM OAuth scopes can still matter on Compute Engine

VPC

What it is
The private network boundary inside Google Cloud.
Key GCP-specific behavior
  • VPC networks are global
  • Subnets are regional
  • Routes are VPC-level
  • Firewall rules are VPC-level and target resources by network tag or service account
When to use
Every private workload design: VMs, GKE, Cloud SQL private IP, internal load balancers, hybrid networking, and private service access patterns.
Use case
A production app uses one shared VPC with private subnets in europe-west1, internal services behind private load balancers, and Cloud NAT for controlled outbound internet access.
Key concepts
  • VPC network
  • Subnets
  • Routes
  • Firewall rules and firewall policies
  • Private Google Access
  • Cloud NAT
  • Shared VPC
  • VPC Peering
  • Private Service Connect
  • Cloud VPN and Cloud Interconnect
Best practice
Use custom mode VPCs for production. They make IP planning explicit and avoid surprise subnets.
Common gotchas
  • Overlapping CIDRs (“sigh-ders”) between VPCs, VPNs, partners, or on-prem networks
  • Assuming VPC peering is transitive, meaning A can talk to B and B can talk to C, but A cannot automatically talk to C through B
  • Forgetting subnets are regional
  • Poor secondary range planning for GKE
  • Thinking “private subnet” is enough while workloads still have external IPs

Subnets

What it is
A regional IP range inside a VPC.
When to use
Any regional workload needing private IP space: VMs, GKE nodes, databases, internal load balancers, and private services.
Example
A prod-europe-west1-apps subnet hosts VM and GKE node IPs, while separate secondary ranges are reserved for GKE Pods and Services.
Key points
  • A subnet belongs to one region
  • VMs in any zone in that region can use the subnet
  • Public or private behavior depends on routes, external IPs, firewall rules, and access paths
  • Secondary ranges are commonly used for GKE Pods and Services. For example, a subnet can use 10.0.0.0/20 as the primary CIDR for VM and node IPs, plus 10.4.0.0/14 and 10.8.0.0/20 as secondary CIDRs for GKE Pod and Service IPs
  • Private Google Access is enabled per subnet
Common gotchas
  • Naming a subnet “private” while giving instances external IPs
  • Not reserving enough IP space for GKE secondary ranges
  • Creating too many tiny subnets
  • Forgetting regional scope during HA design

Routes

What it is
The rules that decide where packets go from resources in a VPC.
When to use
Hybrid networking, appliance routing, internet egress, private service routing, VPN, Interconnect, and custom network segmentation.
Example
Traffic to 10.20.0.0/16 is routed through a Cloud VPN tunnel to an on-prem network, while normal outbound internet traffic goes through the default route and Cloud NAT.
How to think about it
GCP creates basic subnet routes for you, so resources inside the VPC know how to reach each subnet automatically. You add custom static routes when traffic should go somewhere specific, like a VPN tunnel, firewall appliance, or NAT path. Dynamic routes are learned through Cloud Router using Border Gateway Protocol (BGP), usually for VPN or Interconnect. When multiple routes could match, GCP first picks the most specific destination range, for example 10.20.1.0/24 beats 10.20.0.0/16. If two routes are equally specific, route priority decides which one wins.
Key points
  • System-generated subnet routes exist automatically
  • Custom static routes can send traffic to next hops
  • Dynamic routes come from Cloud Router and BGP
  • More specific destination ranges win before priority is considered
  • Route priority matters when prefixes are equally specific
Common gotchas
  • Expecting subnet-attached route tables
  • Forgetting return paths in hybrid designs
  • Dynamic routing mode surprises
  • Appliance routing without clear failure behavior

Firewall rules and firewall policies

What it is
Stateful network filtering for ingress and egress traffic.
When to use
Every production network. Use firewall rules to control workload traffic and hierarchical firewall policies for broader guardrails.
Example
Only VMs with the web tag can receive HTTPS from the load balancer health check and proxy ranges. Only service accounts used by app backends can connect to the database subnet.
How to think about it
Firewall rules are defined on the VPC network, not directly on a VM or subnet. The rule then applies to matching VMs or workloads, usually by network tag, service account, or all instances in the VPC. A rule can reference subnet CIDRs as source or destination ranges, but the rule itself still lives at the VPC level.
Key points
  • Rules are stateful
  • Rules can allow or deny ingress or egress
  • VPC firewall rules target resources by network tag or service account
  • Hierarchical firewall policies can enforce org or folder-level controls
  • Firewall logs help explain allowed and denied traffic
Common gotchas
  • Using network tags inconsistently
  • Blocking load balancer or health check ranges
  • Ignoring egress rules
  • Creating broad “allow all internal” rules with no segmentation
  • Assuming GCP has the same subnet-level stateless filtering model as some other clouds

Cloud NAT

What it is
Managed outbound NAT (“nat”) for private resources that need internet egress without external IP addresses.
When to use
Private VMs, GKE nodes, or other private workloads that need outbound access for package updates, APIs, dependencies, or image pulls.
Use case
Private GKE nodes pull container images and install OS updates without having public IP addresses.
Key points
  • Regional service
  • Provides outbound connectivity only
  • Does not allow inbound connections from the internet
  • Uses Cloud Router for control plane configuration
  • NAT IP allocation and port usage matter under high traffic
Common gotchas
  • Thinking Cloud NAT allows inbound access
  • Port exhaustion under high connection counts
  • Forgetting regional scope
  • Allowing private workloads broad internet egress with no controls

Private Google Access

What it is
Private Google Access lets resources without external IP addresses reach Google APIs and services from a subnet.
When to use
Use it when private VMs or GKE nodes need to call Google APIs like Cloud Storage, BigQuery, Artifact Registry, Secret Manager, or Pub/Sub without using external IP addresses.
Example
A private VM has no external IP, but its subnet has Private Google Access enabled. The VM can still call Cloud Storage and Secret Manager APIs.
How to think about it
Private Google Access is enabled on a subnet. It does not expose your VM to inbound internet traffic, and it does not create a private endpoint for your own app. It simply lets private resources in that subnet reach Google APIs through Google-controlled networking instead of needing public IPs on the resources.
Key points
  • Enabled per subnet
  • Useful for private VMs and private GKE nodes
  • Lets workloads without external IPs reach Google APIs and services
  • Often used together with Cloud NAT, but they solve different problems
  • DNS and routes still need to send Google API traffic to the correct Google API endpoints
Common gotchas
  • Thinking it gives inbound access to private VMs. It does not
  • Thinking it replaces Cloud NAT for non-Google internet access. It does not
  • Confusing it with Private Service Connect
  • Enabling it on the wrong subnet
  • Forgetting that firewall, DNS, and routing can still affect access
Rule of thumb
Private Google Access is for private workloads calling Google APIs. Private Service Connect is for private endpoints to services.

Private Service Connect

What it is
Private connectivity for accessing services through private endpoints inside a VPC.
When to use
Private access to Google APIs, managed services, partner services, or internal producer services without exposing traffic directly to the public internet.
Use case
A service project accesses a managed database or partner API through a private endpoint so traffic stays on private Google Cloud networking paths instead of public IPs.
How to think about it
Private Service Connect (PSC) is for private service access between a consumer VPC and a service provider. The consumer side usually sees a private endpoint with an internal IP in its own VPC. The provider side exposes the service through a service attachment or a supported Google-managed service endpoint. This is useful when one VPC, project, company, or partner needs to consume a service without exposing that service through public IPs.
PSC does not magically make every connection private. The client must resolve the service name to the private endpoint, traffic must route to that endpoint, and firewall rules must allow the path. If DNS still points to a public endpoint, the client may still use the public route even though PSC exists.
Do not mix up the related private access options. Private Google Access lets private VMs reach Google APIs without external IPs. Private Service Connect creates private endpoints for Google APIs, published services, managed services, or partner services. Private services access is a separate VPC peering-based pattern used by some managed services.
Key points
  • Consumer VPCs access services through private endpoints or service attachments
  • Useful for secure service producer/consumer patterns
  • DNS and routing still matter
  • Often appears in private database, private API, and partner connectivity designs
Common gotchas
  • Thinking PSC makes every path private automatically
  • DNS resolving to public endpoints by mistake
  • Confusing Private Google Access, Private Service Connect, and private services access
  • Missing firewall or route dependencies

Cloud Load Balancing

What it is
Google Cloud's managed load balancing family for HTTP(S), TCP, UDP, internal, external, regional, and global traffic.
When to use
Public web services, internal services, VM fleets, GKE ingress, Cloud Run front doors, hybrid backends, CDN origins, and multi-region traffic patterns.
Example
A public web app uses an external Application Load Balancer with host and path routing: /api goes to Cloud Run, /static goes to a Cloud Storage backend bucket, and /admin goes to an internal service through controlled routing.
Main types
  • External Application Load Balancer: L7 HTTP(S), global or regional
  • Internal Application Load Balancer: private L7 HTTP(S)
  • Proxy Network Load Balancer: L4 TCP proxying
  • Passthrough Network Load Balancer: L4 TCP/UDP pass-through
  • Internal passthrough Network Load Balancer: private L4 balancing
Global vs regional
Use a global load balancer when users or backends are spread across regions, or when you want one global anycast IP that sends users to the closest healthy backend. This fits public websites, global APIs, multi-region apps, and CDN-backed services.
Use a regional load balancer when the workload lives in one region, traffic should stay in one region, or compliance requires regional control. This fits private apps, internal services, single-region APIs, and region-bound systems.
Example
A public multi-region API usually uses a global external Application Load Balancer. A private payroll app that only runs in europe-west1 usually uses a regional internal load balancer.
Key concepts
  • Forwarding rule
  • Target proxy or backend service, depending on type
  • URL map for L7 routing
  • Backend service
  • Health checks
  • Network Endpoint Groups (NEGs, “negs”) for serverless, GKE, internet, and hybrid backends
Common gotchas
  • Choosing a global load balancer when the workload must be regional
  • Health checks blocked by firewall rules
  • Mixing serverless, GKE, and VM backends without understanding NEGs
  • Forgetting Cloud CDN is usually configured through the load balancer path

Cloud Armor

What it is
Managed WAF (“waff”) and DDoS (“dee-doss”) protection for supported load balancing setups.
When to use
Public-facing web apps, APIs, rate limiting, geo/IP filtering, bot pressure, and L7 attack protection.
Example
A public API sits behind an external Application Load Balancer. Cloud Armor blocks known malicious patterns, applies rate limits, and temporarily blocks abusive IP ranges.
Key points
  • Attaches to backend services behind supported load balancers
  • Supports allow and deny rules
  • Supports preconfigured WAF rules
  • Supports rate limiting and adaptive protection patterns
  • Works well with external Application Load Balancer
Common gotchas
  • Treating Cloud Armor as a replacement for app authentication
  • Enabling strict WAF rules without observing false positives
  • Blocking health checks or legitimate traffic with broad rules

Cloud DNS

What it is
Managed authoritative Domain Name System (DNS) service for public and private name resolution.
When to use
Use Cloud DNS when you need managed public DNS records, private DNS records inside VPCs, hybrid DNS between Google Cloud and on-prem networks, DNS forwarding, DNS peering, or DNS-based traffic steering.
Example
api.example.com points to a global load balancer, while a private DNS zone resolves db.internal.example.com only inside the production VPC.
How to think about it
Cloud DNS is split mainly into public and private zones. A public zone publishes names to the internet, like www.example.com. A private zone is visible only to the VPC networks you authorize, which makes it useful for internal names like db.prod.internal or api.service.local.
For hybrid networks, Cloud DNS can forward specific DNS names to another resolver, such as an on-prem DNS server reachable through VPN or Interconnect. It can also use DNS peering so one VPC can resolve names from another VPC's DNS namespace without copying all the records.
Cloud DNS can also do DNS-based routing policies, such as weighted routing, geolocation routing, and failover routing. This is useful for controlled traffic splitting or backup targets, but DNS is still affected by time to live (TTL) caching, so it should not be treated like instant traffic switching.
Main setups
  • Public managed zone: internet-visible DNS for public domains and services
  • Private managed zone: internal DNS visible only to selected VPCs
  • Forwarding zone: sends DNS queries for a domain suffix to another DNS server
  • Peering zone: lets one VPC resolve DNS names from another VPC's DNS namespace
  • Reverse lookup zone: resolves IP addresses back to names for private environments
  • Delegated subzone: hands a subdomain to another DNS zone or team
  • DNSSEC (“dee-en-ess-sec”): signs public DNS records to reduce spoofing and cache poisoning risk
  • Routing policies: weighted, geolocation, or failover answers for selected records
Use cases
  • Public website: www.example.com points to an external Application Load Balancer
  • Private service names: orders.internal.example.com resolves only inside the production VPC
  • Hybrid DNS: corp.example.com queries are forwarded to on-prem DNS through VPN or Interconnect
  • Shared services: a service VPC resolves names from a central DNS producer VPC through DNS peering
  • Gradual migration: weighted routing sends 90% of traffic to the old endpoint and 10% to the new endpoint
  • Active/backup design: failover routing returns backup IPs only when the active target is unhealthy
Key points
  • Public zones are visible on the internet
  • Private zones are visible only to authorized VPC networks
  • Forwarding zones are for sending DNS queries to another resolver
  • Peering zones are for resolving names across VPC DNS namespaces
  • DNSSEC helps protect public DNS responses from spoofing, but it does not encrypt DNS queries
  • Routing policies can steer DNS answers, but TTL caching makes them less immediate than load balancer routing
  • In Shared VPC setups, private zones are often created in the host project or bound carefully across projects
Common gotchas
  • Forgetting TTL impact during migrations
  • Expecting DNS routing policies to behave like instant load balancer routing
  • Confusing private zones with full service discovery
  • Overlapping private zones in shared or peered networks
  • Creating forwarding rules but forgetting network reachability to the target resolver
  • DNS resolving to public endpoints when the workload should use private endpoints
  • Forgetting DNSSEC also needs registrar-side DS record configuration for public domains

Compute Engine

What it is
Virtual machines in Google Cloud.
When to use
Legacy apps, custom OS needs, stateful services, special networking, lift-and-shift workloads, or anything that does not fit cleanly into Cloud Run or GKE.
Use case
A legacy Java app requires a specific OS package, a custom startup script, and persistent local process management. Running it on Compute Engine is simpler than forcing it into Cloud Run.
Key points
  • Machine families: general-purpose, compute-optimized, memory-optimized, accelerator-optimized
  • Disks: Persistent Disk, Hyperdisk, and Local SSD
  • Images: public images, custom images, hardened images, golden images
  • Instance templates define repeatable VM configuration
  • Metadata server supports identity, config, and bootstrap patterns
  • VM service account defines what the VM can access
  • Zones are failure domains
Common gotchas
  • Treating a single VM as highly available
  • Manually patching snowflake VMs
  • Leaving external IPs on private workloads
  • Over-granting the VM service account
  • Forgetting that disks and static IPs can still cost money after a VM stops
Self-managed alternative
Bare metal, VMware, Proxmox, KVM, or manually managed VMs.

Managed Instance Groups

What it is
Managed fleets of Compute Engine VMs based on an instance template.
When to use
Stateless VM-based services that need autoscaling, autohealing, rolling updates, or multi-zone availability.
Example
A stateless web service runs on a regional managed instance group across three zones. If a VM fails health checks, the group recreates it automatically.
Key points
  • Uses an instance template as the source of truth
  • Supports zonal and regional groups
  • Autohealing uses health checks
  • Autoscaling can use CPU, load balancing utilization, custom metrics, schedules, or queue-like signals
  • Rolling updates support surge, max unavailable, and canary-style rollout patterns
  • Regional groups spread instances across zones
Common gotchas
  • Scaling request-serving VMs without a load balancer
  • Health checks that do not test real app readiness
  • Terraform and autoscaler fighting over target size
  • Using a group for stateful workloads without understanding stateful group behavior

Persistent Disk, Hyperdisk, and Local SSD

What it is
Block storage for Compute Engine VMs and some GKE storage patterns.
When to use
OS disks, VM data disks, databases on VMs, low-latency persistent storage, and stateful workloads tied to VMs.
Example
A PostgreSQL VM uses a regional Persistent Disk for durability across zones. A temporary analytics VM uses Local SSD because speed matters more than durability.
Key points
  • Zonal disks live in one zone
  • Regional Persistent Disk replicates across two zones in a region
  • Snapshots are used for backup and migration
  • Performance depends on disk type, size, and provisioned characteristics
  • Local SSD is fast but ephemeral
  • Hyperdisk gives newer performance and provisioning models for demanding workloads
Common gotchas
  • Using zonal disks for workloads that require regional availability
  • Assuming snapshots are instant full copies
  • Treating Local SSD as durable storage
  • Not sizing disk performance deliberately

Filestore

What it is
Managed NFS file storage.
When to use
Legacy apps expecting shared POSIX (“pah-zicks”)-style storage, shared app files, CI caches, lift-and-shift workloads, and GKE workloads that require NFS.
Use case
Several VMs running the same legacy app need to read and write shared files from one mounted path. Filestore gives them a managed NFS share.
Key points
  • NFS-based
  • Shared access from multiple clients
  • Different tiers affect performance, scale, and cost
  • Useful when apps require a shared filesystem
Common gotchas
  • Using Filestore when Cloud Storage would fit better
  • Underestimating tier and throughput impact
  • Assuming NFS semantics are ideal for cloud-native apps

Cloud Storage

What it is
Managed object storage. It is not a filesystem.
When to use
Static assets, backups, logs, data lake objects, exports, ML datasets, build artifacts, and large unstructured data.
Example
A web app uploads user images to a Cloud Storage bucket. The app stores only object paths in the database, while signed URLs give users temporary access.
Key points
  • Buckets have globally unique names
  • Buckets are located in a region, dual-region, or multi-region
  • Strong consistency for object reads and metadata operations
  • IAM controls access
  • Uniform bucket-level access is the modern default
  • Object versioning keeps old object generations
  • Lifecycle rules handle transitions and deletion
  • Encryption is Google-managed by default, with CMEK support when needed
Storage classes
  • Standard: hot data and frequent access
  • Nearline: infrequent access
  • Coldline: rare access and DR-style data
  • Archive: long-term retention and compliance archives
Common gotchas
  • Treating Cloud Storage like POSIX storage
  • Leaving object versioning enabled without lifecycle cleanup
  • Accidentally allowing public access
  • Choosing cold storage for data that needs frequent access
  • Applying lifecycle rules too broadly by prefix

Cloud CDN

What it is
Managed CDN for content served through supported Google Cloud load balancing paths.
When to use
Static sites, global latency reduction, caching API responses, content acceleration, and reducing origin load.
Use case
A documentation site serves static assets from Cloud Storage through a load balancer with Cloud CDN enabled, reducing latency for users far from the origin region.
Key points
  • Usually enabled on an external Application Load Balancer backend
  • Can cache content from Cloud Storage, backend services, backend buckets, and supported origins
  • Cache behavior depends on headers, keys, TTLs, and invalidations
  • Signed URLs and signed cookies support restricted delivery patterns
  • Cloud Armor can protect supported backends
Common gotchas
  • Low cache hit ratio because origin headers prevent caching
  • Expensive or overused invalidations
  • Caching personalized responses accidentally
  • Thinking CDN fixes slow origin logic

Cloud SQL

What it is
Managed relational database service for PostgreSQL, MySQL, and SQL (“see-quel”) Server.
When to use
Ordinary production relational workloads that need managed operations but do not require global relational scale or extreme performance.
Example
A SaaS backend stores users, subscriptions, invoices, and app state in Cloud SQL for PostgreSQL, with private IP, backups, and point-in-time recovery enabled.
Key points
  • Engines: PostgreSQL, MySQL, SQL Server
  • High availability (HA) uses regional failover configuration
  • Read replicas help read scaling

Managed gateway for exposing APIs backed by Cloud Run, Cloud Functions, App Engine, or other HTTP backends.
When to use
Simple API front doors, auth enforcement, OpenAPI-defined APIs, quota control, and lightweight API publishing.
Example
A small serverless app exposes three Cloud Run APIs through API Gateway using an OpenAPI spec and JWT validation.
Key points
  • Configured with API definitions
  • Good fit for serverless backends
  • Simpler than Apigee
  • Useful for small and medium API surfaces
Common gotchas
  • Choosing API Gateway when full API lifecycle management is required
  • Expecting it to replace service mesh or internal service discovery
  • Weak versioning and API definition hygiene

Terraform and Google Cloud native infrastructure as code (IaC)

Terraform
  • Common default for GCP infrastructure
  • Strong ecosystem
  • Good for reusable modules and platform standards
  • Common interview expectation
Use case
A platform repo defines projects, IAM, VPCs, subnets, Cloud NAT, log sinks, and baseline monitoring in Terraform. App teams consume approved modules instead of hand-clicking resources.
Infrastructure Manager
  • Google Cloud managed Terraform workflow
  • Useful when teams want Terraform with Google-managed execution and state patterns
Cloud Foundation Toolkit
  • Opinionated modules and blueprints for landing zones, networking, IAM, and enterprise patterns
Deployment Manager
  • Older Google-native IaC service
  • Usually not the default recommendation for new work
Common gotchas
  • Manually changing infrastructure managed by Terraform
  • No module versioning
  • Weak state access controls
  • Terraform and autoscalers fighting over runtime fields

MongoDB Atlas on GCP

What it is
Fully managed MongoDB service operated by MongoDB Inc, deployed on Google Cloud infrastructure.
When to use
Teams that need MongoDB compatibility, managed MongoDB operations, Atlas features, and deployment near GCP workloads.
Use case
A product already built on MongoDB moves its app workloads to GCP but keeps MongoDB semantics and tooling by running Atlas in a nearby GCP region.
Key points
  • Third-party managed service
  • Runs in GCP regions
  • MongoDB operates the database control plane
  • Full MongoDB feature set
  • Automated backups, upgrades, scaling, and monitoring
  • Support path and ownership differ from native Google Cloud services
Common gotchas
  • Treating Atlas as a Google-native service
  • Ignoring networking and private connectivity design
  • No clarity on support ownership
  • Underestimating cost at scale
Rule of thumb
Atlas on GCP is managed, but not Google-native managed. That matters for governance, support, SLAs, and ownership.
