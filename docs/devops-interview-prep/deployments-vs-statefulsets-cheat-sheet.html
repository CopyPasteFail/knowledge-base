Deployments vs StatefulSets - Cheat-sheet

Core Difference

Deployment: stateless, interchangeable pods. StatefulSet: stateful, identity-bound pods with stable storage and stable hostnames.

When to Use What? (Fast Rules)

Use a Deployment when:

  • Pods are identical and replaceable
  • You want fast, parallel scaling
  • You need blue-green or canary strategies
  • You don’t need stable network IDs
  • Storage is ephemeral or externalized (DB-as-a-service, caches, microservices)
Examples: web apps, APIs, workers, queues (non-durable), ML inference, frontend services.

Use a StatefulSet when:

  • Pods need stable names (app-0, app-1)
  • Each pod must keep its own data
  • Ordered startup/shutdown matters
  • Storage must persist across restarts
  • The app expects node identity (DB replicas, brokers)
Examples: databases, Zookeeper, Kafka brokers, per-pod storage apps.

Key Behavioral Differences

Pod Identity

  • Deployment: pod-xxx random names, interchangeable
  • StatefulSet: deterministic identity (name-0, name-1) → The app can rely on “node 0” always being node 0.

Scaling

  • Deployment: parallel, fast
  • StatefulSet: strict one-by-one scale up/down

Rollouts

  • Deployment: supports surge, parallelism, blue-green, canary
  • StatefulSet: ordered, serial rollouts; first pod failing stops everything

Storage

  • Deployment: ephemeral by default
  • StatefulSet: auto PVC per pod; PVC sticks even after pod deletion

Renaming

  • Deployment: trivial, no data implications
  • StatefulSet: renaming causes new PVCs → data migration headache

Common Pitfalls

StatefulSet Pitfalls

  • Slow scaling due to ordered rollout
  • Zombie PVCs remain forever unless cleaned
  • Renaming creates new volume names
  • No native canary/blue-green support
  • Poor for DBs unless paired with an operator
  • Hard resets: identity is sticky
  • Terraform drift: immutable fields cause noise

Deployment Pitfalls

  • Not suitable for identity-aware workloads
  • Data tied to pods is unsafe
  • Random hostnames can break legacy or clustered software
  • Rolling updates can break quorum services if misconfigured

Mini Examples

Example 1 – stateless API: Use a Deployment. Pods can scale from 5 to 50 instantly.
Example 2 – Kafka brokers: Use StatefulSet. Each broker must keep identity + its own log directory.
Example 3 – DB failover: StatefulSet alone isn’t enough. You need an operator (e.g., PGO, MySQL Operator).
Example 4 – renaming pain: old-app → new-app in StatefulSet triggers new PVC names like data-new-app-0 that don’t match old ones.

Knowledge-Check Q&A

Why not put databases in StatefulSets directly?

Because StatefulSet doesn’t handle leader election, replication, failover, fencing, or backups. An operator does.

Can I use a Deployment with persistent storage?

Technically yes but dangerous; any pod may mount the wrong volume. That’s why StatefulSet exists.

How to migrate a StatefulSet safely?

Snapshot PVCs → create new StatefulSet → restore volumes with correct names → reattach.

Is it OK to run RabbitMQ or MySQL in a StatefulSet in production?

Question: Is running databases or brokers inside Kubernetes acceptable?
Quick Answer: RabbitMQ: OK if using the operator and proper storage. MySQL: Usually no. Use managed DB unless you have a strong infra team and specific reasons, because backups, upgrades, failover, replication, and data safety are operationally complex and easy to get wrong in Kubernetes.

Update strategy in Deployment vs StatefulSet

Question: How does update strategy behave differently in a Deployment compared to a StatefulSet?
Answer:
  • Deployment: Pods are stateless and interchangeable, so updates focus on availability and speed. Pods can be created and removed in any order.
  • StatefulSet: Pods have stable identities and ordering, so updates happen one Pod at a time, in order, to protect state and dependencies.
Follow-up: How do maxUnavailable and maxSurge affect the update strategy?
Follow-up answer:
These fields are set on a Deployment under spec.strategy.rollingUpdate. They control the speed vs safety tradeoff: higher values mean faster rollouts but more resource usage or risk.
  • maxUnavailable: how many Pods are allowed to be unavailable during an update.
  • maxSurge: how many extra Pods can be created above the desired replica count during an update.
Important:
  • maxUnavailable and maxSurge apply only to Deployments.
  • StatefulSets do not support them because Pods must be updated sequentially and predictably.
