Devops Interview Prep

HTTP Response Codes – Cheat-sheet

Quick map

  • 1xx: informational, server acknowledges the request. Rare to act on.
  • 2xx: success, the request did what it was supposed to do.
  • 3xx: redirects and caching related responses.
  • 4xx: client-side problems, malformed or unauthorized requests.
  • 5xx: server-side failure, upstream problems, or gateway issues.

The full request route (where things break)

Client -> Internet -> CDN / Edge -> Load Balancer -> API Gateway / Ingress -> Service -> Endpoints -> Pod (app container) -> Downstream dependencies (database, cache, queue, external API)
When I say "route" below I mean the step in this chain where the response likely originates. For each status code I list the most typical failure points along that route.

General triage checklist (short)

  1. Reproduce the request with curl -v to see headers and raw response.
  2. Check which system answered first, by comparing headers or IPs returned by curl --trace-ascii or curl -I.
  3. Inspect the gateway/ingress logs, then service endpoints, then pod logs.
  4. If behind k8s, check kubectl get ingress/service/endpoints/pods and kubectl logs for the pod.
  5. If the path involves a queue or worker, check job/consumer logs and broker status.
Useful commands to keep handy:
curl -v -H "Authorization: Bearer $TOKEN" "https://api.example.com/path"
kubectl get ingress -n myns
kubectl get svc -n myns
kubectl get endpoints -n myns
kubectl get pods -n myns -o wide
kubectl describe pod <pod> -n myns
kubectl logs <pod> -n myns --tail 200
kubectl port-forward svc/my-service 8080:80 -n myns
kubectl get events -n myns --sort-by=.metadata.creationTimestamp
kubectl top pod -n myns


200 OK

Friendly explanation: The request succeeded and returned the expected content. Nothing is broken, but verify that the body and headers match the contract.
Common reasons you still need to investigate:
  • The returned data can be stale due to caching layers, so the result looks wrong but the route worked.
  • Partial success: the endpoint responded OK, but downstream processing failed asynchronously.
Typical route where it comes from: any layer that produced the response body, commonly the app pod or a cache (CDN).
Why it happens: App logic executed successfully and returned a 200. If the content is wrong, it is likely a business logic bug, stale cache, or wrong configuration (feature flag, env var).
Triage steps:
  1. curl -i to inspect headers, look for Age, Via, X-Cache, ETag.
  2. If caching appears, bypass with Cache-Control: no-cache to hit origin.
curl -i -H "Cache-Control: no-cache" https://api.example.com/resource/123

Kubernetes specifics: If only some pods return differing content, check which pod you hit with kubectl get pods -o wide and curl --resolve to target pod IP directly.

201 Created

Friendly explanation: A resource was created. The server will usually send a Location header pointing to the new resource.
Common reasons you need to inspect:
  • Duplicate creation attempts can produce idempotency issues.
  • Missing later processing: the resource was created but background jobs failed.
Typical route: App pod created resource in DB or storage, returned 201. Failures afterwards happen in job/worker components.
Why it happens: Create endpoint completes and persists the entity.
Triage steps:
  1. Inspect Location header, GET that URL to confirm the item exists.
  2. Check job/worker logs if creation should trigger processing.
curl -i -X POST -H "Content-Type: application/json" -d '{"name":"x"}' https://api.example.com/items
curl -i GET "$(curl -s -i -X POST ... | grep Location | awk '{print $2}')"

Kubernetes specifics: If creation triggers a Job or CRD controller, kubectl get jobs -n myns or kubectl get <crd> -n myns and check controller logs.

202 Accepted

Friendly explanation: The server accepted the request but will do the actual work later, asynchronously.
Common reasons:
  • The caller expects synchronous completion, but the API is designed async.
  • The background worker queue is full, slow, or dead.
Typical route: API Gateway / App Pod accepted the request and enqueued a job in a broker like Kafka, RabbitMQ, or database table.
Why it happens: Intentional design, but it becomes a problem when the background processing fails.
Triage steps:
  1. Look for a status or location for the async job in the response.
  2. Check the queue/broker and worker deployment logs.
curl -i -X POST -d '{}' https://api.example.com/long-task
kubectl logs deployment/worker -n myns --tail 200

Kubernetes specifics: Check the worker ReplicaSet, HPA, and broker pods. Use kubectl get pods -l app=worker -n myns and inspect broker metrics.

204 No Content

Friendly explanation: The operation succeeded but there is intentionally no response body, typical for DELETE or successful actions with no return value.
Common reasons to follow up:
  • Client expects a body and misinterprets the lack of content as failure.
  • The resource may not have been fully removed, due to finalizers or async cleanup.
Typical route: App successfully handled the request and returned 204, but cleanup might continue in background.
Triage steps:
  1. GET the resource to confirm deletion or state change.
  2. Check related background jobs.
curl -i -X DELETE https://api.example.com/items/123
curl -i https://api.example.com/items/123

Kubernetes specifics: Deleting k8s resources may show Terminating state because of finalizers. Use kubectl get <resource> -n myns and kubectl describe.

3xx Redirects (301, 302, 307, 304)

Friendly explanation:
  • 301 / 302 / 307: Resource moved temporarily or permanently, client should follow Location.
  • 304 Not Modified: Client's cached version is still fresh, server tells client to use cache.
Common reasons:
  • Trailing slash mismatches, domain canonicalization, or CDN rules rewriting URLs.
  • ETag mismatch or caching headers cause 304 responses.
Typical route: CDN or ingress often issues redirects before the request hits the app pod.
Why it happens: Redirects are often intentional, but misconfig in ingress or CDN can route to wrong host or loop.
Triage steps:
  1. curl -I -L to follow redirects and see the Location chain.
  2. Inspect ingress/edge config for rewrite rules.
curl -I -L https://short.example.com/path
kubectl describe ingress my-ingress -n myns

Kubernetes specifics: Check Ingress annotations like rewrite-target or nginx.ingress.kubernetes.io/configuration-snippet that alter paths. Check if TLS redirect is misconfigured.

400 Bad Request

Friendly explanation: The server cannot process the request because the client sent something malformed or invalid.
Common reasons:
  • Invalid JSON payload, missing required fields, wrong Content-Type header.
  • Invalid query parameters, invalid path variables, or invalid form-data boundaries.
Typical route: Request reaches API gateway or app, validation layer rejects it.
Why it happens: The request format or content fails server-side validation.
Triage steps:
  1. Reproduce the same request with curl and a minimal valid payload.
  2. Check server validation error message or logs for field-level errors.
curl -i -X POST -H "Content-Type: application/json" -d '{"bad": }' https://api.example.com

Kubernetes specifics: If the ingress or API gateway rejects the request due to buffer size or header issues, it can return 400 before the app sees it. Check ingress logs and gateway limits such as client_max_body_size.

401 Unauthorized

Friendly explanation: Authentication failed. Either no credentials were provided, the token is invalid, or the token expired.
Common reasons:
  • Missing Authorization header because a proxy stripped it.
  • Expired or malformed token, wrong signing key, or missing scope.
  • Clock skew in JWT validation.
Typical route: Ingress or auth sidecar may return 401, or the app itself rejects the credentials.
Why it happens: The service performing auth rejects the credentials.
Triage steps:
  1. Check WWW-Authenticate header for details.
  2. Decode the token locally to check expiry and claims.
  3. Verify whether the ingress forwards Authorization to the backend.
curl -v -H "Authorization: Bearer $TOKEN" https://api.example.com/protected
# decode JWT
python -c "import jwt,sys; print(jwt.decode(sys.argv[1], options={\"verify_signature\":False}))" $TOKEN

Kubernetes specifics: Some LB or ingress controllers strip Authorization. Confirm Nginx has proxy_set_header Authorization $http_authorization; or check annotations for header preservation. Check oauth2-proxy or other auth sidecar logs.

403 Forbidden

Friendly explanation: The caller is authenticated but not allowed to perform this action, the server knows who you are but you lack permissions.
Common reasons:
  • Missing role or insufficient scope in token.
  • Resource-level ACL denies access.
  • IP-based restrictions or WAF blocks.
Typical route: Gateway or app policy layer rejects the request after auth succeeds.
Why it happens: Authorization policy denies the action.
Triage steps:
  1. Check the token claims for roles and scopes.
  2. Look for policy engine logs: OPA, Kong, or API gateway.
Kubernetes specifics: If calling Kubernetes API, RBAC rules can return 403. Use kubectl auth can-i to test permissions. For app-level 403, inspect the app's authz module or OPA logs if used.
kubectl auth can-i create pods --namespace=myns


404 Not Found

Friendly explanation: The requested path or resource does not exist, or routing did not reach the expected backend.
Common reasons:
  • Wrong URL path or host header.
  • Ingress rules do not match the host or path.
  • Service has no endpoints.
Typical route: Ingress may return 404, or the app returns 404 if resource ID not found.
Why it happens: Either routing configuration is wrong or the resource simply does not exist.
Triage steps:
  1. Use curl -v and check which IP served the response.
  2. Confirm ingress host/path rules.
  3. Confirm service endpoints exist.
kubectl get ingress -n myns
kubectl get endpoints svc/my-service -n myns

Kubernetes specifics: Empty endpoints will often lead to 502/503, but depending on ingress, 404 can occur when no rule matches. Check host and path in kubectl describe ingress.

405 Method Not Allowed

Friendly explanation: The URL exists but the HTTP method used is not allowed for that resource.
Common reasons:
  • Client used POST where only GET is supported.
  • Ingress or proxy blocks certain verbs, or CORS preflight failing.
Typical route: The app or gateway returns 405 when verb is not in Allow list.
Why it happens: Client and server disagree on supported methods.
Triage steps:
  1. Check Allow header in response to see permitted methods.
  2. Use curl -X OPTIONS to inspect supported verbs.
curl -i -X OPTIONS https://api.example.com/resource

Kubernetes specifics: Ingress controllers or API gateways sometimes limit methods. Also check CORS config if browser clients see 405 on preflight.

408 Request Timeout

Friendly explanation: The client took too long to send the full request, or the connection idled out.
Common reasons:
  • Slow client uploads, poor network connectivity.
  • Proxy or ingress idle timeouts too short.
Typical route: Reached gateway or ingress, which closed the connection because the request stream stalled.
Why it happens: Timeouts on the receiving endpoint while waiting for the client request body.
Triage steps:
  1. Reproduce with the same client or curl --upload-file to check speed.
  2. Check ingress controller timeout settings and LB idle timeouts.
curl --max-time 30 -T largefile.bin https://api.example.com/upload

Kubernetes specifics: Nginx proxy-read-timeout, client-body-timeout, or LB idle timeouts can cause this. Inspect ingress configmap.

409 Conflict

Friendly explanation: Two clients tried to change the same resource simultaneously, or the request conflicts with current state.
Common reasons:
  • Resource version mismatch in optimistic locking.
  • Duplicate create attempts with same unique key.
Typical route: App layer checks resource version or constraints, then rejects request.
Why it happens: The requested change cannot be applied because the target is in a different state.
Triage steps:
  1. Read the error message, look for currentVersion or conflict details.
  2. Fetch latest resource and retry with new version or use server-side apply.
# Kubernetes example
kubectl apply --server-side -f resource.yaml

Kubernetes specifics: kubectl may return 409 if resourceVersion conflicts when doing applies. Use kubectl get to fetch the latest and reapply.

410 Gone

Friendly explanation: The resource used to exist but was deliberately removed permanently.
Common reasons:
  • API owners removed an endpoint or resource, clients must migrate.
Typical route: App returns 410 when it wants to force clients to stop using an endpoint.
Why it happens: Intentional deprecation or removal.
Triage steps:
  1. Check API docs or changelog for migration path.
  2. Modify client to use replacement endpoint.

422 Unprocessable Entity

Friendly explanation: The server understands the content type and syntax, but semantic validation failed.
Common reasons:
  • Field-level validation errors, e.g. invalid email format, business rule violation.
Typical route: App validation layer rejects the payload.
Why it happens: Data is syntactically valid JSON but fails schema or business checks.
Triage steps:
  1. Inspect response body for field-level errors.
  2. Fix the payload and retry.

429 Too Many Requests

Friendly explanation: You hit a rate limit. Stop hammering, back off and retry later.
Common reasons:
  • Client exceeded API quota, or a burst exceeded ingress/gateway limits.
  • A faulty client or deployment loop creating traffic spikes.
Typical route: Rate limiting can happen at the CDN, LB, API gateway, or application level.
Why it happens: A throttling policy blocked the request to protect backend capacity.
Triage steps:
  1. Check Retry-After header.
  2. Identify where rate limiting is enforced: CDN, ingress, or app.
  3. Implement exponential backoff in client, or increase quota in gateway config.
curl -v https://api.example.com/path | grep -i Retry-After

Kubernetes specifics: Look at ingress controller annotations for rate-limiting, or API gateway settings (Envoy, Kong, Nginx rate limits). Also check any Cloudflare or CDN settings.

500 Internal Server Error

Friendly explanation: The server crashed or threw an unhandled exception. Generic, but usually the most urgent.
Common reasons:
  • Null pointer exception, unhandled exception, resource exhaustion, bad config.
  • Recent deploy introduced a bug.
Typical route: The app pod produced the error, but sometimes a sidecar or middleware could return 500.
Why it happens: Something in the server stack failed unexpectedly.
Triage steps:
  1. Reproduce the failing request with curl -v.
  2. Check app logs for stack trace. kubectl logs for the pod.
  3. Check recent deploys and configmap/secrets changes.
kubectl logs deployment/my-app -n myns --tail 200
kubectl describe pod my-app-xxxxx -n myns

Kubernetes specifics: If only some pods return 500, suspect config differences, environment variables, or node-level issues. Use kubectl get pods -o wide to see node assignment and compare.

502 Bad Gateway

Friendly explanation: The gateway or proxy could not get a valid response from upstream. The upstream either failed to respond, returned malformed data, or closed the connection.
Common reasons:
  • Backend app crashed mid-response, upstream returned garbage, or TLS mismatch between ingress and backend.
  • No endpoints registered for the Service, or the backend returned invalid HTTP response (binary, no headers).
Typical route: Ingress / API gateway -> Service -> Endpoint -> Pod. The gateway attempted to connect to backend and failed.
Why it happens: The proxy received a malformed or missing response when it called the service.
Triage steps:
  1. Check ingress/gateway logs for upstream errors.
  2. Confirm endpoints exist: kubectl get endpoints svc/my-service -n myns.
  3. Port-forward to backend and call it directly to confirm health.
kubectl logs -n ingress-nginx <ingress-pod> | tail -n 200
kubectl get endpoints svc/my-service -n myns
kubectl port-forward svc/my-service 8080:80 -n myns
curl -v http://localhost:8080/health

Kubernetes specifics: Common when readiness probes fail but the pod still accepts connections, or when TLS is terminated at ingress and backend expects TLS and vice versa.

503 Service Unavailable

Friendly explanation: The service is unavailable, either down for maintenance or overloaded. It is a soft failure telling clients to try again later.
Common reasons:
  • No healthy pods to handle requests, readiness probe failing.
  • Resource saturation, crash loops, or HPA not scaled.
  • Circuit breaker in gateway or service mesh opened.
Typical route: Ingress sees no healthy endpoints or gateway circuit breaker blocks traffic.
Why it happens: The system intentionally refuses traffic to protect itself or because there is nothing to serve the request.
Triage steps:
  1. kubectl get endpoints svc/my-service -n myns to see whether pods are in endpoints.
  2. kubectl get pods -n myns and inspect readiness and recent events.
  3. Check autoscaler and resource usage.
kubectl get pods -n myns
kubectl describe pod my-app-xxxxx -n myns
kubectl get hpa -n myns
kubectl top pod -n myns

Kubernetes specifics: If readiness probes are misconfigured, pods are removed from endpoints and ingress returns 503. Fix the probe or adjust initialDelay/timeout.

504 Gateway Timeout

Friendly explanation: The gateway timed out waiting for an upstream response. The backend is too slow or hung.
Common reasons:
  • Long-running request, slow DB queries, blocking code.
  • Incorrect gateway timeout settings lower than backend processing time.
Typical route: Ingress or API gateway waits for backend and times out while waiting for a response.
Why it happens: Upstream is taking longer than configured timeouts.
Triage steps:
  1. Reproduce using curl --max-time or with verbose timing flags.
  2. Check backend logs to see if the request was received and how long it took.
  3. Tune timeouts where appropriate, or optimize backend.
curl -v --max-time 60 https://api.example.com/slow-path
kubectl logs -n myns <backend-pod> | grep "request-id"

Kubernetes specifics: Check ingress timeouts and service mesh timeouts. A common pattern is proxy-read-timeout in nginx or the route timeout in Envoy.

520/521/523 Edge specific errors

Friendly explanation: Edge provider specific responses meaning the origin responded unpredictably or the edge lost connectivity to origin.
Common reasons:
  • Cloudflare or CDN sees origin return an unexpected response, or origin refused connection.
Typical route: CDN/edge -> origin. The edge is reporting the origin problem.
Why it happens: Origin instability, network partition between edge and origin.
Triage steps:
  1. Check edge provider dashboard for logs and origin checks.
  2. Confirm origin is reachable from the edge by doing curl from your cloud region or using provider tools.

Final Kubernetes-specific patterns and gotchas

  1. Ingress, Service, Endpoints mismatch: If any link in this chain is broken, traffic fails. kubectl get endpoints being empty is the most common root cause of 502/503.
  2. Readiness probes: When a pod fails readiness it is removed from endpoints, producing 503 even though pods exist and may be running.
  3. Liveness vs readiness timing: Liveness kills can cause restarts and transient 5xx. Liveness should be conservative during deployment.
  4. Authorization header stripping: Load balancers or proxies sometimes strip Authorization header. Confirm ingress config forwards headers.
  5. Sidecar/service mesh issues: Sidecar misconfiguration can intercept traffic, converting successful responses to 502/503. Inspect sidecar logs and iptables rules.
  6. NetworkPolicy: A NetworkPolicy blocking traffic between namespace or pods can silently break the route.
  7. PDB and rolling updates: PDBs can stall rolling updates and leave a small number of pods alive, producing overload and 503s.
  8. Resource exhaustion: CPU throttling, OOMKills, or node pressure cause slow or failed responses. Use kubectl top and kubectl describe pod.

Short quick-check flows I use when I hit each major class

5xx generic flow (my go-to when something is broken):

  1. curl -v to capture raw response and headers.
  2. Check ingress logs to see what upstream was used.
  3. kubectl get endpoints svc/my-service -n myns to see if there are targets.
  4. kubectl logs on the pod that should handle the request.
  5. Port-forward to bypass ingress if necessary and call the pod directly.

4xx generic flow:

  1. Verify client request format and headers. Use curl -v.
  2. Check auth tokens and claims.
  3. Inspect gateway for request blocking rules or WAF.

Handy curl snippets

  • Follow redirects and show the chain:
curl -i -L https://short.example.com

  • Show timing and headers:
curl -w "\ntime_total=%{time_total}s\n" -i -s https://api.example.com

  • Force hitting a specific IP / pod (SNI and host header):
curl --resolve api.example.com:443:10.0.0.5 https://api.example.com/path
