Devops Interview Prep

Redis – Cheat-sheet

Quick recap

  • In-memory store with rich data types.
  • Persistence: RDB (snapshots), AOF (logs), or both.
  • AOF rewrite compacts log (especially efficient with RDB).
  • fsync = OS syscall to flush to disk; ensures durability.
  • Sentinel = HA for single-master replication setups.
  • Cluster = sharding across 16,384 slots, multiple masters + replicas, cluster-aware clients needed.
  • Best for caching, sessions, leaderboards.

Data Types

  • Strings: Simple key-value pairs. SET user:123 "George".
  • Hashes: Store objects. HSET user:123 name "George" age "19".
  • Lists: Queues or logs. LPUSH queue "msg1", RPOP queue.
  • Sets: Unique collections. Good for tags or memberships.
  • Sorted Sets (ZSETs): Ordered by score. ZADD leaderboard 500 "user123".
  • Bitmaps: Track on/off flags for millions of users.
  • HyperLogLog: Approximate unique counts (e.g. visitors).
  • Streams: Log-like structure for event streaming.
  • Modules: RedisJSON (document store), RediSearch (search engine), RedisGraph, RedisTimeSeries.

Persistence

  • RDB (Snapshot):
    • Periodically writes full dataset to disk (e.g., every 5 min).
    • Fast restart.
    • Risk: lose data since last snapshot.
  • AOF (Append-Only File):
    • Logs every write command.
    • Configurable fsync modes:
      • always: safest, slowest.
      • everysec: balanced.
      • no: fastest, risky.
    • File grows over time.
  • AOF Rewrite:
    • Compacts log so it doesn’t grow forever.
    • Example: SET x 1, SET x 2, SET x 3 becomes SET x 3.
    • When combined with RDB, the AOF can be reduced to only the changes since the last snapshot. This makes the AOF smaller and makes Redis restarts much faster.
  • Hybrid (RDB + AOF):
    • On restart: load RDB, then replay only new AOF commands.
    • Combines fast startup with durability.
    • Example:
      • RDB snapshot at 12:00 with 10 million keys.
      • Redis crashes at 12:15.
      • On restart, Redis loads RDB from 12:00, then replays 15 minutes of AOF commands.

fsync

  • Definition: An OS system call that forces the operating system to flush buffered writes from memory to the storage device.
  • Context:
    • Without fsync, data may sit in OS cache and be lost in a crash.
    • Redis calls fsync according to the chosen persistence mode (always, everysec, no).
    • Performance depends on storage type: SSD-backed PVCs in Kubernetes make fsync faster than spinning disks.
  • Use case example: In production Kubernetes clusters, SSD-backed disks help maintain low latency when Redis persists data with fsync.

Sentinel (HA for Redis Replication)

  • Concept: Watches masters and replicas. Elects new master if old one fails.
  • Deployment: Run 3–5 Sentinel pods for quorum.
  • Example:
    • Master goes down. Sentinel promotes replica to master.
    • Operator updates Kubernetes Service to point apps to new master.

Redis Cluster Mode

  • Concept: Splits keyspace into 16,384 hash slots.
  • Mapping: slot = CRC16(key) % 16384.
  • Example: cart:user123 hashes to slot 5500 → belongs to Node2.
  • Topology:
    • Multiple masters, each responsible for a subset of slots.
    • Each master typically has 1 or more replicas for redundancy.
    • In cluster mode, failover is handled internally (not by Sentinel).
    • In Kubernetes, masters and replicas are often deployed as a StatefulSet, with headless Services for discovery.
  • Clients: Must be cluster-aware. If sent to wrong node, get MOVED/ASK and update slot map.
  • Failover Example:
    • Master2 dies.
    • Replica2 is promoted.
    • Clients refresh slot map and send traffic to Replica2.
  • Clarification on numbers:
    • Common setup: 3 masters + 3 replicas (1 per master).
    • Larger clusters may have 6, 9, or more masters with replicas.
    • Sentinels are not used in cluster mode; they are only for single-master replication setups.
  • Limitation:
    • Multi-key commands across slots not supported.
    • Workaround: hash tags {} in key names (e.g., user:{123}:cart, user:{123}:profile).

Use Cases

  • User Sessions:
    • SET sess:abc123 {userId:42, role:"admin"} EX 1800.
    • Auto-expiry after 30 minutes.
    • Persist with AOF if you don’t want sessions wiped on restart.
  • Leaderboards:
    • Use Sorted Sets.
    • ZADD leaderboard 100 "player1", ZREVRANGE leaderboard 0 9 → top 10 players.
  • Cache:
    • Fast GET/SET with TTLs. Prevents hammering Postgres.
  • Why not Kafka?
    • Kafka = long-term streaming + replay.
    • Redis = ultra-low-latency cache/store.
  • Why not Postgres for leaderboards?
    • Postgres would sort and aggregate on disk repeatedly.
    • Redis Sorted Sets update in-memory and are orders of magnitude faster.

What Redis Is

Simple terms:
A super-fast, in-memory dictionary your services use to look things up instantly.
Technical terms:
An in-memory data structure store that supports strings, lists, hashes, sets, sorted sets, streams, publish/subscribe, replication, clustering, and optional persistence (AOF/RDB).

Core Strengths

  • Microsecond latency (memory access)
  • Rich data types optimized for real-world use cases
  • Simple scaling for reads via replicas
  • Optional durability (AOF/RDB)
  • Works well as a building block for caching, locks, queues, leaderboards, rate limiting, etc.

How Redis Works (Simple + Technical Explanation)

Simple terms:
Redis keeps everything in memory like a giant dictionary. When you ask for a key, it’s basically a fast lookup. One thread handles everything, so Redis avoids locking complexity. For durability, Redis can optionally save snapshots or write every change to a log. Clustering lets Redis split data across nodes so it can scale beyond a single machine.
Technical terms:
Redis is a single-threaded, event-loop-driven server that stores data structures in RAM. Commands operate atomically as part of a single event loop. Persistence uses two mechanisms:
  • RDB: fork-based point-in-time dumps
  • AOF: write-ahead logging of all mutations
Replication is asynchronous via PSYNC. Clustering partitions the keyspace into 16384 hash slots distributed among nodes. Clients route commands to the appropriate shard using MOVED/ASK redirections. Evictions occur when maxmemory is hit, depending on policy.

Common Pitfalls

1. Persistence Misconfigurations

Bad practice: Using only RDB snapshots when you care about zero data loss. Why: RDB writes data every X minutes. Crash between snapshots = data loss. Technical: RDB uses fork-based point-in-time dumps; AOF logs every write (fsync policies vary).
Good practice: Use AOF for durability, RDB for faster recovery, or both. Why: You balance performance vs safety.

2. Single-thread Bottleneck

Bad practice: Heavy CPU operations on large keys (big JSON blobs, big SORT). Why: Redis runs everything on a single event loop; one big command blocks all clients.
Good practice: Use small keys, avoid CPU-heavy commands, shard logically if needed. Why: You reduce blocking time and keep latency predictable.

3. Blocking Commands

Bad practice: Using KEYS *, FLUSHALL, or deleting millions of keys in one go. Why: These commands freeze Redis until completed.
Good practice: Use SCAN, UNLINK, or batched deletes. Why: They perform work incrementally and avoid locking the event loop.

4. Memory Explosions

Bad practice: No TTLs, giant keys, unbounded lists, or caching entire DB objects. Why: Redis crashes when it hits maxmemory. It’s not a disk store. Technical: Redis is OOM-killed or starts evicting keys depending on policy.
Good practice: Enforce TTLs, avoid large objects, use proper eviction policy, monitor memory. Why: Redis works best with many small, short-lived keys.

5. Clustering Misuse

Bad practice: Assuming multi-key ops work across slots. Why: Redis cluster shards keys by hash slot; multi-key ops require same slot.
Good practice: Use hash tags {} to force related keys into the same slot. Why: Ensures atomic multi-key operations within one shard.

6. Replication Lag

Bad practice: Assuming replicas are always up-to-date. Why: Replication is async; heavy writes cause replicas to fall behind.
Good practice: Use replicas for reads, not strong consistency. Technical: Redis replication uses PSYNC, async propagation, and backlog buffers.

7. Using Redis as a Primary Database

Bad practice: Relying on Redis for long-term durability or ACID semantics. Why: Redis trades durability for speed; tearing on power loss is real.
Good practice: Use Redis for caching, coordination, rate limiting; use a real DB for persistence. Why: Each tool fits a different cost/consistency tradeoff.

When to Use Redis (Good Fits)

Caching hot paths

Why (simple): Redis is insanely fast; it gives your app instant access to precomputed or frequently used data. Why (technical): In-memory O(1) lookups with microsecond latency outperform databases by orders of magnitude.

Rate limiting

Why (simple): Counting requests per user per timeframe is exactly the kind of tiny counter Redis excels at. Why (technical): Atomic INCR, INCRBY, and Lua scripts allow safe, lock-free rate limiting even under high concurrency.

Leaderboards (sorted sets)

Why (simple): Redis sorted sets can sort and update rankings extremely fast. Why (technical): ZADD, ZRANGE, and ZREVRANGE are optimized C implementations with logarithmic scoring operations.

Pub/Sub for lightweight messaging

Why (simple): Good for simple notifications that don’t need durability. Why (technical): Publish/subscribe is in-memory and ephemeral; messages vanish if clients aren’t connected, keeping overhead low.

Distributed locks (short-lived only)

Why (simple): Great for preventing two processes from touching the same thing at the same moment. Why (technical): Redis implements atomic SET key value NX PX semantics; as long as locks are short, drift and expiry issues are minimal.

Session storage

Why (simple): Sessions are small, frequently accessed, and short-lived, which is Redis' sweet spot. Why (technical): Fast reads/writes + TTL-based expiry reduce load on your main database.

Fast counters, scoring, deduping

Why (simple): Incrementing counters thousands of times per second is effortless in Redis. Why (technical): Atomic increments operate directly in memory and avoid locking overhead.

Lightweight queues (lists/streams)

Why (simple): Good for small workloads where you don’t need the complexity of Kafka or RabbitMQ. Why (technical): LPUSH/BRPOP and Streams (XADD/XREADGROUP) offer low-latency message passing without heavy brokers.

When Not to Use Redis (Bad Fits)

Long-term durable storage

Why (simple): Redis keeps data in RAM; if the machine dies unexpectedly, you can lose data. Why (technical): Even with AOF fsync=always, Redis durability isn't as strong as a disk-backed, WAL-based DB like Postgres.

Large values (MB-scale objects)

Why (simple): Huge objects slow Redis down, eat memory fast, and block everything when processed. Why (technical): Redis copies large values during persistence and event-loop operations; this causes latency spikes and fork overhead.

Workloads requiring ACID or complex transactions

Why (simple): Redis is not a relational database; it doesn’t guarantee multi-key atomicity or strong transactional safety. Why (technical): Transactions in Redis (MULTI/EXEC) don’t provide rollback or isolation levels; they queue commands for atomic execution but lack full ACID semantics.

High fan-out messaging

Why (simple): If you need to broadcast messages to thousands of consumers reliably, Redis can’t scale like Kafka. Why (technical): Redis Pub/Sub is not persistent; it doesn’t support partitioning, consumer offsets, or replay. Kafka does.

Heavy ingestion without tuning persistence

Why (simple): If you write too fast while AOF/RDB are enabled, Redis slows down or creates huge persistence files. Why (technical): Forking for RDB snapshots or continuously appending AOF can saturate I/O and block the event loop under heavy throughput.

Mini Examples

Bad:
Storing 3–5 MB user profile JSON blobs as single keys. Why: Blocks the event loop, wastes memory, increases fork-time for persistence.
Good alternative:
Store only frequently accessed fragments or store the JSON in a real DB and cache small computed values.
Bad:
Running KEYS * in production. Why: Full scan of all keys blocks Redis.
Good alternative:
Use SCAN with cursoring. Why: It’s incremental and non-blocking.
Bad:
Using Redis locks for heavy, long operations. Why: Locks aren’t perfect; if client dies, lock expiry can break correctness.
Good alternative:
Use Redis locks only for short, idempotent operations. Or use Redlock with caution.
