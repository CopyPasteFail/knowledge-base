Devops Interview Prep

Terraform - Cheat-sheet

What Terraform is (1-liners)

  • Terraform = declarative IaC tool that builds a dependency graph and drives provider APIs to converge infra to the desired state.
  • Plan shows proposed changes, Apply executes them, State is Terraform’s source of truth for what it thinks exists.

Terraform file types and their purpose

Terraform loads all .tf files in a directory as a single configuration. Naming is for humans, not the engine.
  • .terraform.lock.hcl
       Provider dependency lock file. Pins exact provider versions. Must be committed.
provider "registry.terraform.io/hashicorp/aws" {
version = "5.32.0"
constraints = ">= 5.0.0"
hashes = ["h1:abcdef..."]
}
  • `terraform.tfstate`
       State file when using local state. Contains real resource IDs and computed values. Treat as sensitive data.
{
"resources": [
{
"type": "aws_s3_bucket",
"name": "logs"
}
]
}
  • terraform.tfstate.backup
       Automatic local backup of the previous state after each apply.
  • *.tf
       Core configuration files. Can contain providers, resources, data sources, variables, outputs, locals, and modules.
resource "aws_s3_bucket" "logs" {
bucket = "${var.env}-logs"
}
  • providers.tf
       Declares required providers and version constraints.
terraform {
required_providers {
aws = { source = "hashicorp/aws", version = "~> 5.0" }
}
}
  • backend.tf
       Configures where state lives and how locking works.
terraform {
backend "s3" {
bucket = "tf-state-prod"
key = "app/terraform.tfstate"
}
}
  • variables.tf
       Declares input variables.
variable "env" { type = string }
  • outputs.tf
       Declares exported values.
output "bucket_name" { value = aws_s3_bucket.logs.id }
  • *.tfvars
       Environment-specific variable values.
env = "prod"
  • terraform.tfvars
       Automatically loaded variable file.
  • .terraform/
       Local working directory created by `terraform init`. Never commit.
Rule of thumb:
  • Structure is for humans.
  • State is Terraform’s memory.
  • Providers and backend define how Terraform talks to the world.

Ownership model (who touches which Terraform files)

This governance model prevents accidents.
Control-plane files are restricted, resource files are owned by service teams, and state is never touched by humans

Platform / Infra team

  • backend.tf
  • providers.tf
  • .terraform.lock.hcl

Application teams

  • *.tf
  • variables.tf
  • outputs.tf

Environment owners / CI

  • *.tfvars
  • terraform.tfvars

Terraform only

  • .terraform/
  • terraform.tfstate and backups

State (terraform.tfstate): what it is and why it matters

State is a database, not a cache.
  • State maps Terraform resources to real-world IDs.
  • Losing state means Terraform cannot reason safely.
Remote state basics:
  • Central backend
  • Locking
  • Encryption
  • Restricted access
Golden rule: fix code first, then fix state.

Chicken and egg: bootstrapping Terraform

Terraform needs backend and identity before it can run safely. This is a layering problem.
Common solution:
  • One-time manual or local-state bootstrap to create backend and IAM
  • All other stacks then use remote state

30-second bootstrap explanation (verbatim)

Bootstrap is intentionally boring by design.
We bootstrap Terraform once to create state and identity. After that, everything runs on remote state with locking. Bootstrap is boring and almost never changes

Terraform commands (what each one actually does)

  • terraform initInitializes the working directory by configuring the backend, downloading providers, and installing modules.
  • terraform fmtFormats Terraform configuration files to canonical style.
  • terraform validatePerforms static validation of the configuration without contacting providers.
  • terraform planCompares desired configuration with state and reality, then shows what will change.
  • terraform applyExecutes the planned changes and updates state.
  • terraform destroyDestroys all resources managed by the current state.
  • terraform refresh (legacy)Updates state from real infrastructure without changing resources (largely replaced by plan -refresh-only).
  • terraform plan -refresh-onlySyncs state with real infrastructure without applying changes.
  • terraform importBrings existing infrastructure under Terraform management by attaching it to state.
  • terraform stateLow-level state inspection and manipulation commands (list, show, mv, rm).
  • terraform providersShows which providers are required and where they are used.

Core workflow (muscle memory)

  • terraform init
  • terraform fmt
  • terraform validate
  • terraform plan
  • terraform apply

Providers, resources, data sources

  • Provider = plugin that talks to an external API (AWS, GCP, Kubernetes, GitHub, etc.).
  • Resource = something Terraform creates or updates.
  • Data source = read-only lookup of something that already exists.
Provider + resource (short):
provider "aws" {
region = var.aws_region
}

resource "aws_s3_bucket" "logs" {
bucket = "${var.env}-logs"
}
Data source (read an existing AMI and use it):
data "aws_ami" "al2" {
most_recent = true
owners = ["amazon"]
}

resource "aws_instance" "app" {
ami = data.aws_ami.al2.id
instance_type = "t3.micro"
}

Variables, locals, outputs

Use variables for inputs, locals for derived values, outputs for exported values.
Variables with types and validation:
variable "env" {
type = string
validation {
condition = contains(["dev", "staging", "prod"], var.env)
error_message = "env must be dev, staging, or prod"
}
}
Locals for naming, tags, composition:
locals {
name = "${var.env}-api"
tags = { env = var.env, managed_by = "terraform" }
}
Outputs, mark sensitive when needed:
output "lb_dns" {
value = aws_lb.main.dns_name
}

Modules

Modules are reusable building blocks. They reduce copy-paste, enforce conventions, and shrink blast radius when you split stacks.
Call a local module:
module "network" {
source = "../modules/network"
env = var.env
}
Call a registry module with version pinning:
module "vpc" {
source = "terraform-aws-modules/vpc/aws"
version = "~> 5.0"

name = "${var.env}-vpc"
cidr = "10.0.0.0/16"
}
Design rule:
  • Variables define the module API.
  • Outputs are the contract to consumers.
  • Avoid hidden side effects (creating random IAM roles, wide permissions) unless the module’s whole job is IAM.

Dependency graph and execution order

Terraform is parallel by default, constrained only by dependencies
Terraform builds a DAG from references. If A references B, B runs first. If nothing links them, Terraform can run them in parallel.
Implicit dependency via reference:
resource "aws_security_group" "sg" { /* ... */ }

resource "aws_instance" "app" {
vpc_security_group_ids = [aws_security_group.sg.id]
}
Explicit dependency depends_on (use when the API relationship is real but not visible in attributes):
resource "aws_s3_bucket" "b" { bucket = "${var.env}-b" }

resource "aws_s3_bucket_public_access_block" "pab" {
bucket = aws_s3_bucket.b.id
depends_on = [aws_s3_bucket.b]
}

Lifecycle meta-arguments

lifecycle controls how Terraform replaces and protects resources.
Common patterns:
  • Prevent accidental deletion:
resource "aws_s3_bucket" "critical" {
bucket = "prod-critical"
lifecycle { prevent_destroy = true }
}
  • Create before destroy to reduce downtime (only when the provider supports it):
lifecycle { create_before_destroy = true }
  • Ignore noisy drift (use carefully, it can hide real problems):
lifecycle { ignore_changes = [tags["owner"]] }

count vs for_each

for_each beats count for long-lived infrastructure
  • count is index-based (thing[0]), refactors can accidentally replace resources.
  • for_each is key-based (thing["api"]), stable for long-lived infrastructure.
for_each example:
resource "aws_s3_bucket" "b" {
for_each = toset(["logs", "assets"])
bucket = "${var.env}-${each.value}"
}
count example (good for 0/1 toggles):
resource "aws_cloudwatch_log_group" "lg" {
count = var.enable_logs ? 1 : 0
name = "/${var.env}/app"
}
Gotcha:
  • Changing for_each keys recreates resources.

Expressions and functions

You use expressions to build names, transform inputs, and safely handle optional values.
Useful functions:
  • try(x, fallback) for optional attributes
  • coalesce(a, b, c) first non-null
  • lookup(map, key, default)
  • merge(map1, map2)
  • flatten(list)
for-expressions (list and map transforms):
locals {
names = [for u in var.users : u.name]
by_id = { for u in var.users : u.id => u }
}
Conditionals:
locals {
instance_type = var.env == "prod" ? "m6i.large" : "t3.micro"
}

IAM, secrets, sensitive data

Never hardcode. State is sensitive.

Drift and reconciliation

Drift = reality changed outside Terraform (console edits, scripts, auto-scaling side effects, manual hotfixes).
How to detect:
  • terraform plan (default refresh behavior depends on version and flags)
  • terraform plan -refresh-only to sync state without changing infra
How to respond:
  • If the change is valid: codify it in Terraform so it becomes the new desired state.
  • If the change is not valid: revert manually or re-apply Terraform to restore the declared config.
Anti-pattern:
  • Leaving permanent manual changes in prod while Terraform still “thinks” it owns the resource.

Environments: folders vs workspaces

Separate state per environment.

Debugging and gotchas

Fast triage sequence:
  • terraform fmt -check
  • terraform validate
  • terraform plan
  • terraform providers (who is actually required)
Common gotchas:
  • Renaming a resource without telling Terraform causes destroy and recreate.
  • Changing for_each keys recreates resources.
  • Provider version drift between machines leads to different plans.
  • -target can leave partial state and surprises (emergency only).
Practical commands:
  • See current state addresses: terraform state list
  • Inspect one resource: terraform state show <addr>

Refactors with moved blocks

Use moved blocks (or terraform state mv) when refactoring addresses, so Terraform does not destroy and recreate.
Short example:
moved {
from = aws_s3_bucket.old
to = aws_s3_bucket.new
}
Module refactor example (excerpt):
moved {
from = aws_instance.app
to = module.compute.aws_instance.app
}
Rule:
  • Refactor address first, then apply. This keeps real infrastructure intact.

CI/CD Terraform flow (why it exists and why it’s good practice)

We plan in PRs, review the plan output, and apply from main with gated approvals for prod. That makes infra changes reviewable, reproducible, and auditable
Terraform is powerful enough to delete production in seconds. CI/CD is how you make changes:
  • reviewable
  • repeatable
  • auditable
  • least-privilege

Typical production workflow

Pull Request (PR):
  • terraform fmt -checkStops style drift and reduces pointless diffs.
  • terraform validateCatches obvious config and type issues early.
  • terraform planProduces the real “change proposal” (diff of infrastructure), not just a code diff.
  • Post the plan output to the PR (comment or artifact)So reviewers can approve the actual infra changes.
Review and policy gates:
  • Humans review the planBecause the plan reveals replacements, deletions, and surprise churn.
  • Optional automated policy checks (OPA/Sentinel/tfsec/checkov)Prevent insecure resources from being merged.
Main branch (merge):
  • terraform apply runs in CIUsing a controlled identity and environment, not a developer laptop.
  • For prod, require a manual approval stepThis is a “last gate” to stop catastrophic mistakes.

Why this is good practice

  • Prevents accidental destructionPR review + plan review catches "this will replace the database" before it happens.
  • Makes changes deterministicSame Terraform version, same provider versions, same env vars, same backend, every time.
  • Avoids "works on my machine" plansLocal credentials, local provider versions, and local state differences stop being a risk.
  • Enforces least privilegeCI uses a tightly-scoped role per environment. Developers do not need broad prod permissions.
  • Creates an audit trailYou can answer: who changed what, when, why, and what plan was approved.
  • Encourages small, safe diffsTeams naturally prefer frequent small PRs when plan output is visible.

Practical hardening patterns

  • Separate CI identity per environment (dev, staging, prod)
  • Restrict prod apply to main branch only
  • Store plan as an artifact and apply the same plan where possible
  • Add drift detection job (scheduled plan that alerts)

Knowledge-Check Q&A

Can the Terraform state file contain sensitive data?

Answer: Yes. State often contains real values returned by providers, including passwords, tokens, endpoints, private IPs, and sometimes more.
Important nuance: marking something as sensitive only hides it in CLI output. It does not keep it out of state.
Best practice: treat state like a secret, restrict access hard, use encryption at rest, and avoid managing secrets directly in Terraform when possible.

If I lost the Terraform state file, what happens to the resources?

Answer: The resources keep running. Terraform just becomes blind.
What breaks:
  • plan may think it needs to create everything again.
  • destroy can’t reliably clean up.
  • You risk duplicates or conflicts if you apply.
Recovery:
  • Restore from remote backend versioning if you have it.
  • Otherwise, rebuild state via terraform import, which is slow and error-prone.

Can Terraform detect unused resources automatically?

Problem: Teams often assume Terraform can tell whether something is safe to delete, but that is not what Terraform does.
Best practice: Terraform manages what should exist, not whether the business still uses it.
Approach
  • Terraform can detect drift and state differences
  • Terraform can show resources tracked in state but no longer in code
  • Terraform cannot tell whether a Lambda is invoked, a table is read, or a queue is active
  • Use CloudWatch, cost signals, and dependency analysis to determine actual usage
  • Remove resources safely through Terraform only after runtime validation
