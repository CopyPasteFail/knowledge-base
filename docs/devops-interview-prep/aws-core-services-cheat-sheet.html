Devops Interview Prep

AWS Core Services – Cheat-sheet

EC2 (Elastic Compute Cloud)

What it is
Virtual machines in AWS. You manage the OS, patches, runtime, scaling logic.
When to use
Legacy apps, custom OS needs, full control, stateful workloads, special networking.
Key points interviewers expect
  • Instance types = compute, memory, storage, GPU optimized
  • On-Demand vs Reserved vs Spot
  • Security Groups = stateful firewall
  • IAM Role attached to instance, never use access keys on disk
Common gotchas
  • Forgetting Auto Scaling Groups
  • No AMI versioning strategy
  • Manual patching debt
Self-managed equivalent
  • Bare metal / VMware / Proxmox / KVM VM

Auto Scaling Group (ASG)

What it is Automatically adds or removes EC2 instances based on rules.
When to use Stateless services that must scale or self-heal.
Key points
  • Works with Launch Templates
  • Health checks via ALB or EC2
  • Can scale on CPU, memory (via CloudWatch), or custom metrics
  • desired_capacity is the ASG setpoint
    • AWS tries to keep the group at desired_capacity (bounded by min_size / max_size)
    • Unhealthy instances are replaced to return to that number
    • Scaling policies do not remove it, they adjust it dynamically over time
    • In Terraform, it is the baseline value
      • Re-applying Terraform can push it back unless you intentionally allow drift
      • Common pattern: Terraform manages min_size, max_size, and policies, AWS manages desired_capacity at runtime
How scaling actually works
  • Auto Scaling works by changing DesiredCapacity
    • Target tracking / step scaling: adjusts DesiredCapacity based on metrics
    • Scheduled scaling: sets DesiredCapacity (or Min/Max) at specific times
  • You do not manually change DesiredCapacity in Terraform for day-to-day scaling
Simplest scaling setup
  • Target-tracking policy on the ASG
    • No separate CloudWatch alarms needed
    • Scales up when metric > target, scales down when < target
    • Always bounded by min_size / max_size
  • Trivial metric: average ASG CPU utilization
Other common options
  • ALB request count per target
    • Often better than CPU for web workloads
    • Requires ALB / Target Group resource label wiring
  • Scheduled scaling
    • Predictable, not load-reactive
    • Example: higher desired_capacity during business hours, lower at night
Common gotchas
  • Scaling a request-serving app without a load balancer, so new instances do not actually receive traffic properly
  • No instance warm-up configured, so policies react to startup noise and scale too aggressively or inconsistently
  • Terraform fighting runtime scaling due to fixed desired_capacity
Self-managed equivalent
  • Kubernetes HPA (pods)
  • Custom scripts with Terraform + cron

ALB / NLB (Elastic Load Balancing)

ELB is the legacy umbrella term.
ALB (Layer 7)
  • HTTP/HTTPS
  • Path-based routing
  • Host-based routing
  • Works with ECS, EKS, Lambda
  • Headers
  • Query strings
  • Weighted routing (canary / blue-green)
  • ALB exposes DNS only, IPs change
NLB (Layer 4)
  • TCP/UDP
  • Ultra-low latency
  • Static IP support (i.e. Elastic IP)
Interview hint
If routing by URL or headers → ALB If raw TCP or performance → NLB
Self-managed equivalent
  • Nginx / HAProxy / Envoy
  • F5 / Citrix ADC

VPC (Virtual Private Cloud)

What it is
Your private network inside AWS.
Key concepts
  • CIDR block
  • Subnets (public vs private)
  • Route tables
  • Internet Gateway
  • NAT Gateway
Interview basics
  • Public subnet = route to IGW
  • Private subnet = no direct internet
  • One NAT Gateway per AZ (best practice)
Common gotchas
  • Overlapping CIDRs
  • Single NAT Gateway for multi-AZ workloads
Self-managed equivalent
  • On-prem network
  • VLAN + routing setup

Subnets

What it is
A slice of a VPC tied to a single AZ.
Key points
  • Cannot span AZs
  • Public or private is defined by routing, not name
  • EC2 lives inside subnets
Interview trap
Naming a subnet “public” does nothing. Routing defines it.

Route Tables

What it is
Controls how traffic flows in a subnet.
Typical routes
  • 0.0.0.0/0 → IGW (public)
  • 0.0.0.0/0 → NAT (private)
Self-managed equivalent
  • Linux routing tables
  • Network firewalls

Security Groups

What it is
Stateful firewall at ENI level.
Key points
  • Allow rules only
  • Stateful, return traffic allowed automatically
  • Attached to ENIs, not subnets
Interview favorite Security Groups vs NACLs:
  • SG = stateful, instance-level
  • NACL = stateless, subnet-level

Elastic Network Interface (ENI)

What it is
An ENI is a virtual network card in AWS. It is where IP addresses live and where Security Groups are attached.
Why it matters
  • An ENI lives in exactly one subnet (and one AZ)
  • It consumes IPs from that subnet
  • Security Groups are attached to the ENI, not to the subnet or VPC
  • ENI limits on the EC2 instance cap pod density in EKS
Concrete example (SG → ENI → subnet → VPC → EC2 → pod)
  1. You create a VPC with a subnet 10.0.1.0/20 in eu-west-1a
  2. An EC2 worker node is launched into that subnet
  3. AWS creates an ENI in that subnet and attaches it to the EC2 instance
  4. You attach a Security Group to the ENI (for example: allow inbound TCP 443 from the ALB SG)
  5. The ENI gets a primary IP (for the node) and secondary IPs (for pods, via the CNI)
  6. A pod is scheduled on the node and is assigned one of the ENI’s secondary IPs
  7. Traffic to the pod is evaluated against the Security Group on the ENI, not the subnet
Key takeaway: Security Groups protect network interfaces. Subnets provide IP space. EC2 instances and pods inherit networking behavior through the ENIs they use.

NACL {"nackle"} (Network ACL)

What it is
Stateless subnet firewall.
When used
Rarely. Mostly compliance or legacy.
Common mistake
Forgetting to allow ephemeral ports.

S3 (Simple Storage Service)

What it is
Object storage. Not a filesystem.
Key points
  • Regional resource
  • Highly Available (HA): yes (multi-AZ by default)
  • Globally unique bucket names
  • Strong read-after-write consistency
  • Lifecycle policies for cost control
  • Versioning for rollback and protection
  • Scales automatically
  • No need to pre-partition anymore
  • Multipart upload for large objects
Security
  • Block public access by default
  • Prefer IAM + bucket policies
Self-managed equivalent
  • MinIO
  • Ceph Object Storage
  • NFS with pain

S3 Storage Classes

S3 Standard
  • Frequent access
  • Low latency
  • Highest cost
S3 Intelligent-Tiering
  • Automatically moves objects between tiers
  • Small monitoring fee
  • Great default if access patterns are unknown
S3 Standard-IA
  • Infrequent access
  • Retrieval cost
  • Same durability as Standard
S3 One Zone-IA
  • Single AZ
  • Cheaper
  • No AZ redundancy
S3 Glacier Instant Retrieval
  • Rare access
  • Millisecond retrieval
  • Higher storage cost than Deep Archive
S3 Glacier Flexible Retrieval
  • Minutes to hours retrieval
  • Cheap storage
S3 Glacier Deep Archive
  • Lowest cost
  • Hours to retrieve
  • Compliance and long-term backups
Interview tip Durability is the same (11 nines). Availability and cost change.

S3 Lifecycle Policies

What it does
Automatically transitions objects between storage classes or deletes them.
Typical flow
Standard → IA → Glacier → Deep Archive → Delete
Interview gotcha
Lifecycle rules apply per object prefix or tag, not bucket-wide magic.

S3 Versioning

What it is Keeps old versions of objects.
Why it matters
  • Protects against accidental deletes
  • Enables rollback
  • Required for some compliance setups
Gotcha Storage costs grow fast without lifecycle cleanup.

S3 Replication

CRR (Cross-Region Replication)
  • Disaster recovery
  • Compliance
SRR (Same-Region Replication)
  • Log segregation
  • Data isolation
Requirements
  • Versioning enabled
  • IAM role
  • Destination bucket policy

S3 Access Control (Important)

Preferred
  • IAM roles
    Example: an EC2 instance has an IAM role with s3:GetObject on my-app-bucket/*, so the app can read files without storing AWS keys
  • Bucket policies
    Example: bucket policy allows only the IAM role arn:aws:iam::123456789012:role/app-server-role to read objects from my-app-bucket
  • OAC (Origin Access Control) with CloudFront
    Example: S3 bucket is private, CloudFront uses OAC to fetch objects, and users access the files only through CloudFront, not directly from S3
Avoid
  • Public ACLs
  • Per-object ACL management
Interview phrase “ACLs are legacy. Policies and IAM are the right model.”

CloudFront

CDN in front of S3, ALB, or custom origin.
When to use

  • Global latency reduction
  • TLS termination
  • DDoS protection (with Shield)
Interview details

  • Invalidations cost money
  • OAC (Origin Access Control) preferred over public S3
Self-managed equivalent

IAM {eye-ay-em} (Identity and Access Management)

What it is
AuthZ and AuthN for AWS.
IAM separates identity, permissions, and assumption, so access can be temporary, least-privileged, and auditable.
Core components
  • Users – identity for a person or app that needs long-term access
  • Groups – collection of users, used to attach permissions once instead of per user
  • Roles – temporary identity that can be assumed, no credentials stored, used by AWS services, applications, CI/CD systems, and users who need temporary access
  • Policies – JSON documents that define permissions (Allow / Deny on resources)
Other components
  • Permission policy – what the identity is allowed to do
  • Trust policy – who is allowed to assume the role
  • STS (Security Token Service) – gives temporary credentials when assuming roles
Best practices
  • Use roles, not users
  • Least privilege
  • No long-lived access keys
  • MFA everywhere
Interview trap IAM is global, not regional.
Self-managed equivalent
  • LDAP
  • Active Directory
  • Keycloak

IAM policies

All IAM policies are JSON:
  • Permission policy: defines what actions are allowed for an identity
  • Trust policy: defines who is allowed to assume a role
  • Resource policy: defines who is allowed to access a resource
Each policy type is attached to a different object:
IAM Role
├─ Trust policy (inside the role)
└─ Permission policies (attached to role)

IAM User / Role / Group
└─ Permission policy

Resource (S3 / KMS / SQS / etc)
└─ Resource policy

Policy type
Attached to
Controls
Simple mental model
Permission policy (identity policy)
User / Role / Group
What actions are allowed
What you can do

Role only

Who can become this role

Resource (S3, KMS, SQS, etc)
Who can access the resource

EBS (Elastic Block Store)

What it is
Block storage for EC2. Think virtual disks.
When to use OS disks, databases, low-latency persistent storage for a single instance.
Key points interviewers expect
  • Attached to one EC2 at a time (except io2 multi-attach)
  • AZ-scoped
  • Snapshots stored in S3
  • Volume types: gp3 (default), io1/io2 (IOPS heavy), st1/sc1 (throughput)
  • Persist independently of instance lifecycle
Common gotchas
  • Snapshots are incremental, restores are lazy
  • Performance tied to volume type and size
Self-managed equivalent
  • Local SSD
  • SAN / iSCSI / LVM

EFS (Elastic File System)

What it is
Managed NFS filesystem.
When to use
  • Shared storage across multiple EC2 instances
  • Containers that need shared state
  • Legacy apps expecting POSIX FS
Key points
  • Shared across multiple EC2 instances
  • Multi-AZ by default
  • Grows automatically
  • POSIX compliant
  • Mounts via NFS
Performance modes
  • General Purpose
  • Max I/O
Common gotchas
  • Higher latency than EBS
  • Costs can explode without lifecycle policies
Self-managed equivalent
  • NFS server
  • GlusterFS
  • CephFS

ECR (Elastic Container Registry)

What it is
Managed container image registry for Docker and OCI images. Think “AWS-native Docker Hub.”
When to use
  • Store images for ECS, EKS, and EC2-based containers
  • Tight IAM-based access control for images
  • Private registry close to your compute
Key points
  • Fully managed, no servers to run
  • IAM-based auth, not username/password
  • Integrated with ECS and EKS out of the box
  • Supports image scanning for vulnerabilities
  • Regional service, with optional cross-region replication
  • Repositories can be immutable or mutable (tag overwrite control)
Rule of thumb
If ECR is expensive, cleanup is missing.
Common gotchas
  • No lifecycle policies → storage quietly explodes
  • Same layer stored once per region (replication is not free)
  • External CI systems pulling images repeatedly can drive data transfer costs
  • Mutable tags can break reproducibility if not controlled
Best practices
  • Enable lifecycle policies (keep last N images per tag)
  • Use immutable tags for prod images
  • Run CI inside AWS when possible
  • Be deliberate with cross-region replication
Self-managed equivalent
  • Docker Registry
  • Harbor
  • JFrog Artifactory

Cost breakdown

Main cost
  • Image storage (old images and layers accumulate fast)
Secondary costs
  • Cross-region image pulls
  • Pulls from outside AWS (CI runners, local dev)
  • Replication between regions or accounts
Almost never the problem
  • API calls

Amazon MSK

What it is

Managed Apache Kafka on AWS.

Engines

  • Apache Kafka (provisioned clusters)
  • MSK Serverless (Kafka without broker management)

Key points

  • Kafka API compatibility, clients and tooling stay standard
  • Multi-AZ broker deployment for durability
  • IAM auth option, TLS in transit, encryption at rest
  • Offsets and retention are core, consumers control replay
  • Serverless removes broker sizing, but has feature and tuning limits

Interview favorite

MSK gives you managed Kafka infrastructure, but you still own topic design, partitioning strategy, consumer lag handling, schema governance, and stream app correctness.

Self-managed equivalent

  • Kafka on EC2
  • Kafka on Kubernetes (Strimzi, Confluent Operator)
  • On-prem Kafka clusters

Amazon Aurora

What it is

Cloud-native relational database, MySQL-compatible or PostgreSQL-compatible

Engines

  • Aurora MySQL-Compatible
  • Aurora PostgreSQL-Compatible

Key points

  • Separation of compute and storage
  • Distributed storage across multiple AZs
  • Fast failover and high availability built in
  • Reader endpoints for horizontal read scaling
  • Better throughput and recovery behavior than standard RDS in many workloads

Interview favorite

Aurora is still relational and SQL-first. You still own schema design, indexes, query plans, transaction boundaries, and migration safety.

Self-managed equivalent

  • MySQL/PostgreSQL clusters on EC2
  • PostgreSQL with Patroni/repmgr on Kubernetes/VMs
  • On-prem HA relational clusters

SQS

What it is

Managed message queue for decoupling services and async work.

Queue types

  • Standard queue
  • FIFO queue (with ordering and deduplication)

Key points

  • Pull-based consumption
  • Visibility timeout controls in-flight processing
  • Dead-letter queues for poison messages
  • At-least-once delivery model
  • Great for task distribution, not event replay logs

Interview favorite

SQS is a queue, not a stream log. Use it for background jobs and worker pipelines where messages are processed then discarded.

Self-managed equivalent

  • RabbitMQ on EC2/Kubernetes
  • ActiveMQ on VMs
  • Redis-based queues (BullMQ, RQ, Celery brokers)

SNS

What it is

Managed pub/sub notification and fan-out service.

Delivery targets

  • SQS
  • Lambda
  • HTTP/S webhooks
  • Email/SMS/mobile push (depending on setup)

Key points

  • One publish, many subscribers
  • Works well with SNS -> multiple SQS queues pattern
  • Message filtering by attributes
  • Durable fan-out when paired with SQS subscribers
  • Simple event broadcasting without Kafka complexity

Interview favorite

SNS handles broadcast and fan-out. Pair with SQS per consumer service to isolate retries, throughput, and failures.

Self-managed equivalent

  • NATS pub/sub
  • RabbitMQ topic exchanges
  • Redis Pub/Sub (lighter, fewer delivery guarantees)

MongoDB Atlas on AWS (partner)

What it is

Fully managed MongoDB service by MongoDB Inc, running on AWS infrastructure.

Service model

  • Third-party managed (MongoDB operates it)
  • Deployed in AWS regions
  • Typically procured via direct MongoDB account or AWS Marketplace routes

Key points

  • Full MongoDB feature set
  • Automated backups, scaling, upgrades, monitoring
  • AWS network integrations available (for example private connectivity patterns)
  • Operational burden is offloaded to MongoDB, not AWS
  • Different support and control plane ownership vs native AWS services

Interview favorite

Atlas on AWS is managed, but not AWS-native managed. Operator is MongoDB Inc. This matters for support paths, SLAs, and platform governance decisions.

Self-managed equivalent

  • MongoDB replica sets/sharded clusters on EC2
  • MongoDB on Kubernetes (community or enterprise operators)
  • On-prem MongoDB clusters

Systems Manager (SSM)

What it is

AWS service for managing and operating EC2 and hybrid servers (automation, patching, remote access, config).

Key parts

  • Session Manager (remote shell access without SSH)
  • Run Command (execute commands remotely)
  • Patch Manager (OS patching at scale)
  • Automation (runbooks for ops workflows)
  • Parameter Store (config + secrets-lite)
  • Fleet Manager (GUI view of managed instances)

Common gotchas

  • Instance must have SSM Agent installed (usually default on Amazon Linux)
  • Instance needs IAM role: AmazonSSMManagedInstanceCore
  • Needs outbound access to SSM endpoints (either internet or VPC endpoints)
  • Session Manager is not enabled magically, you must configure IAM + networking

Self-managed equivalent

  • Ansible / SaltStack
  • SSH + Bastion host
  • Puppet / Chef
  • Rundeck

Session Manager

What it is

SSH-like access to EC2 (and on-prem) through AWS Systems Manager, without exposing port 22.

Why it matters

  • No SSH keys
  • No inbound rules (no 0.0.0.0/0:22)
  • No bastion required
  • Full auditing (CloudTrail + session logs)

Key points

  • Works over outbound HTTPS (443) to AWS SSM service
  • Supports port forwarding (DB access, internal services)
  • Can log sessions to CloudWatch Logs or S3

Common gotchas

  • SCP/rsync need extra setup (SSM port forwarding or S3-based transfer)
  • If the instance is private, you need VPC endpoints for:
    • ssm
    • ec2messages
    • ssmmessages

Self-managed equivalent

  • Bastion host + SSH keys
  • VPN + SSH
  • Teleport
  • Okta ASA

AWS Systems Manager Parameter Store

What it is
Managed key-value store for configuration and secrets-lite.
When to use
  • App configuration
  • Environment variables
  • Small secrets
  • Hierarchical config shared across services
Key points interviewers expect
  • Supports plain strings and secure strings
  • SecureString values are encrypted with KMS
  • Paths like /prod/payments/db/host are common
  • Good for config and lightweight secret storage
  • Native integration with EC2, Lambda, ECS, and automation workflows
Rule of thumb
Parameter Store is great when you want simple managed config without pulling in a full secret-management product.
Common gotchas
  • Using it like a high-throughput database
  • Storing secrets there without thinking about IAM and KMS access boundaries
  • Confusing it with Secrets Manager
Interview trap
Parameter Store can store secrets, but Secrets Manager is usually the better answer when you need secret rotation and richer secret lifecycle features.
Self-managed equivalent
  • Consul KV
  • Kubernetes ConfigMaps and Secrets
  • Env files with regret

VPC Endpoint

What it is
Private connectivity from your VPC to supported AWS services without sending traffic over the public internet.
Types
  • Gateway Endpoint
    • For S3 and DynamoDB only
    • Added to route tables
    • No ENI created
  • Interface Endpoint
    • Powered by PrivateLink
    • Creates ENIs in your subnets
    • Used for many AWS services and some third-party services
When to use
  • Private subnets need access to AWS services without NAT or IGW
  • Tighter egress control
  • Reduce public internet exposure
  • Access partner or internal services via PrivateLink
Key points interviewers expect
  • S3 and DynamoDB Gateway Endpoints are different from Interface Endpoints
  • Interface Endpoints live in subnets and have Security Groups because they use ENIs
  • Private DNS can make the normal AWS service hostname resolve to the endpoint inside the VPC
  • VPC Endpoints do not magically make everything private, routing and DNS still matter
  • Endpoint policies can restrict which actions or resources are allowed
Common gotchas
  • Forgetting to enable or understand Private DNS on Interface Endpoints
  • Missing Security Group rules to the Interface Endpoint ENIs
  • Not updating route tables for Gateway Endpoints

AWS Control Tower

What it is
Landing zone setup and governance for multi-account AWS environments.
When to use
  • Multiple AWS accounts
  • Centralized guardrails
  • Standardized account vending
  • Enterprise environments that do not want every team inventing its own account layout
Key points interviewers expect
  • Built on top of AWS Organizations
  • Uses Account Factory to provision new accounts
  • Applies guardrails across accounts
  • Centralizes logging and audit setup
  • Good for baseline governance, not deep customization of everything
Common gotchas
  • Treating it like a magic enterprise platform
  • Fighting the opinionated setup instead of designing around it
  • Forgetting that teams still need IAM, network, and workload standards inside the accounts
Rule of thumb
Control Tower helps standardize the house. It does not run the house for you.
Self-managed equivalent
  • AWS Organizations + SCPs + Terraform modules + internal platform standards
  • Multi-account landing zone built by your platform team

CloudTrail

What it is
AWS API activity log. It records who did what, when, and from where.
When to use
  • Auditing
  • Incident investigation
  • Change tracing
  • Compliance
Key points interviewers expect
  • Records control plane activity by default
  • Can also log data events, like S3 object-level actions, but that costs more
  • Delivers events to S3, and can integrate with CloudWatch Logs
  • Very useful for answering "who changed this" questions
  • Regional service behavior matters, but trails can be multi-region
Interview favorite
CloudTrail is for API auditing. CloudWatch is for metrics, logs, and alarms. They overlap a bit, but they are not the same thing.
Common gotchas
  • Assuming all data events are logged automatically
  • Not enabling an org-wide trail in multi-account setups
  • Sending logs to S3 and then never actually reviewing or alerting on anything
Self-managed equivalent
  • Audit logs from cloud control planes
  • SIEM ingestion of API and admin activity
  • Linux audit trails plus central log collection, but much worse

Step Functions

What it is
Managed workflow orchestration for coordinating multiple steps, retries, branches, and failure paths.
When to use
  • Multi-step serverless workflows
  • Long-running business processes
  • Retry-heavy integrations
  • Explicit state transitions you want visible and auditable
Key points interviewers expect
  • State machine model
  • Works especially well with Lambda, SQS, SNS, ECS, and service integrations
  • Supports branching, retries, backoff, wait states, and parallel flows
  • Standard workflows for durability and long-running execution
  • Express workflows for higher-volume, shorter-lived flows
Interview favorite
Step Functions replace glue-code orchestration. They do not replace business logic itself.
Common gotchas
  • Putting too much logic inside the state machine definition
  • Using Lambda everywhere when native service integrations would do
  • Ignoring cost and execution model differences between Standard and Express
Self-managed equivalent
  • Temporal
  • Airflow for some workflow classes
  • Custom orchestrator service with queues and state tables

X-Ray

What it is
Distributed tracing for AWS applications.
When to use
  • Debugging latency across service hops
  • Understanding where requests spend time
  • Tracing failures through microservices
Key points interviewers expect
  • Shows request path across services
  • Helps identify bottlenecks and error hotspots
  • Common with Lambda, API Gateway, and instrumented apps
  • Useful when logs are not enough and metrics are too aggregated
Rule of thumb
Metrics tell you that the system is slow. Tracing tells you where it got slow.
Common gotchas
  • Expecting useful traces without instrumenting the application
  • Sampling too aggressively and losing the interesting requests
  • Treating X-Ray as a full observability platform
Self-managed equivalent
  • Jaeger
  • Zipkin
  • OpenTelemetry tracing backends

Amazon Bedrock

What it is
Managed foundation model platform on AWS. It gives API access to multiple models without you hosting the models yourself.
When to use
  • LLM applications
  • Managed inference without running GPUs directly
  • Teams that want model access through AWS-native controls
  • Early GenAI products where speed of integration matters more than custom hosting
Key points interviewers expect
  • Access to multiple model providers through one AWS service
  • No need to manage model-serving infrastructure yourself
  • IAM, VPC integration, and AWS governance story matter a lot here
  • Supports common GenAI patterns like prompting, embeddings, and retrieval-based workflows depending on service capabilities
  • Good for teams already deep in AWS who want managed model access
Interview framing
Bedrock is the managed-consumption path. Hosting open models on EKS or EC2 is the managed-infra path. Different tradeoff.
Common gotchas
  • Assuming Bedrock means zero architecture work
  • Ignoring latency, model limits, and per-model capability differences
  • Treating all foundation models as interchangeable
  • Forgetting that RAG quality still depends mostly on your data, chunking, retrieval, and evaluation
Self-managed equivalent
  • vLLM or TGI on EKS or EC2
  • Self-hosted inference stack with open models
  • External model APIs outside AWS
Rule of thumb
If the interview is infra-focused, talk about Bedrock in terms of governance, integration, latency, cost, and when not to self-host.

Knowledge-Check Q&A

Core VPC Design Considerations

Non-overlapping CIDR

Why: Overlapping CIDRs break peering, VPNs, and future mergers. Fixing overlap later is extremely painful.
Follow-up: What mistake do teams commonly make here?
Follow-up answer: Choosing CIDRs that are too small or conflict with on-prem or future environments.

Enough IP space

Why
  • IP exhaustion silently breaks scaling
  • Kubernetes and ALBs consume IPs aggressively
    • Kubernetes gives every pod its own IP.
    • AWS VPC CNI:
      • Assigns VPC IPs directly to pods
      • Keeps a buffer of unused IPs per node and Pre-allocates IPs to nodes to allow fast pod startup
        • Those IPs are:
          • Allocated from the subnet
          • Count as “used”
          • Not available to anything else
      • Even if no pod is running yet.
      • This is controlled by documented settings:
        • WARM_IP_TARGET
        • MINIMUM_IP_TARGET
        • WARM_ENI_TARGET
      • Important clarification - This is not universal Kubernetes behavior
        • Overlay CNIs (Calico overlay, Flannel) → no, pods don’t consume VPC IPs
        • That’s why this problem is much worse on EKS than on some other clusters
  • Subnet resizing is painful

Why do we design subnets per Availability Zone?

Answer: For fault isolation, predictable routing, and easier debugging.
Follow-up: What breaks if subnets aren’t AZ-aligned?
Follow-up answer: Failover behavior becomes unclear and debugging network issues gets much harder.
Key point: High availability in AWS is achieved by creating multiple subnets, one per AZ, and spreading resources across them.

How should you size VPC subnets?

Question: What is a typical subnet CIDR configuration, and why does sizing matter?
Answer: Subnet CIDRs must be planned intentionally. The CIDR determines how many IPs are available in each AZ, and running out of IPs causes hard failures. This is especially critical for EKS, where nodes, pods, ENIs, load balancers, and VPC endpoints all consume IP addresses.
Typical configuration (example):
  • VPC: 10.0.0.0/16
  • 3 AZs, per AZ:
    • Public subnet: /24 (for ALB/NLB, NAT Gateway)
    • Private app subnet: /20 to /21 (for EKS nodes and most workloads, sized larger because EKS burns IPs)
    • Optional intra / isolated subnet: /24 to /23 (no route to IGW or NAT, used for internal-only components or specific patterns)
Quick sizing intuition:
  • /24 gives 256 IPs minus AWS-reserved addresses, which is easy to exhaust in EKS-heavy subnets.
  • /20 gives 4096 IPs minus reserved, which is why many teams default to /20 for private EKS subnets.
Common pattern: One public subnet and one private subnet per AZ. If you run EKS at scale, private subnets are usually the first ones you oversize.

How subnets are used in multi-AZ EKS

Question: How does EKS use subnets when the cluster spans multiple Availability Zones?
Answer: In a multi-AZ EKS cluster, you provide multiple subnets, typically one private subnet per AZ. EKS spreads worker nodes across these subnets, and the Kubernetes scheduler places pods on nodes in whichever AZ has capacity.
Each node consumes IPs from its subnet, and each pod consumes an IP from the node’s ENI allocation. This means IP pressure is per-AZ, not global. If one AZ’s subnet runs out of IPs, pods cannot be scheduled there, even if other AZs still have free capacity.
Load balancers also follow this model: an ALB or NLB creates one node per AZ and attaches to the corresponding subnets. If a subnet is missing or exhausted, that AZ is excluded from load balancing.
Key implication: High availability in EKS requires both enough subnets and sufficiently large CIDRs in every AZ. Multi-AZ does not save you from IP exhaustion if one subnet is undersized.

Can you get a static IP with an Internet Gateway?

Question: Can an Internet Gateway (IGW) give you a static IP?
Answer: No. An IGW is a routing target, not a resource with an IP. It scales and load-balances globally, so there is nothing to pin a static IP to.
Follow-up: Why did AWS design it this way?
Follow-up Answer: Static IPs would break elasticity and fault tolerance. AWS wants IGW traffic to scale transparently without customers depending on fixed IPs.

Why does ALB not support static IPs?

Question: Why is an Application Load Balancer DNS-only?
Answer: Because ALBs scale horizontally. AWS constantly adds and removes backing nodes (the underlying EC2 instances or network endpoints that actually receive and handle traffic behind the load balancer), so IPs change as part of normal operation.
Follow-up: What is the recommended way to integrate with ALB?
Follow-up Answer: Always rely on DNS. AWS explicitly designs ALB to be consumed via DNS, not IP pinning.

If you truly need static IPs in AWS, what are your options?

Answer:
  • Network Load Balancer with Elastic IPs
  • CloudFront in front of ALB for stable Anycast IP ranges
Follow-up: What are the tradeoffs?
Follow-up Answer: NLB is L4 only with less routing intelligence. CloudFront adds another layer and complexity but gives caching, TLS termination, and WAF.


NAT Gateway vs NAT Instance

Question: When would you use a NAT Instance instead of NAT Gateway?
Answer: Only at small scale when cost matters more than operational simplicity.
Follow-up: Why is a NAT Instance risky?
Follow-up Answer: You manage patching, scaling, and HA yourself. It’s easy to create a single point of failure.

How does IPv6 reduce NAT usage?

Answer: IPv6 gives every instance a globally unique IP, so outbound traffic doesn’t require NAT.
Follow-up: Why isn’t IPv6 widely adopted yet?
Follow-up Answer: Many services are still IPv4-only. Dual-stack increases complexity and makes debugging harder.

What are VPC Endpoints and why use them?

Question: What are VPC Endpoints, why would you use them, and do you need them for every service?
Answer: VPC Endpoints allow private access to supported AWS services without routing traffic over the public internet or through NAT. Traffic stays on the AWS backbone, which improves security and makes costs and latency more predictable.
You do not need endpoints for every service. Only AWS services that support PrivateLink or Gateway Endpoints can use them, and they should be added selectively. High-volume, AWS-internal traffic like S3, ECR, STS, SSM, and CloudWatch is usually a good fit. Low-volume, infrequent, or highly variable traffic is typically fine through NAT.
Why they cost money: Each VPC Endpoint is implemented as managed network interfaces (ENIs). As you add more services and availability zones, the number of endpoints grows, and so does the cost.
Rule of thumb: If traffic is predictable, high-volume, and stays within AWS, use a VPC Endpoint. If traffic goes to many external or changing destinations, or volume is low, keep using NAT.

NAT vs VPC Endpoints at scale

Question: How does cost behavior differ between NAT and VPC Endpoints?
Answer: NAT scales with traffic volume, while endpoints are mostly flat and predictable. At large scale, endpoints are often cheaper.
Follow-up:  What’s the usual cost-optimized pattern?
Follow-up Answer: Use VPC Endpoints for AWS services and NAT only for true external internet access.
Example use case: A private EKS cluster pulling images from ECR and writing logs to CloudWatch. Without VPC Endpoints, all this traffic goes through NAT and scales linearly with usage. With Interface Endpoints for ECR, S3, and CloudWatch, the traffic stays inside the AWS network, costs become predictable, and NAT is only used for real outbound internet calls like external APIs.
Example where NAT is still the right choice: Your workloads need to reach many changing third‑party services on the public internet (payment providers, SaaS APIs, public package registries, webhooks), and you also want a single, controlled outbound egress point with stable source IPs for allowlisting. In that case, NAT is the simplest default: endpoints won’t help (they only cover specific AWS services), and trying to replace NAT with dozens of service-specific paths becomes operationally messy.

Why do some teams put instances in public subnets?

Answer: To avoid NAT cost and simplify routing.
Follow-up: Why is this dangerous?
Follow-up Answer: It increases the attack surface and is easy to misconfigure. One bad security group can expose everything.

When are public IPs acceptable?

Question: When is it acceptable to use public IPs?
Answer:  For stateless services with no SSH access, SSM only, and very tight security groups.
Follow-up: Would you ever do this in regulated environments?
Follow-up Answer: Rarely. Most regulated environments prefer private subnets with controlled egress.

Why use multiple AWS accounts or environments?

Answer: To reduce blast radius, enforce clean IAM boundaries, and simplify audits and billing.
Follow-up: What’s a common anti-pattern?
Follow-up answer: Putting prod, staging, and experiments in the same account and relying only on naming conventions.

Why consider IPv6 even if you don’t use it today?

Answer: It future-proofs networking and can reduce NAT dependency long term.
Follow-up: How should teams adopt IPv6?
Follow-up answer: Gradually, usually via dual-stack, starting with non-critical services.

How does AssumeRole authorization flow work?

Layers flow
IAM Identity (user / role / service) → tries to assume a role → Trust policy (who is allowed to assume) → STS gives temporary credentials → Permission policy (what the role can do) → AWS API authorization
Runtime flow
Caller (user / service / CI) → tries AssumeRole → AWS checks trust policy → if allowed → temporary credentials → permission policies evaluated → API allowed / denied

How should I manage Lambda access to DynamoDB and SQS?

Problem: When several functions share data stores and queues, broad permissions and hardcoded config quickly become messy and unsafe.
Best practice: Use least privilege for access and a central config store for environment-specific values.
Approach
  • Give each Lambda its own IAM role
  • Scope permissions to the exact DynamoDB tables and SQS queues it needs
  • Store table names, queue URLs, feature flags, and non-secret config in Parameter Store
  • Store secrets in Secrets Manager or Parameter Store with KMS encryption
  • Avoid hardcoding endpoints, resource names, or credentials


What is the request path when using LoadBalancer vs Ingress?

LoadBalancer
Client → DNS → Load Balancer → Kubernetes Service → Pod
Ingress
Client → DNS → ALB / ingress load balancer → Ingress rules → Service → Pod

Why use IAM roles instead of users or hardcoded credentials?

An IAM user is a long-lived identity that can have permanent credentials like passwords or access keys, while an IAM role is a temporary identity that is assumed when needed and provides short-lived credentials through STS. In modern AWS design, users are mainly for human access, while roles are preferred for workloads, services, CI/CD, cross-account access, and automation.
This approach follows core security principles:
  • Least privilege — grant only the permissions required
  • Temporary access — use short-lived credentials instead of static secrets
  • Separation of duties — different identities for different responsibilities
  • Credential minimization — avoid distributing long-term secrets
  • Auditability and accountability — role assumption is easier to track and reason about than static credentials.

How is CI/CD given a role in AWS?

Usually through STS AssumeRole or AssumeRoleWithWebIdentity.
Traditional pattern The CI system has some initial AWS credentials and uses them to call AssumeRole into a target role.
Modern preferred pattern The CI platform uses OIDC federation.
Example: GitHub Actions gets an OIDC token from GitHub, AWS verifies it, and AWS lets that workflow assume a role without stored AWS secrets.
