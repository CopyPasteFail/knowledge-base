Cloud Architecture Fundamentals

Cloud Computing and Modern Application Architecture

This document explains the main cloud service models, serverless computing, microservices architecture, and availability/SLA expectations.
The goal is to understand what each model gives you, what you still manage yourself, when each model is useful, and what tradeoffs come with it.

Cloud Service Models

Cloud service models describe how much responsibility stays with you and how much responsibility moves to the cloud provider.
At a high level:

IaaS

IaaS, or Infrastructure as a Service, provides virtualized computing resources over the internet.
Instead of buying and maintaining physical servers, you rent infrastructure such as virtual machines, storage, networking, and compute capacity from a cloud provider.

What you manage

  • Operating system
  • Runtime and dependencies
  • Application code
  • Application configuration
  • Data
  • Security patches above the infrastructure layer

What the provider manages

  • Physical servers
  • Data centers
  • Physical networking
  • Storage hardware
  • Virtualization layer

Simple example

You create a virtual machine on AWS EC2, install Linux, configure Nginx, deploy your application, and manage updates yourself.
That is IaaS: the cloud provider gives you infrastructure, but you still operate most of the software stack.

Best used when

  • You need control over the operating system or runtime
  • You are migrating existing server-based workloads
  • You need custom networking or infrastructure configuration
  • You want flexibility and are willing to manage more complexity

Tradeoffs

  • More control, but more operational responsibility
  • You manage OS updates, runtime patches, scaling, and monitoring
  • Easier to customize, but slower to operate than managed platforms

PaaS

PaaS, or Platform as a Service, gives developers a managed platform for building, deploying, and running applications without directly managing servers.
A PaaS provider hosts the infrastructure, operating system, runtime, and development tools. Developers usually focus on writing and deploying application code.

What you manage

  • Application code
  • Application configuration
  • Application data
  • Environment variables and deployment settings

What the provider manages

  • Servers
  • Storage
  • Networking
  • Operating system
  • Runtime/platform tools
  • Some scaling and deployment capabilities

Simple example

You push a web application to Heroku or Google App Engine. The platform builds it, runs it, exposes it publicly, and handles much of the infrastructure work.
That is PaaS: you focus mostly on the application, not the machines running it.

Best used when

  • You want to deploy applications quickly
  • You do not want to manage servers directly
  • Your application fits the platform’s supported runtimes and deployment model
  • Developer productivity matters more than low-level infrastructure control

Tradeoffs

  • Faster development and deployment
  • Less infrastructure work
  • Less control over the underlying environment
  • Possible vendor lock-in
  • Platform limits may become painful for unusual workloads

SaaS

SaaS, or Software as a Service, is a cloud model where users access a complete application over the internet.
The user does not manage servers, operating systems, runtime, or application code. The provider operates the full application and infrastructure.

What you manage

  • User accounts
  • Permissions
  • Application settings
  • Data inside the application
  • Business usage of the tool

What the provider manages

  • The application itself
  • Servers and infrastructure
  • Operating system
  • Runtime
  • Updates and maintenance
  • Availability and scaling

Simple example

You use Gmail for email. You configure your account and settings, but Google runs the application, infrastructure, storage, updates, and availability.
That is SaaS: you consume the software rather than build or operate it.

Best used when

  • You need a ready-made application
  • You do not want to build or maintain the software yourself
  • The product already solves your business need well enough
  • You want fast adoption with minimal technical operations

Tradeoffs

  • Fastest to adopt
  • Lowest operational burden
  • Least customization and infrastructure control
  • Data, pricing, integrations, and availability depend heavily on the vendor

Serverless Computing

Serverless computing lets developers build and run applications without managing the underlying infrastructure.
The name is a bit misleading. Servers still exist, but the developer does not provision, patch, scale, or directly operate them. The cloud provider handles that work behind the scenes.

What you manage

  • Function or application logic
  • Configuration
  • Permissions
  • Events and triggers
  • Application data

What the provider manages

  • Servers
  • Runtime infrastructure
  • Automatic scaling
  • Provisioning
  • Infrastructure availability

Simple example

A user uploads an image to storage. That upload triggers a serverless function. The function resizes the image and saves the smaller version.
You write the resize logic. The provider runs the function only when needed and scales it automatically.

Common use cases

  • Event-driven tasks
  • APIs with variable traffic
  • Scheduled jobs
  • Image or file processing
  • Webhooks
  • Automation workflows
  • Lightweight backend services

Benefits

  • Less infrastructure management
  • Automatic scaling
  • Pay-per-use pricing model
  • Faster development for event-driven workloads
  • Good fit for spiky or unpredictable traffic

Tradeoffs

  • Cold starts can affect latency
  • Debugging can be harder
  • Local development may not perfectly match production
  • Long-running workloads may not fit well
  • Vendor lock-in is more likely
  • Observability and tracing require more planning

Microservices Architecture

Microservices are an architectural approach where an application is composed of small, independent services that communicate through well-defined APIs.
Each service usually owns a specific business capability and can be developed, deployed, and scaled independently.

Monolith vs. microservices

Architecture
How it works
Strengths
Weaknesses
Monolith
The application runs as one tightly coupled unit
Simpler to build, test, deploy, and debug at first
Harder to scale and change as the codebase grows
Microservices
The application is split into independent services
Independent scaling, deployment, and team ownership
More operational and distributed systems complexity

Simple example

An e-commerce system might be split into services such as:
  • User service
  • Product catalog service
  • Cart service
  • Payment service
  • Order service
  • Notification service
Each service has a clear responsibility. The payment service can be deployed or scaled without redeploying the product catalog service.

Characteristics of microservices

Autonomous

Each service can be developed, deployed, operated, and scaled without tightly depending on the internal implementation of other services.
Services communicate through APIs rather than shared internal code.

Specialized

Each service focuses on a specific business capability or problem area.
For example, a payment service should handle payment-related logic. It should not also own product search, user profiles, and email notifications.

Independently deployable

Teams can release changes to one service without redeploying the whole application.
This is one of the main reasons companies adopt microservices, especially when many teams work on the same product.

Benefits

Agility

Small teams can own specific services and move faster because they work in a smaller, clearer context.

Flexible scaling

Each service can be scaled based on its own demand.
For example, if search traffic spikes, the search service can scale without scaling the entire application.

Easier deployment of isolated changes

A change to one service can be deployed independently, which reduces the blast radius of many releases.

Technology flexibility

Different services can use different technologies when there is a real reason.
For example, one service might use Python for ML workflows while another uses Go for high-throughput APIs.

Resilience

A failure in one service does not always have to crash the whole application.
For example, if the recommendation service fails, the product page can still load without recommendations.

Tradeoffs

Microservices are not automatically better than monoliths. They solve some problems but create others.
Common challenges:
  • More network communication between services
  • Harder debugging and tracing
  • More complex deployments
  • More complicated local development
  • Data consistency becomes harder
  • More monitoring and alerting required
  • Requires stronger DevOps practices
  • Can create unnecessary complexity for small teams or simple products

When microservices make sense

Microservices are usually a better fit when:
  • The product is large enough to justify service boundaries
  • Multiple teams need independent ownership
  • Different parts of the system scale differently
  • Deployment independence matters
  • The organization has strong CI/CD, monitoring, and operations practices
For a small product or early-stage system, a well-structured monolith is often simpler and better.

Availability, Uptime, and SLA

Availability describes how much of the time a system is expected to be working and reachable.
SLA, or Service Level Agreement, defines the availability level a provider commits to.

Why 100% uptime is unrealistic

A 100% uptime SLA sounds attractive, but it is usually unrealistic.
Systems need upgrades, maintenance, failover testing, security patches, and infrastructure changes. Unexpected problems can also happen, such as overloads, hardware failures, software bugs, network issues, and provider outages.
To get close to 100% uptime, a system needs serious redundancy across infrastructure, application components, data stores, and operations. Even then, guaranteeing true 100% availability is extremely difficult.

Practical ways to improve availability

  • Run across multiple availability zones
  • Use load balancing
  • Avoid single points of failure
  • Add health checks and automatic restarts
  • Use monitoring and alerting
  • Keep backups and test restores
  • Design disaster recovery procedures
  • Use automated failover where needed
  • Roll out changes gradually
  • Define clear incident response processes

Simple example

A basic web app running on one virtual machine can go down if that VM fails.
A more available setup might use:
  • Two or more application instances
  • A load balancer
  • A managed database with backups
  • Health checks
  • Monitoring alerts
  • A rollback strategy for bad deployments
That still does not guarantee 100% uptime, but it makes downtime less likely and recovery faster.

Better SLA expectation

Instead of demanding 100% uptime, define a realistic target based on business impact.
For example:
  • Internal dashboard: 99% may be enough
  • Customer-facing SaaS app: 99.9% or 99.99% may be needed
  • Payment or emergency system: higher availability and stronger disaster recovery may be required
The higher the availability target, the more expensive and complex the architecture becomes.
