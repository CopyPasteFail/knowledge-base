Probes & Pod States - Cheat-sheet

One-liner summary

Startup probe delays checks during boot. Readiness continuously controls traffic by adding or removing the pod from Service endpoints. Liveness restarts a container when it is wedged and a restart is the correct fix

Core definitions

  • Readiness: should this pod receive traffic?
  • Liveness: should Kubernetes restart this container?
  • Startup: is the app done booting yet?
Golden rule:
  • Readiness controls traffic
  • Liveness controls restarts
  • Startup protects slow boot
Readiness is continuous (not only at startup)
  • Readiness runs on a schedule (periodSeconds) for the entire pod lifetime
  • It can flip Ready ↔ NotReady multiple times
  • Only startupProbe is “startup-only”

What happens when probes fail

Readiness fails
  • Pod phase usually stays: Running
  • Pod becomes: NotReady (Ready=False)
  • Pod is removed from Service endpoints
  • No restart
  • kubectl get pods often shows:
    • READY 0/1, STATUS Running
Liveness fails
  • Kubelet kills and restarts the container
  • Pod phase usually stays: Running
  • Container cycles: Terminated → Running
  • Restart count increases
  • Traffic impact depends on readiness (best practice is readiness flips to NotReady during restart)
Startup fails
  • Pod never becomes Ready, no traffic
  • While startup is failing: liveness and readiness are ignored
  • If failureThreshold is exceeded: container can be killed (depends on kubelet behavior and config)

When to use what (fast guidance)

Use readiness for
  • Dependency temporarily down (DB, cache, upstream API)
  • Warmup phase (caches, models)
  • Overload and traffic shedding
  • Anything where you want: “stop sending traffic, do not restart”
Use liveness for
  • Deadlock
  • Hung event loop
  • Stuck process where restart is the correct fix
  • Anything where you want: “restart will likely recover”
Do NOT use liveness for
  • DB connectivity checks
  • External service availability
  • Network health
Reason: causes restart storms and makes outages worse.
Use startupProbe for
  • Slow boot apps (JVM, heavy init)
  • Migrations on boot
  • Cold cache warmups
Goal: prevent liveness from killing the app during boot.

Probe knobs (the rules)

  • periodSeconds: how often to check
  • timeoutSeconds: how long to wait per check
  • failureThreshold: consecutive failures before action
  • successThreshold:
    • Readiness: consecutive successes to become Ready again
    • Liveness: effectively 1 in practice
  • initialDelaySeconds: legacy delay, usually replaced by startupProbe
Quick math:
  • Effective “time to action” ≈ periodSeconds * failureThreshold

Canonical YAML example (all 3 probes)

apiVersion: v1
kind: Pod
metadata:
name: probe-demo
spec:
containers:
- name: app
image: my-app:latest
ports:
- containerPort: 8080

startupProbe:
httpGet:
path: /health/startup
port: 8080
periodSeconds: 10
failureThreshold: 30
# up to 5 minutes boot time (30 * 10)

readinessProbe:
httpGet:
path: /health/ready
port: 8080
periodSeconds: 5
timeoutSeconds: 2
failureThreshold: 3
successThreshold: 1

livenessProbe:
httpGet:
path: /health/live
port: 8080
periodSeconds: 10
timeoutSeconds: 2
failureThreshold: 3

What each probe actually does here

startupProbe

startupProbe:
failureThreshold: 30
periodSeconds: 10
  • App gets 300 seconds to boot
  • During this time:
    • Liveness ignored
    • Readiness ignored
  • Prevents crash loops on slow startup

readinessProbe

readinessProbe:
failureThreshold: 3
periodSeconds: 5
  • ~15 seconds of failures → pod becomes NotReady
  • Pod is removed from Service endpoints
  • Container keeps running
Typical /health/ready logic:
  • DB reachable
  • Cache warmed
  • App not overloaded

livenessProbe

livenessProbe:
failureThreshold: 3
periodSeconds: 10
  • ~30 seconds of failures → container restart
  • Pod identity stays the same
  • Restart count increments
Typical /health/live logic:
  • Event loop responsive
  • No deadlock
  • Internal state sane

Basic probe types

HTTP
httpGet:
path: /health
port: 8080
TCP
tcpSocket:
port: 8080
Checks port open only, not app logic.
Exec
exec:
command: ["cat", "/tmp/healthy"]
Works but is usually least preferred (shell, filesystem coupling).

Graceful shutdown pattern (for draining)

Use:
  • readinessProbe
  • preStop
  • terminationGracePeriodSeconds
Example snippet:
terminationGracePeriodSeconds: 30
containers:
- name: api
lifecycle:
preStop:
exec:
command: ["sh", "-c", "sleep 10"]
Conceptual flow:
  • Pod set NotReady
  • Endpoint removed
  • Traffic drains
  • preStop runs
  • process exits within grace

Pod States

Pod phases (kubectl get pod)

Phase
Meaning
Pending
Scheduled but not running yet (image pull, init, etc)
Running
At least one container is running
Succeeded
All containers exited successfully
Failed
All containers exited, at least one failed
Unknown
Node unreachable / status unknown

Container states (inside pod)

State
Meaning
Waiting
Pulling image, starting, or failing to start
Running
Container running
Terminated
Container exited
Common reasons:
  • CrashLoopBackOff
  • ImagePullBackOff, ErrImagePull
  • OOMKilled
Key interview point:
  • A pod can be Running + NotReady. Phase is not the same as readiness.

What state is the pod in when probes fail?

Readiness fails
  • Pod phase: Running
  • Condition: Ready=False
  • Container: Running
  • Traffic: stopped (endpoint removed)
  • Restart: no
Typical output:
NAME READY STATUS RESTARTS
api-123 0/1 Running 0
Liveness fails
  • Pod phase: usually Running
  • Container: restarted
  • Restart count: increases
  • Traffic: depends on readiness and how quickly app returns
Typical output:
NAME READY STATUS RESTARTS
api-456 1/1 Running 3

Bonus edge cases

CrashLoopBackOff

  • Caused by repeated liveness failures or process exit
  • Pod phase often still Running
  • Container repeatedly restarting

OOMKilled

  • Container terminated by kernel
  • Pod phase remains Running
  • Restart depends on restartPolicy
