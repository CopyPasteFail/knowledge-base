EKS – Cheat-sheet

EKS – Cheat-sheet

EKS (Elastic Kubernetes Service)

What it is: Managed Kubernetes control plane. AWS runs:
  • API server
  • etcd
  • scheduler
What you still manage
  • Worker nodes
  • Networking (VPC, subnets, routing)
  • Autoscaling
  • Security
  • Upgrades
Key truth: EKS plugs Kubernetes into AWS networking. It does not abstract it away.

VPC in EKS

Core rule

An EKS cluster lives in exactly one VPC.
Everything happens inside it:
  • Nodes
  • Pods
  • Load balancers
  • ENIs
  • Routing
EKS does NOT:
  • Create overlay networks
  • Hide AWS networking
  • Span VPCs or regions

Subnets in EKS (Critical Section)

Subnets are AZ-scoped

  • One subnet = one Availability Zone
  • Nodes live in a subnet
  • Pods inherit IPs from that subnet
Subnets are not optional details.They directly limit scale.

Public vs Private Subnets (Best Practice)

Public Subnets

  • Route: 0.0.0.0/0 → Internet Gateway
  • Used for:
    • ALB / NLB
    • Ingress endpoints
  • Should NOT host worker nodes

Private Subnets

  • No direct internet access
  • Outbound via NAT Gateway
  • Used for:
    • Worker nodes
    • Pods
Interview-safe statement: “In EKS, nodes and pods run in private subnets, load balancers live in public ones.”

How Pods Get IP Addresses in EKS

EKS uses the AWS VPC CNI.

What this means

  • Every pod gets a real VPC IP
  • No overlay network
  • No NAT between pods

How it works

  • Node gets ENIs from AWS
  • ENIs have multiple secondary IPs
  • Pods are assigned those IPs
Consequence: Pods consume subnet IPs directly.

Why Subnet Size Is Critical in EKS

If subnets are too small:
  • Nodes can’t attach ENIs
  • Pods can’t get IPs
  • Pods stay in Pending
  • Autoscaling fails silently

Production rule of thumb

  • Use /19 or /20 per AZ
  • Never /24
  • Plan for peak pod count, not average
This is one of the most common EKS outages.

Multi-AZ EKS Architecture

Control Plane

  • Always multi-AZ
  • Fully managed by AWS

Worker Nodes

  • Spread across subnets in multiple AZs
  • Each node lives in exactly one AZ

Pods

  • Scheduled onto nodes
  • AZ distribution controlled via:
    • Multiple node groups
    • Topology spread constraints
    • Pod anti-affinity
Important: Multi-AZ EKS does NOT mean state automatically moves across AZs.

Storage and AZ Awareness

EBS

  • AZ-bound
  • Pod must run in same AZ as volume
  • StatefulSets must respect locality

EFS

  • Multi-AZ
  • Shared filesystem
  • Higher latency

S3

  • Regional
  • Accessed via SDK
  • Never mounted as a filesystem in serious setups

Load Balancers and Subnets

  • ALB / NLB are created in public subnets
  • Forward traffic to pods in private subnets
  • Subnet selection is controlled by tags
Wrong tags = broken ingress.

Security Groups in EKS Networking

Node Security Groups

  • Control traffic to and from nodes
  • Pods inherit rules implicitly

Pod Security Groups (optional)

  • Assign SGs directly to pods
  • Useful for strict isolation
  • Adds complexity

Auto Scaling Group (ASG)

What it is
  • AWS EC2 resource
  • Defines how worker nodes are created
  • Exists outside Kubernetes

Defined in an ASG

  • Min / Max / Desired capacity
  • Launch Template:
    • AMI
    • Instance types
    • EBS config
    • Bootstrap script
    • IAM instance profile
    • Security groups
  • Subnets (AZ placement)
  • Health checks
  • Tags (mandatory for autoscaling)
Kubernetes never sees ASGs, only nodes.

Cluster Autoscaler (CA)

What it is
  • Kubernetes controller
  • Runs as a pod
  • Talks to AWS APIs
  • Not a Kubernetes object
What it does
  • Watches pending pods
  • Adjusts ASG desired capacity
What it does NOT do
  • Create pods
  • Change instance types
  • Bypass ASG limits
  • Fix bad subnet design

HPA vs Cluster Autoscaler

HPA

  • Scales pods
  • Based on metrics
  • Kubernetes object

Cluster Autoscaler

  • Scales nodes
  • Based on scheduling pressure
  • Kubernetes controller

Correct flow

  1. Traffic increases
  2. HPA creates more pods
  3. Pods go Pending
  4. CA increases ASG desired_capacity
  5. EC2 nodes launch
  6. Pods are scheduled

Relationship: HPA → CA → ASG

HPA (pods)
↓
Pending Pods
↓
Cluster Autoscaler
↓
ASG Desired Capacity
↓
EC2 Instances
↓
Nodes join cluster

EKS Across Regions (Reality Check)

  • One EKS cluster = one region
  • No multi-region cluster
  • Multi-region = multiple clusters

Common pattern

  • One EKS cluster per region
  • Global routing via Route 53 / CloudFront
  • Data replication handled separately
Kubernetes does not solve multi-region for you.

Karpenter (Modern Replacement)

  • Launches EC2 directly
  • No ASGs
  • Smarter bin-packing
  • Faster scale-up
Still requires HPA.

Common Failure Scenarios

  • Subnets too small → IP exhaustion
  • Single-AZ node group → AZ outage
  • EBS volume rescheduled to wrong AZ
  • Expecting Kubernetes to fix networking
  • Missing ASG tags → autoscaler does nothing

Core Mental Model

  • VPC = network boundary
  • Subnets = AZ placement + IP pools
  • Nodes = live in subnets
  • Pods = consume subnet IPs
  • Kubernetes = scheduling intent
  • AWS = networking and compute execution
If you understand this, you understand EKS.

How EKS CNI and Warm Targets Interact with ENI and Pod Capacity

Amazon VPC CNI

Key truth: EKS plugs Kubernetes into AWS networking. It does not hide AWS networking.
Answer: The Amazon VPC CNI assigns real IP addresses to pods from the node’s subnet CIDR range. There is no overlay network.

How it works

  1. An EC2 worker node starts inside a subnet.
  2. AWS attaches an ENI to the node.
  3. The ENI has one primary IP (node) and multiple secondary IPs.
  4. The aws-node DaemonSet (Amazon VPC CNI) assigns one secondary IP per pod.
Result: Pod IP = a real subnet IP.

ENI, Secondary IPs, and Pods

An ENI can hold multiple IPv4 addresses:
  • Primary IP → used by the node itself
  • Secondary IPs → extra IPs that the CNI can hand out to pods
Secondary IPs are allocated by AWS from the subnet CIDR.
Example: subnet is 10.0.1.0/24, AWS allocates 10.0.1.x addresses to ENIs.
Role of ENI: The AWS resource that holds the IPs (virtual NIC).
Role of CNI: The Kubernetes networking plugin that requests IPs from AWS and assigns one IP to each pod.
Flow: VPC → Subnet → ENI → Secondary IP → Pod.

Capacity Limits (Instance + Subnet)

Pod capacity on a node is limited by EC2 networking limits plus subnet capacity.
Each EC2 instance type has:
  • Max ENIs per instance
  • Max IPs per ENI
Approximate formula: Max pods ≈ (Max ENIs × IPs per ENI) − 1
The −1 accounts for the node’s primary IP.
When limits are reached:
  • No free secondary IPs → CNI tries to allocate more IPs or attach another ENI
  • ENI limit reached → CNI cannot attach more ENIs
  • Pods stay Pending because they cannot get an IP
Even if the instance type supports more pods, a small subnet can run out of IPs. Then new ENIs cannot get IPs, and new pods cannot start.

Why not attach all ENIs upfront?

Answer: Because it wastes IPs and harms scalability.
  • ENI attach takes time and uses AWS API calls
  • Unused ENIs reserve subnet IPs that other nodes could use
  • Higher risk of subnet exhaustion
  • Most nodes do not need peak pod capacity all the time
Better approach: Attach ENIs dynamically and keep a small warm buffer.

Warm IP and Warm ENI Targets

What it means in practice

WARM_IP_TARGET: Keep at least N free IPs available on the node for fast pod startup.
Example: WARM_IP_TARGET=5 → try to keep 5 unused IPs ready.
WARM_ENI_TARGET: Keep N completely unused ENIs attached for burst scaling.
Example: WARM_ENI_TARGET=1 → keep one spare ENI attached.
Tradeoff:
  • Higher values → faster startup, more IP reserved
  • Lower values → slower bursts, better IP efficiency

Where to configure

Configured in Kubernetes as environment variables on:
  • DaemonSet: aws-node
  • Namespace: kube-system
Terraform can automate it if you manage the add-on, but the live configuration is in Kubernetes.

Default behavior

Yes, there are defaults and the cluster works without setting these.
  • ENIs attach dynamically
  • IPs are allocated automatically
  • A small buffer is maintained
Exact default behavior depends on the VPC CNI version and whether prefix delegation is enabled.

AWS Secrets Manager with EKS

IRSA (recommended)

Answer: Use IAM Roles for Service Accounts (IRSA). Create an IAM role with permission to read a specific secret, bind it to a Kubernetes service account, and pods assume the role automatically. The application fetches secrets via the AWS SDK at runtime. No static AWS keys are stored in the cluster.

What is OIDC?

OIDC (OpenID Connect) is an identity layer built on top of OAuth 2.0. In EKS, it allows Kubernetes service accounts to federate with AWS IAM.
In practice:
  • The Kubernetes service account issues a signed identity token.
  • AWS trusts the EKS OIDC provider.
  • IAM validates the token.
  • AWS issues temporary credentials for the IAM role.
This is how IRSA works without static access keys.
Mental model: Pod → Service Account Token → OIDC Federation → IAM Role → Temporary Credentials.

Is OIDC built-in in EKS?

OIDC support is built into EKS, but it is not automatically usable until you associate an IAM OIDC provider with the cluster.
Important distinctions:
  • It is not a Kubernetes object you manually create.
  • It is an IAM identity provider that must be created in AWS and linked to the EKS cluster.
  • This is usually done once per cluster (for example via eksctl utils associate-iam-oidc-provider or Terraform).
Once the IAM OIDC provider is associated:
  • Kubernetes service accounts can issue OIDC tokens.
  • IAM can trust those tokens.
  • IRSA works.
So OIDC is built into EKS at the platform level, but it must be explicitly enabled at the AWS IAM level before IRSA can function.

Step-by-step

1. Create IAM policy

{
"Effect": "Allow",
"Action": "secretsmanager:GetSecretValue",
"Resource": "arn:aws:secretsmanager:region:account-id:secret:my-secret"
}

2. Create IAM role with OIDC trust

Trust relationship must allow:
  • Principal: EKS OIDC provider
  • Condition: service account name + namespace

3. Annotate Kubernetes service account

apiVersion: v1
kind: ServiceAccount
metadata:
name: app-sa
namespace: production
annotations:
eks.amazonaws.com/role-arn: arn:aws:iam::account-id:role/app-secrets-role

4. Use service account in the deployment

spec:
serviceAccountName: app-sa

5. Application retrieves the secret (example)

AWSSecretsManager client = AWSSecretsManagerClientBuilder.defaultClient();
GetSecretValueRequest request = new GetSecretValueRequest().withSecretId("my-secret");
Important points to say:
  • No static AWS keys inside pods
  • Credentials are short-lived
  • Least privilege IAM
  • Works because EKS uses OIDC federation

Knowledge-Check Q&A

ALB 502 Bad Gateway in EKS

Question: You’re getting 502 Bad Gateway from an AWS ALB in EKS. What do you check first?
Answer: A 502 from ALB usually means the ALB could not get a valid response from its targets, or the targets are unhealthy/unreachable. I follow a fast checklist to isolate whether it’s ALB config, Kubernetes wiring, networking, or app behavior.
Checklist:
  • Confirm it’s really ALB: check response headers, if you see Server: awselb/2.0 the response was generated by ALB (meaning the request reached ALB but ALB failed talking to the backend). This immediately narrows the issue to target group health, networking, protocol mismatch, or backend failures, instead of debugging the client, DNS, or the application itself. If enabled, check ALB access logs.
  • Target group health: in AWS console go to Target Group → Targets → Health status + reason. If unhealthy, verify:
    • Health check path (/healthz vs /health)
    • Health check port (service port vs container port)
    • Success codes (200 vs 204)
    • Protocol (HTTP vs HTTPS)
  • Kubernetes wiring (most common): verify Ingress, Service, and Endpoints are correct:
    • kubectl get ingress -n <ns>
    • kubectl describe ingress -n <ns> <name> (check controller events)
    • kubectl get svc -n <ns> / kubectl describe svc -n <ns> <svc>
    • kubectl get endpoints -n <ns> <svc> (empty endpoints = no traffic)
    • kubectl get pods -n <ns> -l <selector> -o wide
  • Look for:
    • Service selector doesn’t match Pods
    • targetPort points to wrong container port
    • Pods not Ready (readinessProbe failing)
    • App only listening on localhost instead of 0.0.0.0
  • Security Groups and networking: if pods are healthy but ALB can’t reach them:
    • Security Groups and networking is about verifying the network path hop by hop.
Traffic flow: Client → ALB listener → Target Group → Node/Pod IP → Container port
Cause and effect checks:
  • If clients can’t reach the ALB (ALB SG issue):
    • ALB security group must allow inbound on the listener port (e.g. 443).
    • If this is wrong, you won’t even reach ALB.
  • If ALB is reachable but can’t reach targets (Node/Pod SG issue):
    • Target Group forwards to a backend port (e.g. 8080).
    • Node security group (or Pod security group ) must allow inbound from the ALB SG to that backend port.
    • If this is blocked, ALB cannot connect, targets become unhealthy, and you get 502.
  • If using IP target mode (targets are pods):
    • ALB connects directly to Pod IPs.
    • Security group rules must allow ALB → Pod IPs on the target port.
    • If this is misconfigured, ALB returns 502 even if pods are Ready.
Concrete example:
  • Client hits ALB on 443
  • Target Group forwards to backend on 8080
  • Service maps port: 80 → targetPort: 8080
Required rules:
  • ALB security group: allow inbound 443 from client
  • Node/Pod security group: allow inbound 8080 from ALB SG
If the Node/Pod security group does not allow 8080, ALB fails to connect to targets and returns 502.
  • Protocol mismatch / TLS confusion: common 502 cause:
    • ALB sends HTTP but backend expects HTTPS (or vice versa)
    • Wrong backend-protocol annotation
    • Backend closes connection or redirects unexpectedly
  • App behavior causing 502:
    • Crashes / OOMKills during traffic
    • Slow startup, readiness passes too early
    • Connection closed before response
  • Check:
    • kubectl logs -n <ns> <pod>
    • kubectl describe pod -n <ns> <pod> (restarts, OOMKilled)
  • Timeouts: less common but real:
    • ALB idle timeout too low for long requests
    • Backend takes too long and returns nothing
Follow-up: What’s the fastest signal to narrow it down?
Follow-up answer: If the target group shows unhealthy, it’s usually health check config or Kubernetes wiring. If targets look healthy but ALB still returns 502, it’s usually security groups, protocol mismatch, or app-level connection failures.

Infrastructure (AWS-side)

  • VPC, subnets, routing
  • EKS cluster
  • Node groups / Karpenter
  • IAM, OIDC, IRSA
How managed
  • Terraform
  • Separate state
  • Platform team only
Platform inside the cluster
  • Ingress controller
  • cert-manager
  • ExternalDNS
  • autoscalers
  • CSI drivers
  • observability
How managed
  • Helm
  • GitOps (ArgoCD / Flux)

Workloads

  • Deployments, Services, Ingress
  • HPA
  • ConfigMaps / Secrets
How managed
  • Namespaces
  • Helm charts
  • Team-owned repos

Why separate node groups in EKS

Common node pools
  • system (cluster infra)
  • private-nat (general workloads)
  • private-no-egress (restricted workloads)
  • batch / gpu (specialized)
Why
  • Prevent noisy neighbors
  • Control internet access
  • Predictable scaling and cost
How enforced
  • Subnets + routing
  • Security groups
  • Taints / tolerations
  • Node affinity

Who actually scales nodes in EKS

  • Cluster Autoscaler or Karpenter
Trigger
  • Pending pods
  • Resource requests, not usage
Key insight
  • Over-requested CPU/memory causes unnecessary scale-out

Requests vs usage

Question: Why does Kubernetes scale nodes based on requests, not usage?
Answer: Because the scheduler guarantees capacity. If requests can’t be satisfied, pods can’t be scheduled safely.
Follow-up: What’s the common failure mode here?
Follow-up answer: Over-requesting CPU or memory causes unnecessary node scaling and higher cost.

What health checks does an ASG use by default?

Answer: EC2 health checks only: hardware, network reachability, and hypervisor status.
Follow-up: What does that mean in practice?
Follow-up answer: ASG only knows whether the EC2 instance is alive from AWS’s perspective. It has no understanding of Kubernetes health.

Why ASG alone is insufficient in EKS

Question: Why can’t you rely on ASG alone for EKS scaling?
Answer: Because ASG has no awareness of Kubernetes scheduling, pod health, or resource pressure.
Follow-up: What happens if you don’t run a Cluster Autoscaler?
Follow-up answer: Pods remain pending forever even though ASG is healthy and running.

What ASG health checks ignore

Question: What does ASG not consider unhealthy?
Answer:
  • kubelet failures
  • CNI issues
  • Kubernetes NotReady state
  • Pods failing to schedule
Follow-up: Why is this dangerous in EKS?
Follow-up answer: Kubernetes may consider a node broken while ASG keeps it running, leading to stuck workloads and silent failures.

If a node is NotReady, will ASG replace it?

Answer: No. ASG only replaces instances if the EC2 health check fails.
Follow-up: So how are bad nodes handled in EKS?
Follow-up answer: Through Kubernetes controllers, Cluster Autoscaler logic, Karpenter, or manual remediation. ASG itself is unaware.

What is ASG’s role in EKS?

Answer: It manages EC2 instances only and ensures the desired number of nodes exist.
Follow-up: Does ASG understand Kubernetes at all?
Follow-up answer: No. ASG does not know about pods, scheduling, or cluster state.

Pods failing to schedule and Auto Scaling Groups

Question: If pods are failing to schedule, will that trigger the Auto Scaling Group (ASG)?
Answer: Not by itself. Unschedulable pods do not directly trigger an ASG scale-out. ASGs react to EC2-level signals (like CPU, memory via CloudWatch, or explicit scaling policies), not Kubernetes pod states.
What actually triggers scale-out: In EKS, scale-out happens only if you run a Cluster Autoscaler (or Karpenter). The autoscaler watches for pods that cannot be scheduled due to lack of resources and then requests new nodes by increasing the ASG desired capacity (or provisioning new instances).
Common failure case: Pods are pending, but the ASG does nothing because:
  • No Cluster Autoscaler is installed
  • The pod requests resources that no existing node type can satisfy
  • ASG has reached max capacity
  • Subnet or AZ capacity is exhausted
Mental model: Kubernetes decides what it wants to run. The autoscaler translates that into how many nodes are needed. The ASG only follows scaling instructions, it does not understand pods.

ASG vs HPA

Question: Does HPA affect ASG directly?
Answer: No. HPA scales pods, ASG scales nodes. They are decoupled.
Follow-up: How do they interact indirectly?
Follow-up answer: HPA creates more pods. If pods become unschedulable, the Cluster Autoscaler increases ASG desired capacity.
