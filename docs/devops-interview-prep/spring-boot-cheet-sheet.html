Spring Boot - Cheet-sheet

Spring vs Spring Boot

Spring Core Java framework that provides DI, web, DB, transactions, etc. You configure most things yourself.
Spring Boot Built on top of Spring. Auto-configures the app, gives defaults, embeds server, reduces setup.

Fundamentals: A Quick Reference

  • Spring Boot bootstraps and auto-configures a Java app
  • @SpringBootApplication is the usual entry point
  • Spring manages objects called `
  • Dependency injection means Spring provides dependencies instead of classes creating them
  • @RestController handles HTTP
  • @Service holds business logic
  • @Repository handles persistence
  • Request flow is controller -> service -> repository -> DB
  • @Valid validates input DTOs
  • @Transactional defines transaction boundaries
  • @ControllerAdvice = centralized exception handling
  • Spring Data JPA = ORM/repository layer for relational DB
  • application.yml = config like DB URL, ports, profiles

One full mini example

This is the whole picture in one place:
@SpringBootApplicationpublic class DemoApplication { public static void main(String[] args) { SpringApplication.run(DemoApplication.class, args); }}

@Entitypublic class User { @Id @GeneratedValue private Long id; private String name; private String email; // getters/setters}

public class CreateUserRequest { @NotBlank private String name; @Email private String email; // getters/setters}

@Repositorypublic interface UserRepository extends JpaRepository<User, Long> { Optional<User> findByEmail(String email);}

@Servicepublic class UserService { private final UserRepository repo; public UserService(UserRepository repo) { this.repo = repo; } @Transactional public User createUser(CreateUserRequest request) { if (repo.findByEmail(request.getEmail()).isPresent()) { throw new IllegalArgumentException("email already exists"); } User user = new User(); user.setName(request.getName()); user.setEmail(request.getEmail()); return repo.save(user); }}

@RestController@RequestMapping("/users")public class UserController { private final UserService service; public UserController(UserService service) { this.service = service; } @PostMapping public User create(@Valid @RequestBody CreateUserRequest request) { return service.createUser(request); }}

@ControllerAdvicepublic class GlobalExceptionHandler { @ExceptionHandler(IllegalArgumentException.class) public ResponseEntity<String> handleBadRequest(IllegalArgumentException ex) { return ResponseEntity.badRequest().body(ex.getMessage()); }}
If you understand that example, you understand the basics.

The mental model

A typical Spring Boot backend looks like this:
HTTP request -> Controller -> Service -> Repository -> DB
That layering is the main thing to understand.
  • Controller: receives HTTP request
  • Service: business logic
  • Repository: data access
  • DB: persistence
In interview terms, if they show you code, you should be able to say: “this endpoint enters through the controller, the service contains the business logic, and the repository talks to the database”
That alone already gets you most of the way.

1. @SpringBootApplication

This is the main annotation on the app entry class. In practice it marks the application as a Spring Boot app and bundles common behavior, including component scanning and auto-configuration. That is why one main class can bootstrap the app with very little manual setup.
Example:
@SpringBootApplicationpublic class MyApp { public static void main(String[] args) { SpringApplication.run(MyApp.class, args); }}
Quick reference:
@SpringBootApplication is usually the entry point. It tells Spring Boot to start the app, scan for components, and apply auto-configuration
Your C++ analogy:
  • this is like your main() plus framework bootstrap plus default wiring setup

2. Dependency Injection

This is the core Spring idea.
Instead of a class constructing its dependencies itself, Spring constructs them and injects them. Spring’s container manages objects called beans and wires them together by type and configuration. Spring supports constructor-based and setter-based injection, and constructor injection is the usual clean approach.
Without dependency injection:
public class UserService { private UserRepository repo = new UserRepository();}
With dependency injection:
@Servicepublic class UserService { private final UserRepository repo; public UserService(UserRepository repo) { this.repo = repo; }}
Why this matters:
  • easier testing
  • looser coupling
  • framework can manage lifecycle and configuration
C++ analogy:
  • instead of UserService doing new UserRepository(), something like an app container provides it
Quick reference:
Dependency injection means classes declare what they need, and Spring provides those dependencies rather than the class creating them itself

3. @RestController, @Service, @Repository

These are role markers.

@RestController

Used for HTTP endpoints. It handles incoming requests and returns responses.
@RestController@RequestMapping("/users")public class UserController { private final UserService service; public UserController(UserService service) { this.service = service; } @GetMapping("/{id}") public UserDto getUser(@PathVariable Long id) { return service.getUser(id); }}

@Service

Used for business logic.
@Servicepublic class UserService { private final UserRepository repo; public UserService(UserRepository repo) { this.repo = repo; } public UserDto getUser(Long id) { User user = repo.findById(id).orElseThrow(); return new UserDto(user.getId(), user.getName()); }}

@Repository

Used for persistence and DB access. Spring treats it as a persistence component and can translate persistence exceptions into Spring’s data-access exception model. Stereotype annotations such as @Component, @Service, and @Repository are recognized as Spring-managed components.
Quick reference:
Controller is the web boundary, service holds business logic, repository handles persistence
C++ analogy:
  • controller = request handler
  • service = domain/application layer
  • repository = DB adapter

4. Request flow: controller -> service -> repository -> DB

This is the flow you should be able to recognize instantly in code.
Example request:
GET /users/42
Flow:
  1. controller receives the HTTP request
  2. controller calls service
  3. service applies business logic
  4. service calls repository
  5. repository queries DB
  6. result goes back up the chain
  7. controller returns JSON
Why this matters:
  • helps you debug
  • helps you explain architecture
  • helps you know where bugs belong
Rule of thumb:
  • controller should stay thin
  • business rules should not live in controller
  • SQL and persistence details should not live in controller either
Quick reference:
I’d first identify the request path through controller, service, and repository, then narrow the bug to the correct layer

5. Component scanning

Spring can scan packages and automatically discover candidate classes and register them as beans instead of requiring manual XML registration. That is why annotations like @Service and @Repository matter. By default, Spring Boot scans from the package of the main application class downward.
Meaning:
  • if your MyApp class is in com.company.app
  • Spring usually scans com.company.app.*
Why bugs happen here:
  • class is in the wrong package
  • bean is not scanned
  • app fails because dependency cannot be found
Quick reference:
Component scanning is how Spring finds annotated classes and registers them as managed beans

6. Configuration: application.yml or application.properties

Spring Boot reads external configuration from files like application.properties or application.yml, environment variables, and other property sources. This is where DB URL, port, feature flags, profile-specific values, and secrets references often live.
Example application.yml:
server: port: 8080spring: datasource: url: jdbc:postgresql://localhost:5432/appdb username: appuser password: secret
Same idea in .properties:
server.port=8080spring.datasource.url=jdbc:postgresql://localhost:5432/appdbspring.datasource.username=appuserspring.datasource.password=secret
What to recognize in an interview zip:
  • DB config
  • active profile
  • ports
  • logging config
  • JPA settings
C++ analogy:
  • this is your config file plus env vars, but the framework knows how to bind those values into the app

7. Bean lifecycle, high level

A bean is just an object managed by Spring.
Very simplified lifecycle:
  1. Spring finds the class
  2. Spring creates the object
  3. Spring injects dependencies
  4. Spring keeps it in the application context
  5. app uses it where needed
  6. on shutdown, cleanup hooks may run
You do not need deep internals for today.
What matters:
  • Spring owns object creation for managed components
  • many beans are singleton by default
  • if something is not a bean, Spring cannot inject it
Quick reference:
A bean is a Spring-managed object. Spring creates it, wires dependencies into it, and keeps it in the application context

8. Exception handling with @ControllerAdvice

Instead of putting try/catch everywhere in controllers, Spring lets you define centralized exception handling for controllers with @ControllerAdvice. You can add @ExceptionHandler methods that map exceptions to HTTP responses.
Example:
@ControllerAdvicepublic class GlobalExceptionHandler { @ExceptionHandler(UserNotFoundException.class) public ResponseEntity<String> handleUserNotFound(UserNotFoundException ex) { return ResponseEntity.status(404).body(ex.getMessage()); }}
Why this is good:
  • keeps controllers clean
  • consistent error responses
  • easier maintenance
Quick reference:
@ControllerAdvice is for centralized web exception handling so controllers don’t need repetitive error-mapping logic

9. Validation with @Valid

Spring integrates with Bean Validation so you can validate request objects automatically. Mark the request body parameter with @Valid, and Spring will validate constraints such as @NotNull, @Size, @Email, and so on before your business logic runs.
Example:
public class CreateUserRequest { @NotBlank private String name; @Email private String email; // getters/setters}
Controller:
@PostMappingpublic ResponseEntity<Void> createUser(@Valid @RequestBody CreateUserRequest request) { service.createUser(request); return ResponseEntity.ok().build();}
Why it matters:
  • fail fast
  • less manual validation code
  • cleaner boundary checks
Quick reference:
@Valid lets the framework validate incoming request DTOs automatically before the service layer runs

10. Spring Data JPA basics

This is the DB abstraction they are very likely to use.
JPA is the Java persistence model for mapping classes to relational DB tables. Spring Data JPA builds on that and lets you define repositories with less boilerplate. In many cases, you create an interface that extends a Spring Data repository type and get common CRUD behavior automatically.
Entity example:
@Entitypublic class User { @Id @GeneratedValue private Long id; private String name; private String email;}
Repository example:
@Repositorypublic interface UserRepository extends JpaRepository<User, Long> { Optional<User> findByEmail(String email);}
What this gives you:
  • object-to-table mapping
  • CRUD operations
  • query methods by naming convention
  • less raw SQL in basic cases
Common interview bug areas here:
  • lazy loading surprises
  • N+1 queries
  • wrong entity relationships
  • missing transaction boundaries
  • bad query assumptions
C++ analogy:
  • imagine an ORM layer that maps objects to SQL rows and generates common persistence operations

11. @Transactional

This marks a transaction boundary. Spring’s transaction management lets you define that a method should run within a transaction, so related DB operations succeed or fail together.
Example:
@Servicepublic class OrderService { private final OrderRepository orderRepo; private final InventoryRepository inventoryRepo; public OrderService(OrderRepository orderRepo, InventoryRepository inventoryRepo) { this.orderRepo = orderRepo; this.inventoryRepo = inventoryRepo; } @Transactional public void placeOrder(Order order) { orderRepo.save(order); inventoryRepo.decreaseStock(order.getItemId(), order.getQuantity()); }}
Meaning:
  • if one DB operation fails, the whole transaction can roll back
  • helps preserve consistency
Why interviewers care:
  • many bugs happen because transaction boundaries are wrong
  • updates may partially succeed
  • lazy loading may fail outside a transaction
  • concurrent behavior can get weird
Quick reference:
@Transactional defines a transaction boundary, so related persistence operations are treated as one unit of work

Repo Scan

Use this prompt:
You are reviewing a Java Spring Boot codebase for a technical interview.

Your job is to scan the project and identify potential bugs, design flaws, misconfigurations, reliability issues, and architecture problems.

I do NOT want a shallow summary. I want a structured audit.

Goals:
1. Understand the codebase structure first
2. Trace request flow: controller → service → repository → DB/integration
3. Find likely bugs and risky patterns
4. Explain each issue clearly and technically
5. Suggest the correct fix or better design
6. Prioritize findings by severity and confidence

Instructions:

First, map the project:
- main application entry point
- packages/modules
- controllers
- services
- repositories
- entities/models/DTOs
- config classes
- exception handlers
- tests
- build file and dependencies
- application.yml / application.properties
- DB-related code
- external integrations

Then inspect the code for issues in these buckets:

1. Dependency injection / bean issues
- missing bean
- wrong component scan
- circular dependency
- concrete class injection where interface would be better
- suspicious singleton mutable state

2. REST/controller issues
- wrong request mapping
- wrong HTTP method semantics
- bad path variable / request param binding
- missing @RequestBody / @Valid
- weak input validation
- bad status codes
- inconsistent API responses
- exception handling problems
- business logic leaking into controller

3. Service layer issues
- business rules in wrong layer
- null handling bugs
- unsafe Optional usage
- boundary / edge case bugs
- lack of idempotency
- transactional mistakes
- hidden coupling
- unclear separation of concerns

4. Repository / DB issues
- incorrect query definitions
- broken JPQL/SQL
- lazy loading risks
- N+1 query risks
- missing transaction boundaries
- duplicate write risks
- data consistency bugs
- uniqueness / constraint handling problems
- inefficient queries or pagination issues

5. Config / environment issues
- wrong profile usage
- missing or unresolved properties
- bad datasource config
- environment-specific assumptions
- hardcoded paths/URLs/secrets
- startup-time misconfiguration risks

6. Concurrency / reliability issues
- race conditions
- non-thread-safe shared state
- retry-unsafety for side effects
- partial failure across DB + external API
- no timeout / fallback / error handling around integrations
- operations that can succeed twice under retry

For every issue you find, use this exact format:

Issue #N
Title: <short name>
Severity: Critical / High / Medium / Low
Confidence: High / Medium / Low
Location: <file + class + method, and line if possible>
Category: <one of the buckets above>

What is happening:
<describe the code behavior>

Why this is a problem:
<technical explanation in simple words>

Risk / impact:
<what can break in production or in edge cases>

Recommended fix:
<show the correct approach, with small code snippet if useful>

Evidence:
<quote or reference the actual code pattern that triggered the finding>

Also include:
- “Potential issues” when evidence is suggestive but not fully proven
- “Confirmed issues” when the code clearly demonstrates the problem

At the end, give me 3 summary sections:

1. Highest-risk findings
- top 5 issues worth mentioning in an interview

2. Likely interview talking points
- architecture flaws
- reliability concerns
- Spring Boot specific problems
- DB and transaction concerns

3. Quick win fixes
- easiest changes with highest impact

Important rules:
- Do not invent issues without evidence
- Do not stop at syntax or formatting
- Focus on correctness, architecture, Spring Boot behavior, transactions, and production reliability
- Explain things in technical terms, but in plain English
- Prefer concrete findings over generic advice
- If something depends on runtime configuration, explicitly say that
- If there are tests, compare the code against what the tests expect
- Flag suspicious places where the code may fail only under concurrency, retries, or invalid input

Start by giving me:
1. a short map of the codebase
2. then the full findings report
A shorter version, if you want something more aggressive and fast:
Scan this Java Spring Boot codebase like a senior reviewer preparing me for a technical interview.

First map the architecture:
- entry point
- controllers
- services
- repositories
- entities
- config
- exception handling
- tests
- DB/integrations

Then find potential bugs and design flaws in these categories:
- dependency injection / bean wiring
- REST/controller problems
- service-layer logic issues
- repository/DB/query/transaction issues
- config/profile/property issues
- concurrency/reliability issues

For each finding, output:
- title
- severity
- confidence
- file/class/method
- what is happening
- why it is a problem
- production risk
- recommended fix
- supporting evidence from code

Focus on:
- Spring Boot wiring
- request flow
- validation
- exception handling
- transactions
- lazy loading / N+1
- idempotency
- duplicate writes
- race conditions
- partial failure
- bad config assumptions

Separate findings into:
- Confirmed issues
- Potential issues

End with:
- top 5 biggest risks
- likely interview talking points
- quick win fixes
Best way to use it in practice:
  1. First run the short prompt on the whole repo
  2. Then run a follow-up like:
Now go deeper only on transaction, DB, and concurrency issues. Show me the exact code paths and failure scenarios.
  1. Then another:
Now go deeper only on controller/service layering, validation, and exception handling.
That gets better results than one giant pass only.
